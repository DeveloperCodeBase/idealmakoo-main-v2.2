# ابزارهای شاهدِ مستقل برای مسیر proxy در ممیزی

این پوشه ابزارهای **ثبت هویت محیط آزمون و صدور شواهد امن** را نگه می‌دارد.
این‌ها بخشی از کد اجراشوندهٔ وب‌سایت یا جایگزین راهنمای نصب محصول نیستند.
هیچ فایل محیط واقعی، اطلاعات ورود، قرارداد خصوصیِ یک اجرا، log خام یا تصویر
مرورگر در این پوشه قرار ندارد. مسیرها و شناسه‌های مثال‌ها باید توسط مسئول
محیط تعیین شوند؛ هیچ مثال زیر به‌تنهایی اجازهٔ فعال‌سازی محیط دیگری نیست.

**وضعیت شواهد این پوشه در زمان تهیه:** ۲۲ آزمون متمرکز guard و چهار آزمون
مصنوعی چرخهٔ توقف موفق شده‌اند. بازبینی مستقلِ محدود نیز بسته شده است.
این موفقیت‌ها به معنی استخراج واقعی Caddy، ورود به حساب آزمایشی، پاک‌سازی
واقعی دیتابیس یا کامل‌شدن Lighthouse نیستند. آن موارد فقط با رسید جداگانهٔ
همان اجرای واقعی قابل استنادند.

## فایل‌ها و حدود کار

| فایل | کاربرد |
| --- | --- |
| `native-proxy-guard.py` | آماده‌سازی مشتق محدود، ثبت هویت زنده، کنترل قبل/حین/بعد فرمان و صدور مشتق امنِ قرارداد |
| `prove-native-proxy.mjs` | بررسی محدودِ HTTP و سپس ورود واقعیِ حساب آزمایشیِ از قبل موجود، MFA، محدودیت IP و پاک‌سازی همان حساب |
| `proxy-proof-lifecycle.mjs` | مهلت مطلق درخواست و مدیریت `SIGTERM`/`SIGINT` برای ابزار بالا |
| `test-proxy-proof-lifecycle.mjs` | سرور HTTP موقتِ loopback و فرزندان موقت Node برای بررسی deadline و سیگنال |
| `*.safe.json` | رسیدهای منتخب با hash نسخه‌های دقیق، نتیجهٔ واقعی آزمون و مرز ادعا |

فایل‌های کدِ موجود در این پوشه با نسخهٔ بررسی‌شده بایت‌به‌بایت برابرند؛ hashها در
`EXPORT.safe.json` آمده‌اند. رسید بازبینی مستقل، آزمون اجرایی نیست و به‌عنوان
چنین آزمونی شمارش نمی‌شود. نخستین خطای استخراج خلاصهٔ تست‌ها نیز حفظ شده:
خلاصه‌خوان، خروجی TAP انتظار داشت ولی Node گزارش متنی داده بود؛ فرمان چهار
آزمون از ابتدا موفق بود و برای اصلاح این خلاصه دوباره اجرا نشد.

کپیِ مستنداتیِ `test_native_proxy_guard.py` **در بسته ارسال نمی‌شود**. بررسی
واقعیِ بسته، نمونه‌های URI آن را تحت قانون ثابتِ منع رمز داخل سورس رد کرد.
قانون بررسی تغییر نکرد و literalهای سورس آزموده‌شده هم دست‌کاری نشدند؛ فقط
کپیِ اضافی از این پوشه کنار گذاشته شد. سورس اصلیِ آزمون با SHA256 برابر
`bb2d7b4fe22736e696b748a470ea6d5b5de5e4ccf5bdbc7c4413c5c2d69d8a32`
در بایگانی آزمون باقی است. رسید ۲۲ آزمون، hash سورس و تمام تلاش‌های قبلی در
این پوشه حفظ شده‌اند، اما اجرای دوبارهٔ همان ۲۲ تست به آن harness خارج از
بسته نیاز دارد. تست‌های اصلی محصول و ابزار اجرایی guard حذف نشده‌اند.
`EXPORT.historical-before-package-check.safe.json` فهرست تاریخیِ پیش از این
کنترل است و شامل نام harness ارسال‌نشده می‌شود؛ فهرست فعلی فقط
`EXPORT.safe.json` است. دلیل و نتیجهٔ بررسیِ محدود در
`packaging-correction.safe.json` ثبت می‌شود.

## پیش‌نیازهای صریح و محدودیت جابه‌جایی

guard به Linux، Python 3، `/proc`، namespace واقعی پردازش‌های تحت بررسی،
قابلیت خواندن xattr و امکان خواندن وضعیت پردازش‌های متعلق به اجرا نیاز دارد.
در این مسیر، Caddy مطابق پیکربندی محصول با UID/GID عددی `10002` بررسی می‌شود.
مشاهدهٔ پردازش متعلق به آن کاربر ممکن است از خواندن مستقیم منع شود؛ ابزار
این منع را ثبت می‌کند و فقط در محیط مجاز، خوانندهٔ جداگانه‌ای با همان UID
ایجاد می‌کند. اگر مشاهده واقعاً ممکن نباشد، رد می‌کند؛ تنظیمات `/proc` یا
مجوز `ptrace` را ضعیف نمی‌کند.

ابزار HTTP به Node و وابستگی‌های همان پروژه، از جمله `tsx`، `pg` و `sharp`
نیاز دارد. مسیر پروژه صریح است؛ importهای داخل پروژه بر اساس همان مسیر حل
می‌شوند. هیچ مسیر مطلقِ متعلق به دستگاه تهیهٔ این بسته در کد ثابت نشده است.
بااین‌حال، ابزار عمومی و مستقل از محصول نیست: ساختار `.next/BUILD_ID`،
`deploy/caddy/Caddyfile`، APIها، نقش‌ها، fixture policy، یک آیکن و یک تصویر
عمومی همین محصول را می‌شناسد. پشتیبانی از معماری دیگر، پروکسی دیگر یا نسخهٔ
دیگری از این قراردادها ادعا نمی‌شود. قرارداد استخراج، ELF64/x86_64 را می‌سنجد.

مبدأ بیرونی و upstream باید HTTP و IPv4 loopback، با پورت‌های متفاوتِ بیشتر
از ۱۰۲۴ باشند. این شاهد TLS، HTTP/2، شبکهٔ بیرونی یا ایزولاسیون کانتینر را
نمی‌سنجد. ابزارهای احراز هویت فقط دیتابیس آزمونِ loopback با نام مجاز و نقش
اجراییِ جدا از نقش fixture را می‌پذیرند؛ روی دیتابیس عملیاتی اجرا نشوند.

## ۱. آماده‌سازیِ بدون فعال‌سازی

متغیرهای زیر فقط نشانی و هویت آزمایش‌اند؛ رمز یا کلید را در فرمان قرار ندهید.
فایل runtime باید فقط دسترسی محدود برنامه را داشته باشد. فایل harness جداگانه
می‌تواند اتصال مدیریتی fixture به **همان** میزبان، پورت و دیتابیس مجاز را داشته باشد.

```bash
AUDIT_PROJECT=/absolute/path/to/project
AUDIT_TOOLS=/absolute/path/to/this-tools-directory
AUDIT_ROOT=/absolute/path/to/new-private-audit-directory
AUDIT_RUNTIME_ENV=/absolute/path/to/private-runtime.env
AUDIT_HARNESS_ENV=/absolute/path/to/private-harness.env
AUDIT_INPUT_RECEIPT=/absolute/path/to/application-inputs.safe.json
AUDIT_BUILD_ID=REPLACE_WITH_ACTUAL_BUILD_ID
AUDIT_INPUT_SHA=REPLACE_WITH_ACTUAL_INPUT_FINGERPRINT

python3 "$AUDIT_TOOLS/native-proxy-guard.py" prepare \
  --project "$AUDIT_PROJECT" \
  --runtime-env "$AUDIT_RUNTIME_ENV" \
  --harness-env "$AUDIT_HARNESS_ENV" \
  --output "$AUDIT_ROOT" \
  --origin http://127.0.0.1:3100 \
  --upstream http://127.0.0.1:3102 \
  --inputs "$AUDIT_INPUT_RECEIPT" \
  --build-id "$AUDIT_BUILD_ID" \
  --input-fingerprint "$AUDIT_INPUT_SHA"
```

مقصد باید تازه باشد. تغییر مجاز در هر فایل محیط فقط یک خط `TRUST_PROXY=false`
به `true` است؛ شکل نقل‌قول و سایر بایت‌ها حفظ می‌شوند. این محدودیت مخصوص
مشتقِ محیط آزمون است؛ تنظیم عملیاتی سایت را برای راضی‌کردن ابزار عوض نکنید.
در Caddy فقط upstream عوض و `bind 127.0.0.1` اضافه می‌شود. اصل فایل‌ها حفظ
می‌شود. ابزار سرویس، دیتابیس یا مرورگری راه نمی‌اندازد.

## ۲. باینری، تنظیم مؤثر و پردازش‌های زنده

مسئول محیط باید همان باینریِ تصویر واقعاً آزموده‌شده را با رسید استخراج
`idealmakoo-caddy-extraction-v1` فراهم کند. یک tag متغیر یا ادعای شفاهی کافی نیست.
guard این داده‌ها را با فایل واقعی و خروجی همان باینری مقایسه می‌کند:

| بخش رسید | کنترل لازم |
| --- | --- |
| `format` و `status` | قرارداد دقیق و نتیجهٔ واقعیِ موفق |
| `source.imageId` | همان شناسهٔ immutable معرفی‌شده به `seal` |
| `source.binaryPath` | `/usr/bin/caddy` |
| `source` و `hostCopy` | SHA256، تعداد بایت، نسخهٔ دقیق و معماری برابر با فایل واقعی |
| `hostCopy.permissions` | mode، uid و gid عددی برابر با فایل واقعی |
| capability | مشاهدهٔ صریح منبع؛ نبود `security.capability` در فایل میزبان با بررسی مستقل |
| منشأ | هویت منبع ثابت، بایت‌های برابر، منبع تغییرنکرده و دانلود تازه انجام‌نشده |

فهرست repository digest ممکن است برای تصویر محلی خالی باشد؛ شناسهٔ واقعی
image و hash فایل همچنان لازم‌اند. ابزار رسید ساختگی تولید نمی‌کند.

باینری و JSON مؤثر باید root-owned و برای کاربر Caddy غیرقابل‌نوشتن باشند؛
پوشهٔ والد نیز نباید امکان حذف یا جایگزینی فایل به آن کاربر بدهد. پوشه‌های
داده و تنظیمِ قابل‌نوشتن Caddy جدا، متعلق به `10002:10002` و با mode `0700`
هستند. محیط Caddy دقیقاً چهار نام `SITE_ADDRESS`، `PATH`، `XDG_DATA_HOME` و
`XDG_CONFIG_HOME` دارد. کلیدهای برنامه و proxy شبکهٔ محیط میزبان به آن منتقل
نمی‌شوند. `admin off`، نبود watch/reload، بدون capability و `no_new_privs`
حفظ می‌شوند. این ابزار launcher سرویس نیست.

Next باید فایل runtime مشتق را با override صریحِ `PORT=3102` و
`HOSTNAME=127.0.0.1` بگیرد؛ worker همان runtime را بدون override listener
می‌گیرد. محیط باید **پیش از exec** برقرار باشد: `/proc/PID/environ` لزوماً
تغییرهایی را که Node بعداً از `--env-file` بار کرده نشان نمی‌دهد. نبودِ مشاهده
به معنی تطابق نیست. همهٔ متغیرهای تعریف‌شده در فایل runtime در حافظه مقایسه
می‌شوند؛ برابری همهٔ متغیرهای سیستم‌عامل ادعا نمی‌شود. سه اتصال مدیریتی
`TEST_DATABASE_URL`، `TEST_ADMIN_DATABASE_URL`، `MIGRATION_DATABASE_URL` و
تمام نام‌های `BOOTSTRAP_ADMIN_` در app و worker ممنوع‌اند.

پس از راه‌اندازی مجازِ همان سرویس‌ها، `seal` با پارامترهای زیر اجرا می‌شود:

```bash
python3 "$AUDIT_TOOLS/native-proxy-guard.py" seal \
  --plan "$AUDIT_ROOT/plan.json" \
  --binary "$AUDIT_CADDY_BINARY" \
  --adapted-config "$AUDIT_ADAPTED_JSON" \
  --provenance "$AUDIT_EXTRACTION_RECEIPT" \
  --image-id "$AUDIT_CADDY_IMAGE_ID" \
  --caddy-data-dir "$AUDIT_CADDY_DATA" \
  --caddy-config-dir "$AUDIT_CADDY_CONFIG" \
  --native-pid-namespace "$AUDIT_NATIVE_PID_NAMESPACE" \
  --caddy-pid "$AUDIT_CADDY_PID" \
  --next-pid "$AUDIT_NEXT_PID" \
  --worker-pid "$AUDIT_WORKER_PID" \
  --output "$AUDIT_ROOT/topology.private.json"
```

همهٔ متغیرهای بالا باید از **مشاهدهٔ واقعی همان محیط** پر شوند. فضای PID
یک sandbox دیگر جای namespace میزبان را نمی‌گیرد. hash قرارداد خصوصی که
خود `seal` برمی‌گرداند، برای تمام مراحل بعدی ثابت می‌ماند.

## ۳. ترتیب بررسی محدود و ثابت‌کردن موجودی

ترتیب مجاز قبل از امتیازدهی چنین است:

1. `verify` واقعی و بررسی عمومی HTTP: readiness، gzip در برابر identity،
   برابری بایت‌های JSON بازشده، origin/redirect، CSP، noindex، رد ناشناس و دارایی‌ها.
2. اجرای گزینهٔ موجود `--prepare-fixtures-only` در ابزار خصوصی پروژه؛ هر ۱۲
   حساب و همان درخواست متعلق به مشتری پیش از هر manifest آماده می‌شوند.
3. حالت `authenticated` ابزار این پوشه: فقط همان `superAdmin` موجود برای
   دو ورود واقعی، enrollment/TOTP، رد CSRF/origin/MFA و بررسی IP به کار می‌رود؛
   حساب اضافی، ارسال پیام و reset سهمیه‌ای انجام نمی‌شود.
4. غیرفعال‌کردن و revoke نشست همان حساب با helper موجود و خواندن نتیجهٔ واقعی.
5. ساخت موجودی تازهٔ خصوصی/عمومی و crawl metadata؛ سپس مراحل امتیازدهی سریالی.

حالت authenticated، نبودِ manifest قبلی، هویت هر ۱۲ حساب آماده و غیرفعال و
تازه‌بودن وضعیت MFA حساب مورد استفاده را کنترل می‌کند. تلاش ناموفق را با
ویرایش وضعیت MFA یا reset محدودیت‌ها به موفقیت تبدیل نکنید. خطا و پاک‌سازی
نامعلوم باید در رسید همان تلاش باقی بماند.

هر فرمان داخل `run` اجرا می‌شود؛ نمونهٔ قالب برای بررسی عمومی:

```bash
python3 "$AUDIT_TOOLS/native-proxy-guard.py" run \
  --contract "$AUDIT_ROOT/topology.private.json" \
  --topology-sha256 "$AUDIT_TOPOLOGY_SHA" \
  --phase public-transport-proof-01 \
  --receipt-dir "$AUDIT_ROOT/phase-receipts" \
  --kind metadata --environment runtime -- \
  node --env-file="$AUDIT_ROOT/audit.proxy.runtime.env" --import tsx \
  "$AUDIT_TOOLS/prove-native-proxy.mjs" \
  --project "$AUDIT_PROJECT" \
  --base-url http://127.0.0.1:3100 \
  --upstream-url http://127.0.0.1:3102 \
  --build-id "$AUDIT_BUILD_ID" --mode public \
  --output "$AUDIT_ROOT/proof-public-01.safe.json"
```

فرمان Node از ریشهٔ پروژه اجرا می‌شود. برای حالت authenticated، محیط harness،
`--kind fixtures`، `--mode authenticated` و مسیر صریحِ اجرای آماده‌شده در
`--private-run` لازم‌اند. هر نام phase و مقصد رسید باید تازه باشد.

در مراحل موجودی، امتیازدهی و صدور شواهد، گزینهٔ تکرارپذیر `--artifact-dir`
را برای پوشه‌های مربوط بدهید تا hashهای manifest، inventory، summary و
`EXPORT.json` به همان رسید متصل شوند. ابزار اصلی و سیاست امتیاز، نشست، نقش
و پاک‌کردن کش تغییر نمی‌کنند. **`configurationHash` ابزار اصلی به‌تنهایی
هویت proxy را مقید نمی‌کند**؛ پیوند جانبیِ این رسیدها ضروری است.

## ۴. توقف، مهلت و تفسیر نتیجه

guard قبل و بعد هر مرحله کنترل کامل و هنگام فرمان هر پنج ثانیه کنترل سبک
انجام می‌دهد. تغییر هویت، فقط به فرمان فرزند متعلق به خودش `SIGTERM` می‌دهد؛
fallback اجباریِ پس از ۶۰ ثانیه، جدا ثبت می‌شود. خروج واقعی فرمان، سیگنال و
نتیجهٔ کنترل topology از هم جدا هستند. guard پاک‌سازی یک صفحهٔ قطع‌شده را
از روی پایان فرایند حدس نمی‌زند.

بررسی HTTP حداکثر ۶۴ درخواست و برای هر درخواست مهلت **مطلق ۳۰ ثانیه** دارد؛
رسیدن قطره‌قطرهٔ داده این مهلت را تمدید نمی‌کند. `SIGTERM`/`SIGINT` به وضعیت
ناموفق/قطع‌شده و `finally` ناهمزمان می‌رسند. مسئولیت پاک‌سازی پیش از انتظار
برای فعال‌کردن حساب ثبت می‌شود تا فعال‌سازی نیمه‌تمام هم بررسی شود. اتصال
کوتاهِ مخصوص پاک‌سازی، statement timeout پنج‌ثانیه‌ای دارد و پس از readback
از بین می‌رود؛ این تغییر به اتصال‌ها یا سیاست برنامه اعمال نمی‌شود.

خروج `72` از guard امتناع کنترل هویت/مشاهده است؛ خودبه‌خود شکست Lighthouse
نیست. خروج `2` ابزار proof یعنی خود proof یا پاک‌سازی موفق نشده است. نتیجهٔ
هر تلاش، از جمله شکست، باید حفظ شود؛ ادامهٔ همان ممیزی فقط با هویت یکسان
و سیاست resume ابزار اصلی مجاز است.

## ۵. صدور امن و بازتولید آزمون‌های کمکی

قرارداد اصلی خصوصی می‌ماند. مشتق منتخب با این فرمان تولید می‌شود:

```bash
python3 "$AUDIT_TOOLS/native-proxy-guard.py" export-topology \
  --contract "$AUDIT_ROOT/topology.private.json" \
  --topology-sha256 "$AUDIT_TOPOLOGY_SHA" \
  --output "$AUDIT_ROOT/topology.safe.json"
```

این مشتق هویت تاریخیِ زمان seal است؛ زنده‌بودن فعلی را ادعا نمی‌کند و به
رسیدهای مراحل نیاز دارد. مقدار یا hash کلید محرمانه، مسیر فایل محیط، آرگومان
خام، PID خام، کوکی، DOM خصوصی و تصویر در آن صادر نمی‌شود. گزارش خصوصی فقط
با exporter سخت‌گیر موجود پروژه، و گزارش عمومی فقط با مشتقِ بدون تصویرِ
مستندشده صادر می‌شود. گزارش خام یا log را کنار این ابزارها قرار ندهید.

چهار آزمون چرخهٔ توقف که سورسشان در این پوشه موجود است، بدون وب‌سایت یا
دیتابیس برنامه قابل اجرا هستند:

```bash
node --test "$AUDIT_TOOLS/test-proxy-proof-lifecycle.mjs"
```

این آزمون یک سرور موقت loopback و فرزندان موقت Node ایجاد می‌کند. رسید ۲۲

## اصلاح محدودِ مقایسهٔ پاسخ عمومی

اولین شاهد واقعیِ فشرده‌سازی با خروج ۲ در مقایسهٔ بایت‌های دو پاسخ شکست خورد؛ کنترل هویت proxy، وضعیت HTTP و gzip موفق بودند. API عمومی در هر پاسخ یک `observedAt` تازه می‌سازد. بررسی دو پاسخ فقط تفاوت همین فیلد را نشان داد. نسخهٔ پیشین و رسید شکست حفظ شده‌اند.

ابزار جاری فقط برای `/api/v1/site`، پس از اعتبارسنجی قالب دقیق UTC هر دو timestamp، برابری ساختاری همهٔ داده‌ها به‌جز همین فیلد سطح اول را می‌سنجد. `rawDecodedBytesEqual` نتیجهٔ واقعیِ برابری بایت‌ها را جدا گزارش می‌کند؛ برابری بایتی پس از حذف فیلد ادعا نمی‌شود. مقایسهٔ خصوصی `/workspace` همچنان دقیقاً بایتی است. سه آزمون مستقلِ این اصلاح با خروج صفر گذشتند و بازبینی محدود عامل همکار نیز hashهای دقیق را تأیید کرد. این شاهد آزمون کمکی، جای تلاش واقعی تازه را نمی‌گیرد.

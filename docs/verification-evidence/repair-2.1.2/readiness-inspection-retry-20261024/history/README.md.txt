# Ideal Makoo — سامانهٔ سروری ۲٫۱٫۲

کد کامل سایت پنج‌زبانه، پنل مدیریت محتوا، CRM و حساب مشتری، با Next.js و TypeScript، PostgreSQL 16، صف پایدار، رسانهٔ خصوصی و استقرار Docker Compose.

این نسخه، فرانت‌اند تحویل‌شده را به سرور واقعی وصل می‌کند. نشست، مجوز، داده، انتشار و درخواست‌ها از PostgreSQL خوانده می‌شوند. در حالت production، ورود دمو و انتخاب نقش از localStorage غیرفعال است. اطلاعات کاتالوگ و فایل‌های مرجع قبلی حفظ شده‌اند؛ حساب مشتری، پرونده، عضو سازمان و آمار تجاری ساختگی seed نمی‌شوند.

## قابلیت‌های اصلی

پیش‌فرض نسخهٔ ۲.۱، مدیریت کاربران از پنل در حالت `hybrid` است: مالک می‌تواند کاربر جدید با نقش، زبان‌های مجاز و دسترسی‌های مرتبط بسازد. اطلاعات، ایمیل، وضعیت و رمز کاربران از همان پنل و در محدودهٔ مجوز مدیر قابل تغییرند. حساب‌های اولیه همچنان از env ساخته می‌شوند و اجرای عادی seed، ویرایش‌های بعدی پنل را بازنویسی نمی‌کند. ثبت‌نام عمومی فقط حساب مشتری ایجاد می‌کند. حالت صریح `env` مدیریت اختیار کارکنان را به فرمان مالک محدود می‌کند. [راهنمای مدیریت کاربران](docs/USER-MANAGEMENT.fa.md).

قابلیت‌های اصلی این اصلاح شامل محتوای اولیهٔ قابل ویرایش، ترجمه و انتشار مستقل زبان‌ها، پیشنهاد AI قابل بازبینی، محدودیت فایل و سهمیه از پنل، دانلود جریانی با بررسی مجوز، و بکاپ کامل رمزنگاری‌شده با دانلود و بازیابی است. [برنامهٔ اجرایی اصلاح](docs/REPAIR-2.1.2-PLAN.fa.md) مراحل و معیار پذیرش را مشخص می‌کند.

سورس شامل ۴۱ migration تا شمارهٔ `042` است؛ شمارهٔ `005` وجود ندارد. نصب تازه ۱۲۰ پیش‌نویس صفحهٔ منبع و ۱۷ محصول کاتالوگ را آماده می‌کند. دادهٔ ساختگی مشتری یا معامله ساخته نمی‌شود. اطلاعات محتوایی، نقش، مجوز و انتشار از PostgreSQL خوانده می‌شوند.

## سازگاری با سورس ارسالی ۲٫۰٫۰

هر ۳۷ فایل migration موجود در آرشیو ارسالی ۲٫۰٫۰، با فایل متناظر همین نسخه بایت‌به‌بایت برابر است؛ چهار migration جدید به آن‌ها افزوده شده و مجموع به ۴۱ رسیده است. شمارهٔ `005` در مجموعهٔ اصلی نیز وجود ندارد. در پذیرش تاریخی نسخهٔ ۲٫۱٫۱، migrationهای اصلی روی PostgreSQL واقعی اجرا شدند، ارتقا دقیقاً چهار migration افزود و اجرای دوباره تغییری نداد؛ چهار ردیف آزمایشی و ledger قبلی حفظ شدند. این آزمایش ارتقا در نوبت ۲٫۱٫۲ دوباره اجرا نشده است. هر ۴۱ migration و ابزارهای مربوط نسبت به ۲٫۱٫۱ ثابت‌اند و نصب دیتابیس تازه در این نوبت بررسی شده است. این آزمایش محدود، وضعیت تمام داده‌های دیتابیس نصب‌شده روی سرور دیگر را ثابت نمی‌کند.

پیش از ارتقا، بکاپ معتبر بگیرید و ledger واقعی دیتابیس را با سورس نصب‌شده بررسی کنید. ابزار migration اگر checksum یک فایل اجراشده تغییر کرده باشد متوقف می‌شود؛ ledger یا checksum را برای عبور از خطا بازنویسی نکنید. مراحل نصب تازه، ارتقا و بازگشت در [راهنمای استقرار](docs/DEPLOYMENT.fa.md) آمده‌اند.

## نصب روی اوبونتو با یک فرمان

بسته را روی سرور انتقال و استخراج کنید. برای تنظیم تمام حساب‌ها و سرویس‌ها، از `.env.example` یک فایل خصوصی با مجوز `600` بسازید و `SITE_URL`، `SITE_ADDRESS`، `ACME_EMAIL`، اطلاعات مدیر و `STAFF_ACCOUNTS_JSON` را طبق راهنما تکمیل کنید. سپس داخل پوشهٔ پروژه، نصب را با یک فرمان اجرا کنید:

```bash
sudo bash scripts/install-ubuntu.sh --env-file /root/idealmakoo.env --app-dir /var/www/idealmakoo-v2
```

فایل env ورودی، کد shell نیست و اجرا نمی‌شود. رمزهای داخلیِ خالی فقط در نصب اول تولید می‌شوند؛ کلید واقعی سرویس خارجی را اپراتور وارد می‌کند. نصابِ بدون env ورودی نیز از این فرمان پشتیبانی می‌کند و یک مدیر اولیه با رمز اختصاصی می‌سازد:

```bash
sudo bash scripts/install-ubuntu.sh --domain idealmako.ir --email YOUR_REAL_EMAIL --app-dir /var/www/idealmakoo-v2
```

برای دامنهٔ دیگری، مقدار `--domain` را عوض کنید. DNS باید به سرور اشاره کند و پورت‌های ۸۰ و ۴۴۳ آزاد باشند. نصاب برای Ubuntu 22.04/24.04 با systemd و sudo تهیه شده است. حداقل ظرفیت پیشنهادی با ClamAV محلی: ۶ گیگابایت RAM و ۱۵ گیگابایت دیسک آزاد؛ ۸ گیگابایت RAM برای build و بهره‌برداری مناسب‌تر است. نصب اولیه به دسترسی اینترنت به مخازن سیستم‌عامل، رجیستری و npm نیاز دارد.

این فرمان Docker را در صورت نیاز نصب می‌کند، رمزهای تصادفی ایجاد می‌کند، تصویر برنامه را می‌سازد، migration و seed را اجرا می‌کند، برنامه و worker و TLS را بالا می‌آورد و بکاپ رمزنگاری‌شدهٔ زمان‌بندی‌شده تنظیم می‌کند. کد سایت دیگری یا دادهٔ موجود بی‌ارتباط حذف نمی‌شود. تداخل پورت یا نصب موجود با خطای مشخص متوقف می‌شود.

راهنمای کامل، حالت HTTP آزمایشی، پیش‌نیازها و نصب دستی: [DEPLOYMENT.fa.md](docs/DEPLOYMENT.fa.md).

## ورود اولیه

حساب مدیر از `BOOTSTRAP_ADMIN_EMAIL` ساخته می‌شود. نصاب به‌صورت پیش‌فرض از `admin@دامنه` استفاده می‌کند؛ `--admin-email` آن را تغییر می‌دهد. رمز تصادفی در فایل محافظت‌شدهٔ `shared/.env` همان نصب قرار دارد و در خروجی یا بستهٔ سورس چاپ نمی‌شود.

۱. وارد `/fa/auth/login/` شوید.
۲. در بخش امنیت حساب، MFA را با برنامهٔ احراز هویت فعال کنید و کدهای بازیابی را در جای امن نگه دارید.
۳. رمز اولیه را تغییر دهید.
۴. از بخش کاربران پنل، حساب جدید، نقش، زبان و مجوزهای لازم را تعیین کنید. ساخت اولیهٔ تیم از `STAFF_ACCOUNTS_JSON` و فرمان مالک `scripts/provision-staff.sh` نیز پشتیبانی می‌شود. حالت پیش‌فرض `hybrid` هر دو مسیر را فراهم می‌کند؛ حالت صریح `env` مدیریت اختیار کارکنان را به فرمان مالک محدود می‌کند. برای انتشار محتوای نیازمند بازبینی، نویسنده و بازبین باید دو حساب مستقل باشند؛ مدیر نیز نمی‌تواند بازبینی نوشتهٔ خودش را تأیید کند.
۵. برای ایمیل واقعی، SMTP و `NOTIFICATIONS_MODE=live` را تنظیم کنید. وضعیت «در صف» به معنی تحویل پیام نیست.

مشتری از مسیر `/fa/auth/register/` ثبت‌نام می‌کند و نمی‌تواند نقش کارکنان انتخاب کند. فعال‌سازی MFA برای کارکنان پیش‌نیاز پنل است. ساخت کدهای بازیابی جدید از بخش امنیت حساب با رمز جاری و کد تازهٔ برنامهٔ احراز هویت انجام می‌شود؛ کدهای قدیمی پس از restore معتبر نمی‌مانند. [راهنمای کامل نقش‌ها و فرمان‌های محیطی](docs/STAFF-ENV.fa.md).

## بکاپ کامل، دانلود و بازیابی

بکاپ کامل روی سرور، در یک پوشهٔ خروجی خصوصیِ از قبل ساخته‌شده:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/backup.sh --output /secure-export/website.tar.age
```

بکاپ format3 شامل دیتابیس، تمام فایل‌های رسانه، سورس همان نسخه، تنظیمات خصوصی، integration، وضعیت TLS و اطلاعات لازم دفتر مستقل حریم خصوصی برای میزبان تازه است. کلید رمزگشایی مستقل در خود آرشیو قرار نمی‌گیرد. کپی جداگانه و امنِ `shared/backup-identity.txt` برای بازیابی ضروری است.

ساخت و دانلود از دستگاه شخصی در یک فرمان:

```bash
bash scripts/download-backup.sh --host ubuntu@YOUR_SERVER --remote-root /var/www/idealmakoo-v2 \
  --output ./website.tar.age --recovery-key-output ./website-recovery-key.txt
```

در نخستین دانلود، هر دو مسیر خروجی باید جدید باشند. آرشیو و کلید بازیابی را در دو محل امن مستقل نگه دارید؛ اگر کلید همین نصب را قبلاً جداگانه نگهداری کرده‌اید، دانلودهای بعدی به گزینهٔ `--recovery-key-output` نیاز ندارند.

بازیابی روی نصب موجود و بازیابی Ubuntu خالی فرمان‌های مجزا دارند؛ نصب موجود به `--confirm-replace` نیاز دارد. مسیر دقیق، ورودی کلید مستقل، تمرین `--drill`، حفظ لغو دسترسی و دفتر حذف داده در [BACKUP-RESTORE.fa.md](docs/BACKUP-RESTORE.fa.md) آمده است. برای بررسی خطای نصب یا سرویس نیز `scripts/doctor.sh` اطلاعات لازم را بدون نمایش env یا رمزها جمع می‌کند.

برای هر ۳۲ بند CRM و P01–P12، گردش واقعی، کنترل مجوز و حد پشتیبانی در [ماتریس پوشش تولید](docs/PRODUCTION-COVERAGE.fa.md) آمده است. کمپین حداکثر پنج گام محدود دارد؛ ویرایشگر Markdown و بلوک است؛ script یا webhook دلخواه از پنل اجرا نمی‌شود. موارد وابسته به تنظیم سازمان و پذیرش زیرساخت در همان ماتریس مشخص‌اند.

## معماری

| مسیر | مسئولیت |
| --- | --- |
| `src/app` | صفحه‌های Next و ورودی HTTP یکپارچه |
| `src/components`، `src/lib` | رابط، فرم‌ها، پنل، سازگارکنندهٔ API و سیاست‌های مشترک |
| `src/server` | مجوز، تراکنش، احراز هویت، CMS، CRM، فایل، PDF، AI و صف |
| `db/migrations` | migrationهای SQL با قفل و checksum |
| `scripts/worker.ts` | پردازش مستقل صف و زمان‌بندی |
| `deploy` و `scripts/*.sh` | نصب، شبکه، grant، سلامت، ارتقا، بکاپ و بازیابی |
| `tests` | آزمون‌های منطقی، PostgreSQL، API و مرورگر |
| `public` | دارایی‌های عمومی و مرجع؛ فایل خصوصی در این مسیر قرار نمی‌گیرد |

پایگاه داده نقش مالک migration و نقش محدود runtime جدا دارد. API و worker از نقش runtime استفاده می‌کنند. ردیف‌های audit و snapshotهای انتشار/پیش‌فاکتور در سطح دیتابیس در برابر بازنویسی محافظت می‌شوند. مجوز نقش عملیاتی به‌تنهایی مجوز دیدن محتوای خصوصی همهٔ کاربران نیست.

## اجرای توسعه یا اجرای Node بدون Docker

این مسیر برای توسعه‌دهنده‌ای است که Node 24 و PostgreSQL 16 را آماده کرده است. برای سرور خالی از نصاب بالا استفاده کنید.

۱. `npm ci` را اجرا کنید.
۲. با راهنمای `.env.example`، دو فایل محافظت‌شده بسازید: `.env.owner` با اتصال `idealmakoo_owner` برای آماده‌سازی، و `.env.local` با اتصال `idealmakoo_app` برای runtime. مقدارهای رمز نمونه نیستند و باید تولید شوند. `STORAGE_DIR` و `PRIVACY_LEDGER_DIR` دو مسیر مطلق مستقل‌اند؛ مسیرها، کلید نشست/MFA و URL سایت در دو فایل یکسان باشند. `DATABASE_APP_ROLE=idealmakoo_app` صریح لازم است.
۳. نقش‌های دیتابیس و extensionهای `pgcrypto` و `vector` را آماده کنید؛ راهنمای استقرار توضیح owner/app را دارد. اتصال مالک را در فایل runtime نگه ندارید.
۴. روی دیتابیس تازهٔ همین نسخه، migration، دفتر مستقل، seed و grant را به این ترتیب اجرا کنید:

```bash
chmod 600 .env.owner .env.local
node --env-file=.env.owner --import tsx scripts/db-migrate.ts
node --env-file=.env.owner --import tsx scripts/privacy-ledger.ts initialize
node --env-file=.env.owner --import tsx scripts/privacy-ledger.ts replay
node --env-file=.env.owner --import tsx scripts/privacy-ledger.ts ready
node --env-file=.env.owner --import tsx scripts/db-seed.ts
DATABASE_APP_ROLE=idealmakoo_app node --env-file=.env.owner deploy/grant-runtime.mjs
node --env-file=.env.local --import tsx scripts/privacy-ledger.ts ready
```

اجرای توسعه، در دو ترمینال:

```bash
node --env-file=.env.local --run dev
node --env-file=.env.local --import tsx scripts/worker.ts
```

اجرای build سروری، در دو ترمینال:

```bash
node --env-file=.env.local --run build
node --env-file=.env.local --run start
```

```bash
node --env-file=.env.local --import tsx scripts/worker.ts
```

`npm start` فایل standalone را اجرا می‌کند و دارایی‌های عمومی و `.next/static` را در محل لازم قرار می‌دهد. برنامهٔ Node به‌صورت پیش‌فرض پورت ۳۰۰۰ دارد. نشانی `SITE_URL` باید با مبدأ واقعی مرورگر یکی باشد؛ تفاوت localhost و 127.0.0.1 نیز برای کنترل CSRF مهم است.

## آزمون و پذیرش

برای فرمان‌های متصل به دیتابیس زیر، `.env.test` محافظت‌شده را فقط برای دیتابیس آزمایشی جدا بسازید؛ `MIGRATION_DATABASE_URL` آن نقش مالک آزمون و `DATABASE_URL` اتصال مورد نیاز harness است. مسیر رسانه و ledger آزمون نیز از محیط عملیاتی جدا باشد. برای گیت PostgreSQL و `test:integration`، `NODE_ENV=test` و `STAFF_PROVISIONING_MODE=panel` را در محیط آزمون مشخص کنید؛ این مجموعه قواعد حالت panel را هم می‌سنجد و fixtureهای اختصاصی، حالت env را جدا فعال و بررسی می‌کنند. این تنظیم آزمون را به فایل env نصب production منتقل نکنید؛ برای اجرای مرورگر روی نسخهٔ تولیدی، اتصال و تنظیمات همان محیط پذیرش مستقل را به کار ببرید.

```bash
npm run typecheck
npm run test:unit
node --env-file=.env.test --run test:integration
npm run build
npx playwright install chromium
node --env-file=.env.test --run test:e2e
npm audit --omit=dev --audit-level=high
```

تست‌های integration به PostgreSQL واقعی و نقش دارای مجوز ساخت schema نیاز دارند. از دیتابیس آزمایشی جدا و فایل محیط آزمون با اتصال مالک استفاده کنید؛ آن را به دادهٔ عملیاتی مشتری وصل نکنید. آزمون‌ها schema موقت و مجزا می‌سازند؛ نبود دیتابیس به‌عنوان خطا گزارش می‌شود و سبب موفقیت با آزمون skipشده نیست. آزمون restore privacy به `pg_dump`/`pg_restore` و کتابخانه‌های همان نصب PostgreSQL نیاز دارد؛ در نصب استخراج‌شده، `TEST_POSTGRES_BIN` و `TEST_POSTGRES_LIBRARY` را طبق harness تنظیم کنید. تست‌های قدیمی فرانت فقط در subprocess آزمون، حالت دمو را فعال می‌کنند.

برای تست روی سروری که از قبل build و اجرا شده است، `PLAYWRIGHT_NO_SERVER=true` و در صورت لزوم `PLAYWRIGHT_BASE_URL` را تنظیم کنید. فایل `playwright.config.ts` مرجع دقیق تنظیمات است. نتیجهٔ واقعی اجرای این تحویل در [VERIFICATION.fa.md](docs/VERIFICATION.fa.md) ثبت می‌شود؛ تعریف CI به معنی اجرای آن روی GitHub نیست.

آزمون‌های مرورگر را فقط به دیتابیس دورریختنی متصل کنید. برای اجرای کامل، `TEST_DATABASE_URL` باید دقیقاً به همان دیتابیس `DATABASE_URL` اشاره کند و `PLAYWRIGHT_DISPOSABLE_AUTH_BUDGET=true` صریح باشد. fixture محدود آزمون، در آغاز اجرا و سناریوهای مستقلِ پرورود، فقط دو شمارندهٔ ورود و MFA مربوط به IP محلی را بازنشانی می‌کند؛ شمارندهٔ ایمیل، ثبت‌نام، سایر محدودیت‌ها و تنظیمات برنامه تغییر نمی‌کنند. این آماده‌سازی تنها برای نشانی برنامه و دیتابیس loopback و نام `idealmakoo_test` یا نام تولیدشدهٔ دیتابیس پذیرش پذیرفته می‌شود؛ روی دیتابیس عملیاتی متوقف خواهد شد. محدودیت‌های واقعی ورود و MFA در آزمون PostgreSQL مستقل بررسی می‌شوند.

هر اجرای کامل E2E را روی دیتابیس آزمایشی تازه با migration و seed انجام دهید؛ CI نیز دیتابیس سرویس تازه می‌سازد. اجرای چند دور روی یک دیتابیس، دادهٔ سناریوها و سهمیه‌های ساعتی ثبت‌نام/درخواست را نگه می‌دارد و می‌تواند به پاسخ صحیح `429` برسد. برای رفع این وضعیت، دیتابیس آزمایشی تازه آماده کنید؛ افزایش محدودیت برنامه یا پاک‌کردن عمومی شمارنده‌ها، روش پذیرش نیست.

اگر مسیر آزمون از Caddy می‌گذرد، `PLAYWRIGHT_HTTP_ENTRYPOINT=caddy` را صریح تنظیم کنید؛ مقدار پیش‌فرض `next` برای اتصال مستقیم به سرور Next است:

```bash
PLAYWRIGHT_NO_SERVER=true PLAYWRIGHT_BASE_URL=http://127.0.0.1:3080 PLAYWRIGHT_HTTP_ENTRYPOINT=caddy node --env-file=.env.test --run test:e2e
```

طبق [RFC 3986، بخش ۲٫۴](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.4)، درصدی که بخشی از عنوان نشانی است باید روی HTTP به صورت `%25` ارسال شود. هر ۴۰ آدرس سند با encoding معتبر همچنان به `301` و مقصد دقیق و `no-store` نیاز دارند. ورودی نامعتبرِ درصد خام، جداگانه در مرز واقعی Caddy یا Next آزموده می‌شود؛ [جزئیات قرارداد encoding](docs/OPERATIONS.fa.md#۱۳-نشانی-تاریخی-و-مرز-encoding-در-caddy).

شواهد نسخهٔ جاری از سورس و lockfile همین نسخه جمع‌آوری می‌شوند. گزارش پذیرش بین PostgreSQL واقعی با transport کنترل‌شدهٔ provider، اجرای مرورگر، نصب Docker و ارتباط واقعی سرویس خارجی تفاوت می‌گذارد. تعریف pipeline یا وجود تست به‌تنهایی نتیجهٔ موفق محسوب نمی‌شود.

## سرویس‌های بیرونی

SMTP، Kavenegar، Najva، Telegram و مدل‌های AI نیازمند حساب، اعتبار و تنظیم معتبر همان سرویس هستند. حالت پیش‌فرض اعلان بیرونی غیرفعال و گفت‌وگوی AI ناشناس بسته است. حساب و مخاطب CRM namespace مستقل دارند؛ ارسال به endpoint/device تأییدشده و رضایت فعلی همان موضوع/کانال محدود است. quiet hours، تناوب، suppression و اختیار فرستنده پیش از ارسال دوباره بررسی می‌شوند. کانال‌های ایمیل، SMS، Telegram، push و inbox دارای قرارداد و گیت جدا هستند؛ ساخت worker/SDK نجوا از روی فایل رسمی عرضه‌شدهٔ اپراتور است. [راهنمای ارتباطات](docs/COMMUNICATIONS.fa.md) تنظیم دقیق و شاهد mock را از تحویل واقعی جدا می‌کند.

کلیدهای قبلیِ موجود در اسناد تاریخی از بستهٔ خروجی حذف شده‌اند. مقدار کلید را فقط در فایل runtime محافظت‌شده بگذارید؛ اگر کلیدی قبلاً در متن عمومی یا اشتراکی قرار گرفته، آن را در ارائه‌دهنده تعویض کنید.

## ساخت بستهٔ سورس خصوصی

```bash
npm run package:source
```

بسته خارج از `public` ساخته می‌شود و شامل کد، lockfile، دارایی‌های لازم، migration، تست‌ها، راهنماها و manifest دارای SHA-256 است. پوشهٔ build، node_modules، دادهٔ runtime، کلیدها، بکاپ و خروجی موقت آزمون در آن قرار نمی‌گیرند. هیچ مسیر عمومی برای دریافت سورس کامل سرور وجود ندارد.


[بررسی مستقل پس از شکست populated](docs/verification-evidence/repair-2.1.2/populated-restore-failure-final-state-20261024.json) باقی‌ماندن سه کاربر، پروفایل/صفحهٔ تغییرکرده، کارمند غیرفعال و نبود مشتری حذف‌شده را تأیید کرد؛ این نتیجه موفقیت بازگردانی آرشیو نیست.

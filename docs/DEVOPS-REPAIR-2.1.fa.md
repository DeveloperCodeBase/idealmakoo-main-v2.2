# اصلاح استقرار، پشتیبان و بازیابی نسخهٔ ۲٫۱

این سند تغییرات عملیاتی بستهٔ جاری و مرز شواهد اجرای آن را ثبت می‌کند. طراحی رابط کاربری با این تغییرات عوض نشده است. فرمان‌ها برای مقصد اعلام‌شدهٔ شما، `/var/www/idealmakoo-v2`، نوشته شده‌اند؛ آزمایشگاه مستقل Ubuntu مسیر و نشانی دیگری دارد و نتیجهٔ آن به معنی استقرار روی سرور عمومی شما نیست.

## ۲. تنظیمات کاربران مطابق درخواست تکمیلی

پیش‌فرض نصب تازه `STAFF_PROVISIONING_MODE=hybrid` است. محیط، حساب‌های اولیه را می‌سازد؛ مدیر مجاز دارای MFA می‌تواند کاربران را از پنل اداره کند. seed و provisioning عادی، تغییر رمز و اطلاعات و مجوزهای بعدی حساب موجود را برنمی‌گردانند. `env` سیاست قفل‌شدهٔ صریح برای سازمانی است که اعطای نقش و دعوت کارکنان را با فرمان مالک انجام می‌دهد. مقدار نامعتبر mode پیش از نصب رد می‌شود. مقدار انتخاب‌شدهٔ نصب قبلی بدون تصمیم اپراتور تغییر نمی‌کند.

کلید AI، SMTP و سایر سرویس‌ها همچنان فقط در محیط محافظت‌شده هستند. ثبت‌نام عمومی فقط حساب مشتری می‌سازد و اختیار انتخاب نقش سازمانی به بازدیدکننده نمی‌دهد. برای نام نقش‌ها، زبان مجاز، ایجاد اولیه، چرخش رمز و کار با پنل، [راهنمای حساب‌ها](STAFF-ENV.fa.md) را بخوانید.

## ۳. فرمان‌های اصلی

### نصب

فایل نمونه را به مسیر خصوصی منتقل کنید، مجوز `600` بدهید و دامنه، ایمیل و حساب‌های خودتان را در ویرایشگر تنظیم کنید. secretهای داخلی خالی طبق قواعد نصب نخست تولید می‌شوند؛ کلید سرویس بیرونی باید واقعی باشد.

```bash
sudo install -m 600 .env.example /root/idealmakoo.env
sudoedit /root/idealmakoo.env
sudo bash scripts/install-ubuntu.sh \
  --env-file /root/idealmakoo.env \
  --app-dir /var/www/idealmakoo-v2
```

از مسیر نصب‌شده وضعیت را بررسی کنید:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/doctor.sh
sudo bash /var/www/idealmakoo-v2/current/scripts/check-health.sh 240
```

### یک فرمان برای دریافت پشتیبان کامل روی دستگاه اپراتور

SSH باید از قبل مجاز و کلید میزبان بررسی‌شده باشد. فرمان با رمزنگاری فعال، یک snapshot هماهنگ تازه روی سرور می‌گیرد و آن را دانلود می‌کند. مسیر خروجی باید تازه باشد.

```bash
bash scripts/download-backup.sh \
  --host ubuntu@YOUR_SERVER \
  --remote-root /var/www/idealmakoo-v2 \
  --output ./idealmakoo-complete.tar.age \
  --recovery-key-output ./idealmakoo-recovery-key.txt
```

کلید مستقل را در محل خصوصی جدا از آرشیو نگه دارید. نسخهٔ جدید بکاپ و دفتر جاری حذف داده‌ها باید به محل امن خارج سرور هم منتقل شود. این بسته بدون credential و تصمیم شما مقصد ابری دلخواه ایجاد نمی‌کند. این فرمان در این سند، نمونهٔ قابل اجرا برای سرور اعلام‌شده است و به معنی اجرای آن روی آن سرور نیست.

### بررسی و بازیابی

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/restore.sh \
  --file /secure/idealmakoo-complete.tar.age --verify-only

sudo bash /var/www/idealmakoo-v2/current/scripts/restore.sh \
  --file /secure/idealmakoo-complete.tar.age --drill
```

برای جایگزینی واقعی، از پوشهٔ release منطبق با آرشیو و نام دقیق پروژه استفاده کنید:

```bash
sudo bash /var/www/idealmakoo-v2/releases/RELEASE_ID/scripts/restore.sh \
  --file /secure/idealmakoo-complete.tar.age --confirm-replace idealmakoo
```

برای میزبان Ubuntu تازه با مقصد خالی:

```bash
sudo bash scripts/recover-ubuntu.sh --new-host \
  --file /secure/idealmakoo-complete.tar.age \
  --identity /secure/idealmakoo-recovery-key.txt \
  --app-dir /var/www/idealmakoo-v2 \
  --domain idealmako.ir --email YOUR_OPERATIONS_EMAIL
```

این مسیر کدِ داخل آرشیو احرازاصالت‌شده را دوباره می‌سازد. دسترسی به مخزن بسته‌ها و imageها لازم است؛ فایل بکاپ، image آفلاینِ تمام dependencyها نیست. کانال‌های خروجی بازیابی‌شده به‌صورت پیش‌فرض متوقف می‌مانند تا تنظیم مقصد بررسی شود. اگر پس از زمان بکاپ درخواست حذف تازه‌ای اجرا شده، آخرین دفتر مستقل را با `--latest-ledger` همراه کنید. [راهنمای کامل بکاپ](BACKUP-RESTORE.fa.md) پیش‌نیازها و ادامهٔ عملیات ناموفق را توضیح می‌دهد.

بکاپ هماهنگ، app، worker و پراکسیِ همین پروژه را برای snapshot متوقف می‌کند و همان مجموعهٔ کانتینرها را دوباره آماده می‌کند. مدت وقفه به حجم DB و رسانه، سرعت دیسک و زمان آمادگی سرویس‌ها بستگی دارد؛ ادعای وقفهٔ ثابت یا صفر نمی‌شود.

راه‌اندازی بومی build جاری و سلامت اولیهٔ برنامه، دیتابیس و دفتر حریم خصوصی در رسید واقعی ثبت شدند؛ DB در این مرحله ایجاد یا بازنشانی نشد. این آمادگی، اعتبارسنجی Dockerfile یا میزبان تازه نیست. این گزارش پیش از بسته‌بندی نهایی منجمد می‌شود. SHA و نتیجهٔ اسکن مقدارهای معلومِ خودِ ZIP بسته‌شده، پس از ساخت آرشیو در مدرک نهاییِ جداگانه ثبت می‌شوند؛ وضعیت این مرحله درون بسته همچنان پیش از اسکن است.

### آزمون‌های عملیاتیِ بدون تغییر

اجرای تاریخی ۲۱ اکتبر شامل **۱۹۴ آزمون استقرار و بازیابی موفق و ShellCheck موفق برای هر ۱۴ اسکریپت** است. مقایسهٔ تازه، ۴۲ ورودی عملیاتی و ۱۸ فایل آزمون را، در مجموع ۶۰ فایل و ۶۷۱٬۱۳۶ بایت، هم با SHA ثبت‌شدهٔ همان gate و هم با بایت‌های checkpoint تأییدشده تطبیق داد: اختلاف صفر است. فهرست کامل ۲۳ فایل `deploy` و فهرست ۱۴ اسکریپت shell نیز ثابت مانده‌اند.

این تطبیق، کاربرد نتیجهٔ تاریخی را برای همین ورودی‌های تغییرنکرده تأیید می‌کند؛ آزمون عملیاتی دوباره اجرا نشده است. مجموعهٔ تاریخی parser واقعی Compose، رمزنگاری age، fixture HTTP، تنظیمات خصوصی، آرشیو، cleanup، ادامهٔ restore و انتخاب image را پوشش می‌دهد و اجرای daemon واقعی Docker در آن ادعا نشده است. جزئیات ورودی‌ها و فرمان‌های آزمون در [مدرک تطبیق منبع عملیاتی](verification-evidence/release/operational-source-applicability-reconnected.json) آمده است.

این آزمون‌های تاریخی روی Ubuntu 24.04 با Docker، PostgreSQL و ClamAV واقعی اجرا شدند. fixture از QEMU/TCG، شش vCPU و چهار GiB RAM، گزینهٔ صریح `--skip-resource-check` و بودجهٔ سلامت مخصوص آزمایش استفاده کرد. حداقل تولیدی نصاب تغییر نکرده است؛ سرعت این شبیه‌سازی معیار کارایی سرور واقعی نیست. پس از بازنشانی محیط، دیسک و مواد خصوصی موقتِ آن آزمایش در دسترس نیستند؛ رسیدهای تاریخی حفظ شده‌اند و اجرای جدید به fixture تازه نیاز دارد.

### مراحل اجرایی باز و وضعیت منابع

ماشین Ubuntu جدید فقط آماده شده و هنوز boot نشده است. build کامل با Dockerfile اصلی، نصب جاری و سلامت/AV/systemd، بکاپ و دریافت مستقل، drill و restore همان میزبان، و بازیابی کامل روی Ubuntu تازه برای نسخهٔ جاری هنوز نیازمند اجرای واقعی‌اند. build بومی و آزمون مرورگر موفق، این مراحل را تکمیل نمی‌کنند.

در مشاهدهٔ واحدِ ۲۲ اکتبر ساعت ۰۵:۰۱:۴۰ UTC، فضای آزاد میزبان **۱۷٬۱۳۸٬۵۲۰٬۰۶۴ بایت** بود و در cgroup با سقف **۸٬۵۸۹٬۹۳۴٬۵۹۲ بایت**، **۴۳۰٬۸۰۰٬۸۹۶ بایت** headroom باقی مانده بود. دو شرط شروع fixture، یعنی ۲۰ GiB دیسک آزاد و ۵٫۵ GiB headroom حافظه، در آن لحظه برقرار نبودند؛ VM راه‌اندازی نشد. این مشاهده وضعیت لحظه‌ای میزبان مشترک است و محدودیت دائمی یا نیاز حداقلی جدید محصول محسوب نمی‌شود. ادامهٔ اجرا به پنجرهٔ مناسب منابع و بررسی مستقل همان مرحله وابسته است.

### شکست‌های حفظ‌شده و مرز ادعا

مشکل probe کوتاه سلامت، خواندن نامعتبر Health پراکسی، گزینهٔ نامعتبر Compose و انتخاب image از tag یا اولین digest واقعاً مشاهده و با اصلاح محدود و آزمون متناظر رفع شدند. ابزار خارجی آزمایش نیز یک فراخوانی قدیمی Compose داشت؛ تنها همان ابزار اصلاح و مرحلهٔ ناموفق با سابقهٔ مستقل تکرار شد.

تلاش‌های تاریخیِ ناموفق، از جمله timeout با child نامشخص و خروج ۱۳۹/سیگنال ۱۱ از Node، در شمار نصب موفق نیستند. بازپخش تشخیصی موفق علت قطعی آن خطاها را ثابت نمی‌کند. در ارتقای تاریخی پذیرفته‌شده، timeout ناظر SSH از نتیجهٔ واقعیِ همان فرایند مهمان جدا شد و نصاب دوباره اجرا نشد. گواهی TLS عمومی، DNS، تحویل ایمیل واقعی، عملیات provider بیرونی و استقرار روی سرور عمومی نیز از این fixtureها استنتاج نمی‌شوند.

## ۵. قواعد عملیاتی مهم

- بکاپ کامل حاوی داده و credential است. ciphertext، identity بازیابی و دفتر مستقل را خصوصی نگه دارید؛ کلید را جدا از آرشیو ذخیره کنید. مقایسهٔ checksum به‌تنهایی احراز هویت فرستنده نیست؛ کانال دریافتِ مورد اعتماد، identity مستقل و اعتبارسنجی format3 لازم‌اند.
- تصاویر Docker داخل format3 حمل نمی‌شوند. image سفارشی دیتابیس باید در repository مورد استفاده منتشر شده، digest آن نگه‌داری شده و برای میزبان بازیابی قابل دریافت باشد. انتخاب digest درست از metadata محلی، دسترسی واقعی registry را تضمین نمی‌کند.
- روی همان میزبان، دسترسی جاری و کلیدهای جاری طبق قرارداد امنیت بازیابی حفظ می‌شوند. `--restore-keys` تصمیم صریح جداگانه است. روی میزبان تازه، وضعیت کارکنان آرشیو مبناست؛ دفتر جاری حذف داده‌ها با `--latest-ledger` اضافه می‌شود.
- اگر restore ناموفق checkpoint خصوصی ساخته است، آن را پاک نکنید و با آرشیو دیگری ادامه ندهید. همان فرمان مقید با `--resume` استفاده می‌شود؛ راهنمای امنیت بازیابی مراحل تشخیص و بازیابی owner را توضیح می‌دهد.
- برای انتقال دفتر جدیدتر، از روش snapshot هماهنگ، رمزگشایی و استخراج تأییدشدهٔ [راهنمای بکاپ](BACKUP-RESTORE.fa.md) استفاده کنید. کپی مستقیم log زندهٔ در حال نوشتن، روش توصیه‌شدهٔ انتقال نیست.

# راهنمای بهره‌برداری، بکاپ و بازیابی

این راهنما برای نصبی است که با `scripts/install-ubuntu.sh` ساخته شده است. در فرمان‌ها، `/var/www/idealmakoo-v2` را با مقدار واقعی `--app-dir` جایگزین کنید. اسکریپت‌ها فقط پروژهٔ Compose همان نصب را مدیریت می‌کنند.

برای نصب از محیط، دانلود کامل با SSH، بازیابی format3 روی میزبان خالی و قواعد دفتر جاری، ابتدا [راهنمای جاری بکاپ و بازیابی](BACKUP-RESTORE.fa.md) را بخوانید. بخش‌های گزارش تاریخی این سند، شاهد اجرای نسخه‌های قبلی‌اند و با قابلیت یا نتیجه اجرای تازه یکی فرض نمی‌شوند.

## ۱. مشاهدهٔ وضعیت و لاگ

برای اجرای عملیات مدیریتی، در شل مدیر سرور وارد نسخهٔ جاری شوید و تابع Compose را آماده کنید:

```bash
sudo -i
cd /var/www/idealmakoo-v2/current
source deploy/lib.sh
require_environment
dc ps
lifecycle check --timeout 240
dc logs --tail 100 app worker db proxy
```

تابع `dc` هر دو فایل `.env` و `.release.env` را مصرف می‌کند؛ این موضوع در نصب releaseها ضروری است. `docker compose config` بدون `--quiet` ممکن است محیط بسط‌یافته را شامل رمزها چاپ کند؛ برای بررسی اعتبار پیکربندی از `dc config --quiet` استفاده کنید.

| مشاهده | معنی و اقدام مرتبط |
| --- | --- |
| سلامت API موفق، worker ناموفق | heartbeat کارگر تازه نیست؛ لاگ worker، اتصال دیتابیس و صف را بررسی کنید |
| migration با exit غیرصفر | برنامه نباید با schema ناقص فعال شود؛ همان خطای migration و سازگاری نسخه بررسی شود |
| proxy در حال اجرا و نشانی عمومی ناموفق | دامنه، DNS، پورت، صدور TLS و مسیر واقعی دسترسی بررسی شود |
| فایل غیرتصویری در قرنطینه | worker باید نتیجهٔ واقعی ClamAV را ثبت کند؛ اسکنر غیرفعال یا ناموفق نباید فایل را پاک اعلام کند |
| پاسخ ۴۰۱ یا ۴۰۳ در پنل | نشست، MFA و مجوز سروری بررسی شوند؛ تغییر نقش در مرورگر مجوز ایجاد نمی‌کند |
| پاسخ ۵۰۳ با کد `AUTH_BUSY` هنگام ورود | ظرفیت موقت محاسبهٔ رمز پر شده است؛ پس از مکث کوتاه دوباره تلاش و در تکرار خطا، CPU و تعداد درخواست‌های هم‌زمان بررسی شوند |
| خطای فضا در بکاپ یا آپلود | ظرفیت Volume و مسیر shared/backups بررسی شود؛ چرخش لاگ جایگزین مدیریت ظرفیت رسانه نیست |

سلامت عمومی در `/api/v1/health` و زنده‌بودن پردازش در `/api/v1/health/live` ارائه می‌شود. گزارش سلامت عمومی، رمز، رشتهٔ اتصال یا جزئیات حساب‌ها را برنمی‌گرداند. جزئیات صف و رخدادها از مسیر مدیریتی و لاگ محدود قابل بررسی است.

اسکنر محلی علاوه بر امضاهای بدافزار، با `AlertExceedsMax` و `AlertEncrypted` موارد تشخیص‌داده‌شدهٔ محدودیت اسکن و سند/آرشیو رمزدار را رد می‌کند. علت `Heuristics.Limits.Exceeded.*` یا `Heuristics.Encrypted.*` را با خرابی worker یا اثبات بدافزار یکی نگیرید؛ فایل تا نتیجهٔ پاک واقعی قابل دانلود نمی‌شود. حدود و مرز این سیاست در [راهنمای آپلود و ذخیره‌سازی](UPLOAD-STORAGE.fa.md) توضیح داده شده است. سلامت `PING` به‌تنهایی شاهد اسکن فایل یا دریافت تازه‌ترین امضاها نیست؛ برای بررسی عملیاتی، نسخهٔ daemon و پایگاه امضا، نتیجهٔ یک فایل کنترل و رخداد واقعی worker بررسی شوند.

### ظرفیت ورود و ارتقای هش رمز

`AUTH_BUSY` به معنی نادرست‌بودن رمز، لغو نشست یا اثبات خرابی دیتابیس نیست. هر پردازش برنامه حداکثر دو محاسبهٔ رمز هم‌زمان و شانزده درخواست منتظر دارد؛ انتظار در صف حداکثر دو ثانیه است. این عدد، مهلت پایان کل ورود یا محاسبه‌ای که شروع شده نیست. صف پر یا انتظار منقضی‌شده پاسخ عمومی `503` می‌دهد؛ رابط کاربری پیام موقت یکسانی برای همهٔ حساب‌ها دارد و صرف این پاسخ، نشست معتبر را پاک نمی‌کند. تلاش ورود که در این مرحله رد شود، شمارندهٔ رمز ناموفق و قفل حساب را تغییر نمی‌دهد؛ محدودیت تعداد درخواست برای IP و ایمیل ممکن است پیش از آن یک تلاش را شمرده باشد. درخواست‌ها را پیاپی و خودکار تکرار نکنید.

اگر خطا تکرار می‌شود، مصرف CPU، محدودیت منابع کانتینر و هم‌زمانی درخواست‌های ورود را با لاگ محدود بررسی کنید. برای عبور از آن، رمز کاربران، MFA، عامل کار هش یا محدودیت‌های امنیتی را تغییر ندهید. این حدود در `src/server/crypto.ts` تعریف شده‌اند و کلید env برای کاهش آن‌ها وجود ندارد. بررسی سلامت سرویس و مهلت Docker با صف محاسبهٔ رمز دو کنترل جدا هستند.

رمزهای جدید با `scrypt N=32768,r=8,p=3` ذخیره می‌شوند. verifier قدیمی `p=1` پس از تأیید درست رمز در مسیر ورود و بررسی دوبارهٔ حساب به قالب جاری ارتقا می‌یابد؛ حتی اگر مرحله بعدی ورود، MFA باشد. رویداد `auth.password.rehashed` فقط نام پروفایل‌ها را ثبت می‌کند. این ارتقا رمز خام، MFA ثبت‌شده و عمر عادی نشست‌های موجود را تغییر نمی‌دهد و به بازنشانی دسته‌جمعی رمز نیاز ندارد. چون اثرانگشت امنیتی restore شامل خود verifier است، بازیابی snapshot پیش از این ارتقا می‌تواند کنترل اختلاف اعتبارنامه را فعال کند؛ روش بررسی و بازیابی صریح مالک در [RESTORE-SECURITY.fa.md](RESTORE-SECURITY.fa.md) آمده است.

### مهلت‌های بررسی سلامت و میزبان کند

مهلت‌ها را فقط پس از بررسی وضعیت و لاگ محدود سرویس تنظیم کنید. timeout فرمان سلامت با خطای داخلی برنامه یکسان نیست؛ `OOMKilled`، restart، کد خروج، وضعیت دیتابیس و مرحلهٔ راه‌اندازی باید جداگانه بررسی شوند. افزایش مهلت، خطای پیکربندی، دسترسی یا پاسخ ناموفق API را برطرف نمی‌کند.

| کلید env محافظت‌شده | پیش‌فرض، ثانیه | بازهٔ مجاز، ثانیه |
|---|---:|---:|
| `APP_HEALTH_TIMEOUT_SECONDS` | ۸ | ۸ تا ۱۲۰ |
| `APP_HEALTH_START_PERIOD_SECONDS` | ۴۵ | ۴۵ تا ۶۰۰ |
| `WORKER_HEALTH_TIMEOUT_SECONDS` | ۱۰ | ۱۰ تا ۱۲۰ |
| `WORKER_HEALTH_START_PERIOD_SECONDS` | ۶۰ | ۶۰ تا ۶۰۰ |

هر start period باید حداقل برابر timeout همان سرویس باشد. مقدار صحیح ده‌دهی بدون واحد، علامت یا صفر ابتدایی وارد کنید؛ مقدار خالی یا نبودن کلید، پیش‌فرض را نگه می‌دارد. نصاب و wrapper محافظت‌شدهٔ Compose مقدار نامعتبر را پیش از راه‌اندازی کانتینر رد می‌کنند. این چهار کلید به محیط برنامه یا کارگر وارد نمی‌شوند. Compose مقدار `APP_HEALTH_TIMEOUT_SECONDS` را به‌صورت آرگومان ثابت به فرمان probe می‌دهد؛ مهلت داخلی HTTP دو ثانیه کمتر از بودجهٔ Docker است تا شروع و خروج پردازش فرصت داشته باشند. بنابراین افزایش معتبر بودجه، هر دو لایه را هماهنگ می‌کند و سقف شش‌ثانیه‌ای قدیمی باقی نمی‌ماند. probe نیز آرگومان نامعتبر را پیش از درخواست شبکه رد می‌کند.

در یک آزمایش تاریخی Ubuntu تحت شبیه‌سازی TCG، مهلت‌های پیش‌فرض فرمان سلامت کافی نبودند؛ آماده‌سازی TypeScript و دفتر حذف داده نیز کند بود. مقدارهای `90` برای timeout و `600` برای start period هر دو سرویس، صرفاً تنظیم پیشنهادی آن آزمایش‌اند؛ پیش‌فرض پروداکشن یا شاهد موفقیت نصب محسوب نمی‌شوند. نتیجهٔ اجرای واقعی با هر override باید همراه مشخصات میزبان گزارش شود. آن‌ها را خودکار روی میزبان معمولی کپی نکنید.

پس از تغییر env با دسترسی مالک، سرویس‌ها باید طبق رویهٔ تغییر تنظیمات دوباره ایجاد شوند تا Docker مهلت جدید را بگیرد. بررسی سلامت HTTP، تازگی heartbeat کارگر، آماده‌بودن دفتر حریم خصوصی و اسکنر فعال باقی می‌مانند؛ زمان‌بندی و تعداد retryها تغییر نمی‌کند. سلامت worker همان اسکریپت موجود را مستقیماً با Node/tsx اجرا می‌کند تا فرآیند واسط npm ایجاد نشود. تا زمانی که همهٔ بررسی‌های واقعی موفق نشده‌اند، نصب یا بازیابی موفق اعلام نمی‌شود.

### راه‌اندازی مرحله‌ای و مهلت کل عملیات

تابع `lifecycle`، پیاده‌سازی بررسی‌شدهٔ `deploy/service-lifecycle.py` را با ریشهٔ release و فایل محیط همان نصب اجرا می‌کند. `up` سرویس‌های انتخاب‌شده را به ترتیب app، worker، proxy با تصویر محلی موجود و بدون build، pull یا شروع خودکار وابستگی‌ها آماده می‌کند. سلامت app پیش از شروع worker و سلامت هر دو پیش از proxy کنترل می‌شود؛ حالت `unhealthy` یا خروج سرویس، شکست است و با رسیدن به مهلت به موفقیت تبدیل نمی‌شود. در پایان، اگر proxy انتخاب شده باشد، پاسخ واقعی readiness سایت با بررسی TLS لازم است. `check` کنترل خواندنی نهایی است و ClamAVِ فعال را نیز می‌سنجد.

| فرمان helper | مهلت پیش‌فرض کل، ثانیه | کاربرد |
| --- | ---: | --- |
| `snapshot --output /absolute/private/file.json` | ۳۰ | ثبت هویت containerهای واقعاً روشن، پیش از توقف |
| `stop --snapshot /absolute/private/file.json` یا `stop app worker` | ۹۰ | توقف و مشاهدهٔ دوبارهٔ همان شناسه‌ها؛ دو شیوهٔ انتخاب با هم پذیرفته نمی‌شوند |
| `start --snapshot /absolute/private/file.json` | ۱۲۰۰ | شروع فقط شناسه‌های snapshot، بدون recreate |
| `up app worker proxy` | ۱۲۰۰ | راه‌اندازی مرحله‌ای یا recreate لازم برای محیط/image منتخب |
| `check` | ۲۴۰ | سلامت همهٔ سرویس‌های runtime، اسکنر فعال و readiness عمومی |

`--timeout` عدد صحیح ۱ تا ۳۶۰۰ ثانیه و بودجهٔ مشترک کل فرمان است، نه بودجهٔ جدا برای هر سرویس. این مهلت با چهار کلید healthcheck Docker در جدول بالا فرق دارد. هر درخواست readiness حداکثر ۱۲ ثانیه فرصت دارد و کنترل‌های موقت فقط داخل مهلت کل تکرار می‌شوند. پس از شکست یا SIGINT/SIGTERM در `up`/`start`، helper برای توقف سرویس‌هایی که همان تلاش آغاز کرده، حداکثر ۹۰ ثانیه بودجهٔ cleanup مستقل دارد؛ توقف تأییدنشده صریح گزارش می‌شود و خطای اولیه حفظ می‌شود. بنابراین زمان خروج در مسیر خطا می‌تواند از بودجهٔ آغاز فرمان بیشتر شود. برای تغییر runtime، بلوک قفل‌دار بخش ۶ را اجرا کنید؛ صرفاً `check` یا مشاهدهٔ لاگ، سرویس را راه‌اندازی نمی‌کند.

## ۲. بکاپ هماهنگ و رمزنگاری‌شده

```bash
cd /var/www/idealmakoo-v2/current
sudo bash scripts/backup.sh
```

اسکریپت قفل عملیاتی همان نصب را می‌گیرد تا با ارتقا یا بازیابی همزمان نشود. برنامه، کارگر و پراکسیِ در حال اجرا برای مدت ساخت snapshot متوقف می‌شوند؛ snapshot دیتابیس با `pg_dump`، آرشیو کل `/app/storage` و داده/پیکربندی TLS در همان بازه ساخته می‌شود. مسیرهای عمومی، خصوصی و قرنطینه در Volume رسانه قرار دارند و در همین بکاپ لحاظ می‌شوند. پیش از توقف، فهرست خصوصیِ همان container IDهای روشن ثبت می‌شود؛ بازگشت فقط همین شناسه‌ها را به ترتیب مرحله‌ای شروع می‌کند و سرویس از قبل خاموش را روشن یا کانتینر را recreate نمی‌کند. بکاپ در مسیر عادی یا cleanup فقط یک بار برای بازگرداندن این مجموعه تلاش می‌کند؛ شکستِ تلاش عادی، تلاش دوم از EXIT ایجاد نمی‌کند. بنابراین مدت عدم دسترسی به حجم snapshot و زمان واقعی آمادگی سرویس‌ها وابسته است؛ کوتاه‌بودن آن تضمین نمی‌شود.

`pg_dump` به خودی خود یک snapshot سازگار از دیتابیس می‌سازد؛ توقف نویسندگان در این بسته، هماهنگی همان snapshot با فایل‌های بیرون دیتابیس را نیز برقرار می‌کند. [مستند رسمی PostgreSQL درباره SQL dump](https://www.postgresql.org/docs/16/backup-dump.html)

آرشیو format3 شامل دیتابیس، رسانه، سورس/lockfile همان نسخه، تنظیمات محافظت‌شده، integration، داده/پیکربندی TLS، کپی مخصوص بازیابی میزبان تازه از دفتر حریم خصوصی و manifest دارای SHA-256 و MAC است. نتیجه با age برای کلید مستقل همان نصب رمزنگاری می‌شود. فایل موقتِ رمزنگاری‌نشده در پوشه‌ای با مجوز ۷۰۰ ساخته می‌شود و حذف آن در پایان یا خطا بررسی می‌شود. شکست حذف، صریح گزارش می‌شود و مانع همان یک تلاش مجاز برای بازگرداندن سرویس‌ها نمی‌شود؛ خطای غیرصفر اولیهٔ بکاپ حفظ می‌شود. اگر آمادگی مجموعهٔ قبلی تأیید نشود، snapshot خصوصی هویت در کنار پوشهٔ موقت باقی می‌ماند؛ روش بررسی و ادامهٔ صریح در [راهنمای بکاپ](BACKUP-RESTORE.fa.md) آمده است. فایل نهایی به شکل `idealmakoo-<زمان UTC>-<شناسه>.tar.age` و فایل checksum مربوط در `shared/backups` قرار می‌گیرد. کلید خصوصی age درون آرشیو نیست و باید جدا نگهداری شود.

در اسکریپت بکاپ این نسخه، شناسه، image و مسیر سورس از کانتینر واقعاً مستقر خوانده می‌شود؛ پوشهٔ caller به‌تنهایی مرجع نسخهٔ داده نیست. در ارتقا، کد بررسی‌شدهٔ تازه همین قرارداد را روی وضعیت قبلی اجرا می‌کند. اگر کانتینر، برچسب، سورس یا قرارداد ابزارهای runtime تاریخی قابل تأیید نباشد، بکاپ باید با خطا متوقف شود. اجرای مستقیم اسکریپت تاریخی، ضمانت‌های helper تازه را به آن اضافه نمی‌کند.

کلید `shared/backup-identity.txt` باید در یک محل امن جدا از سرور نگهداری شود. داشتن آرشیو بدون کلید، امکان بازیابی نمی‌دهد. داشتن بکاپ فقط روی همان دیسک نیز در خرابی کامل میزبان کافی نیست؛ انتقال بکاپ رمزنگاری‌شده به مقصد دوم باید با حساب و مقصد واقعی سازمان تنظیم شود. این بسته بدون تعیین مقصد، فایلی را به یک سرویس بیرونی ارسال نمی‌کند.

زمان‌بندی پیش‌فرض به وسیلهٔ timer با نام `idealmakoo-<project-name>-backup.timer`، حدود ساعت ۰۳:۳۰ به وقت تهران با حداکثر ۱۰ دقیقه تأخیر تصادفی انجام می‌شود. برای نام پیش‌فرض پروژه:

```bash
systemctl list-timers idealmakoo-idealmakoo-backup.timer
systemctl status idealmakoo-idealmakoo-backup.service
journalctl -u idealmakoo-idealmakoo-backup.service --since yesterday
```

با `--without-backup-timer` هنگام نصب می‌توان ساخت timer را کنار گذاشت. اسکریپت بکاپ به‌صورت خودکار بکاپ قدیمی را حذف نمی‌کند؛ نگهداشت و انتقال دوره‌ای باید با ظرفیت و سیاست سازمان مدیریت شود. فایل‌های خام موقت و نسخهٔ رمزنگاری‌شده برای مدتی همزمان روی دیسک هستند؛ برای اندازهٔ snapshotها فضای کافی لازم است.

## ۳. اعتبارسنجی و تمرین واقعی بازیابی

### بررسی رمزنگاری و ساختار، بدون تغییر داده

```bash
sudo bash scripts/restore.sh --file /var/www/idealmakoo-v2/shared/backups/BACKUP.tar.age --verify-only
```

رمزگشایی، فهرست نام‌های مجاز، نبود symlink و مسیر خروج از آرشیو، checksum تک‌تک اعضا، خوانایی dump و ساختار امن آرشیو رسانه بررسی می‌شوند. این کار، اجرای واقعی SQL بازیابی را شبیه‌سازی نمی‌کند؛ برای آن از مرحلهٔ بعد استفاده کنید.

### تمرین واقعی و ایزوله

```bash
sudo bash scripts/restore.sh --file /var/www/idealmakoo-v2/shared/backups/BACKUP.tar.age --drill
```

یک دیتابیس موقت با نام یکتای `idealmakoo_drill_*` در همان PostgreSQL ایجاد می‌شود و dump واقعاً در آن restore می‌شود. برای format3، hash محتوای تمام relationها، ساختار، sequenceها و migrationها باید با snapshot برابر باشد؛ grants دوباره اعمال و با نقش واقعی محدود بررسی می‌شوند. رسانه نیز در مسیر موقت جدا استخراج و بایت فایل‌ها کنترل می‌شود. دفتر جاری replay و readiness آزموده می‌شود. دیتابیس و فایل‌های تمرین در پایان پاک می‌شوند. دیتابیس زنده، کاربران و Volume رسانهٔ فعال جایگزین نمی‌شوند. تمرین روی همان میزبان مقداری CPU، دیسک و حافظه مصرف می‌کند؛ برای حجم بالا، اجرای آن در ساعت مناسب برنامه‌ریزی شود.

در برنامهٔ CI نیز اجرای همین مسیر روی PostgreSQL واقعی تعریف شده است؛ نتیجهٔ واقعی workflow باید جدا بررسی شود. برای پذیرش عملیاتی، تاریخ و نتیجهٔ تمرین روی بکاپ واقعی سازمان نیز ثبت شود؛ صرف موفقیت ساخت فایل age، اثبات امکان بازیابی کامل نیست.

## ۴. بازیابی جایگزین‌کننده

برای جایگزینی داده‌ها، دستور باید از پوشهٔ نسخه‌ای اجرا شود که شناسه‌اش با نسخهٔ داخل بکاپ یکسان است. این کنترل از اتصال ناخواستهٔ کد تازه به schema قدیمی جلوگیری می‌کند.

```bash
cd /var/www/idealmakoo-v2/releases/RELEASE_ID
sudo bash scripts/restore.sh --file /var/www/idealmakoo-v2/shared/backups/BACKUP.tar.age --confirm-replace idealmakoo
```

`--confirm-replace` باید دقیقاً نام پروژهٔ Compose را داشته باشد. پیش از جایگزینی، یک safety backup رمزنگاری‌شده از وضعیت فعلی ساخته می‌شود. سپس فقط برنامه و کارگر همان پروژه متوقف، دیتابیس همان پروژه بازسازی، رسانهٔ همان Volume جایگزین، grants دوباره اعمال و سرویس‌ها بررسی می‌شوند. هیچ فرمان `down -v` یا حذف عمومی Volume در مسیر عملیاتی وجود ندارد.

پیش از تغییر داده، وجود imageهای همان نسخه بررسی می‌شود؛ برنامه، کارگر و پراکسی با همان imageهای محلی دوباره ایجاد می‌شوند. در نصب مدیریت‌شده، پس از موفقیت سلامت، `current` نیز به نسخهٔ بازیابی‌شده اشاره می‌کند و مسیر قبلی در `previous` باقی می‌ماند. imageها و پوشهٔ نسخه‌های لازم را تا پایان دورهٔ نگهداشت بکاپ حذف نکنید.

اگر کلیدهای رمزنگاری فعلی یک نصب مدیریت‌شده با بکاپ متفاوت باشند، دستور متوقف می‌شود. پس از انتخاب پوشهٔ نسخهٔ متناظر، گزینهٔ صریح زیر فقط کلیدهای نشست و MFA را از بکاپ بازمی‌گرداند؛ رمزهای نقش‌های دیتابیس و تنظیمات اتصال نصب موجود حفظ می‌شوند. برای سرور خالی، از `recover-ubuntu.sh --new-host` طبق [راهنمای بازیابی کامل](BACKUP-RESTORE.fa.md) استفاده کنید:

```bash
sudo bash scripts/restore.sh --file /path/BACKUP.tar.age --confirm-replace idealmakoo --restore-keys
```

فایل `.env` کامل از بکاپ روی نصب موجود رونویسی نمی‌شود. ابتدا safety backup با کلیدهای وضعیت موجود گرفته می‌شود، سپس کلیدهای لازم برای دیتابیس بازیابی‌شده اعمال می‌شوند. اگر بازیابی پس از توقف نویسندگان خطا بدهد، آن‌ها خاموش باقی می‌مانند تا وضعیت ناقص وارد سرویس نشود؛ safety backup و پیام خطا مبنای ادامهٔ عملیات‌اند.

دسترسی جاری حساب‌ها پیش از حذف DB در checkpoint خصوصی و پایدار `shared/.pending-restore` نگه داشته می‌شود. وجود آن نصب، ارتقا، بکاپ عادی و تلاش دوبارهٔ بدون `--resume` را می‌بندد؛ وضعیت تاریخی نباید به‌عنوان دسترسی جاری دوباره capture شود. پس از رفع خطا، **از همان release و با همان آرشیو و انتخاب کلیدها** ادامه دهید:

```bash
sudo bash scripts/restore.sh --file /path/BACKUP.tar.age --confirm-replace idealmakoo --resume
```

اگر فرمان اولیه `--restore-keys` داشته است، آن را در ادامه نیز بیاورید. مرحلهٔ `prepared` اجازهٔ بازواردکردن همان snapshot با حفظ access capture و safety backup اولیه را می‌دهد. مرحلهٔ `security-applied` DB/رسانه/کلیدها را دوباره وارد نمی‌کند و وجود همان audit reconciliation را بررسی می‌کند. در خروج ۲، حفاظت‌ها ثبت شده‌اند اما superAdmin فعال باقی نمانده است؛ فقط در همین مرحله، فرمان مالک کارکنان می‌تواند هویت صریح env را بازیابی کند، سپس `--resume` سلامت و تکمیل عملیات را انجام می‌دهد. checkpoint تا پس از تمام gateها نگه داشته می‌شود. آن را دستی حذف نکنید و نویسندگان را برای دورزدن gate روشن نکنید. دستورهای دقیق در [BACKUP-RESTORE.fa.md](BACKUP-RESTORE.fa.md) و [RESTORE-SECURITY.fa.md](RESTORE-SECURITY.fa.md) آمده‌اند.

## ۵. ارتقای نسخه

بستهٔ تازه را در یک پوشهٔ جدا استخراج و از نسخهٔ جاری اجرا کنید:

```bash
cd /var/www/idealmakoo-v2/current
sudo bash scripts/update.sh --source /path/to/reviewed-new-release
```

ارتقا از کد محلیِ تعیین‌شده استفاده می‌کند و خودکار از یک شاخهٔ دلخواه Git کد دریافت یا merge نمی‌کند. ابتدا تصویر تازه ساخته می‌شود و سرویس موجود هنگام ساخت فعال می‌ماند. سپس اسکریپت بکاپِ نسخهٔ تازه و بررسی‌شده، سورس و image واقعاً فعالِ قبلی را مشاهده و از همان وضعیت بکاپ می‌گیرد؛ برای بازگرداندن سرویس‌های آن بکاپ نیز helper جاری به کار می‌رود. قرارداد ناسازگارِ نسخهٔ تاریخی پیش از migration باید با خطا متوقف شود، نه با اجرای خودکار کد قدیمی جبران. بعد از بکاپ، نویسندگان متوقف، migration اجرا و app/worker/proxy مرحله‌ای با تصویر تازه آماده می‌شوند. پس از موفقیت سلامت، `current` و `previous` عوض می‌شوند. فایل `.env` و Volumeها بازنویسی نمی‌شوند و تصویر قبلی برای rollback باقی می‌ماند.

این نسخه ۴۱ فایل migration تا 042 دارد؛ شمارهٔ 005 وجود ندارد. migration 042 دو index ترتیب فهرست حساب‌ها/کارکنان را در تراکنش معمولی می‌سازد. روی جدول بزرگ، زمان ساخت و قفل آن را در پنجرهٔ نگهداشت در نظر بگیرید. اجرای دوبارهٔ migrator نباید index یا ledger تازه‌ای برای همان فایل بسازد؛ checksum فایل اعمال‌شده را تغییر ندهید.

migration باید قبل از انتشار مرور و در CI روی دیتابیس تست اجرا شده باشد. شیوهٔ توصیه‌شده برای تغییرات زنده، افزودن سازگار، مهاجرت داده و سپس حذف در انتشار مستقل است. نصاب برای schema ناسازگار، rollback خودکار کور انجام نمی‌دهد.

### بازگشت فقط کد، با schema سازگار

```bash
sudo bash scripts/update.sh --rollback /var/www/idealmakoo-v2/previous --schema-compatible
```

این گزینه پس از بررسی سازگاری schema استفاده می‌شود و داده‌های ایجادشده پس از انتشار را برنمی‌گرداند. یک بکاپ پیش از اقدام تهیه می‌شود؛ برنامه، worker و پراکسی به تصویر مشخص قبلی بازمی‌گردند و migration معکوس اجرا نمی‌شود. برای تغییر schema ناسازگار، باید کد متناظر و بکاپ متناظر طبق بخش بازیابی انتخاب شوند؛ بازگشت به snapshot قدیمی، تغییرات ثبت‌شده پس از آن snapshot را کنار می‌گذارد.

در rollback، مسیر helper جاری پیش از انتخاب release قدیمی ثابت نگه داشته می‌شود؛ فایل Compose، metadata تصویر و ریشهٔ اجرا از release انتخابی خوانده می‌شوند، اما `lib.sh` تاریخی بارگذاری نمی‌شود. release قدیمی لازم نیست خودِ helper تازه را داشته باشد؛ وجود Compose wrapper و پیکربندی سازگار و imageهای لازم همچنان شرط است. `current` و `previous` فقط پس از موفقیت startup و check عوض می‌شوند. فرمان rollback را از اسکریپت نسخهٔ بررسی‌شدهٔ دارای این helper اجرا کنید. تغییر اشاره‌گر `current` به release قدیمی، helper تازه را در آن release ایجاد نمی‌کند؛ برای عملیات بعدی، نسخه و مسیر واقعی اسکریپت انتخابی را بررسی کنید. این مرز، سازگاری خودکار هر release یا schema قدیمی را تضمین نمی‌کند.

## ۶. تغییر امن تنظیمات و گردش رمز

پس از ویرایش `.env` و حفظ مجوز ۶۰۰، برای اعمال تنظیمات runtime از recreation استفاده کنید:

```bash
sudo -i
cd /var/www/idealmakoo-v2/current
(
  source deploy/lib.sh
  require_environment
  acquire_ops_lock
  pending_restore assert-clear
  lifecycle up --timeout 1200 app worker proxy
  lifecycle check --timeout 240
)
```

این بلوک برای محیط فعال و imageهای بررسی‌شدهٔ نصب موجود است؛ عملیات هم‌زمان را با قفل رد می‌کند و در صورت restore نیمه‌تمام، قبل از راه‌اندازی متوقف می‌شود. subshell در پایان قفل را آزاد می‌کند. `restart` محیط تازه را وارد کانتینر قبلی نمی‌کند؛ `lifecycle up` همان recreate مورد نیاز Compose را به ترتیب کنترل‌شده انجام می‌دهد. برای تغییر دامنه یا سایر متغیرهای عمومیِ زمان build، نسخهٔ تازه بسازید. برای تغییر رمز PostgreSQL موجود، ابتدا با کاربر مدیر دیتابیس از `psql` و فرمان تعاملی `\password` استفاده و سپس passwordها و URLهای متناظر را در `.env` هماهنگ کنید. تغییر متغیر `POSTGRES_*_PASSWORD` به تنهایی نقش موجود را تغییر نمی‌دهد، چون init تنها روی دیتابیس خالی اجرا می‌شود.

کلید `MFA_ENCRYPTION_KEY` با تعویض رمز ورود مدیر متفاوت است؛ تغییر بدون مهاجرت رمزنگاری داده‌ها، MFAهای قبلی را ناخوانا می‌کند. کلیدها در بکاپ هماهنگ حفظ می‌شوند. credential ارائه‌دهندگان بیرونی نیز پس از تغییر باید با ارسال/درخواست کنترل‌شدهٔ همان provider اعتبارسنجی شوند.

## ۸. قوانین خودکار CRM و یادآوری فعالیت‌ها

قانون‌ها در پنل CRM ذخیره می‌شوند. رکورد باید وضعیت `active` داشته باشد و `details.automationRule.enabled` نیز `true` باشد. ایجاد یا ویرایش قانون با مجوز همان مدیر بررسی می‌شود. در زمان اجرای worker، فعال بودن حساب سازنده، MFA، نقش و دامنهٔ کیفیت او دوباره از دیتابیس خوانده می‌شوند. حساب ایجادکنندهٔ درخواست مشتری، مجوز اجرای قانون را تعیین نمی‌کند. اگر سازنده غیرفعال شده باشد، مجوزش تغییر کند یا تعریف قانون پس از صف‌شدن تغییر کرده باشد، اجرای صف‌شده با نتیجهٔ مشخص متوقف می‌شود.

ساختار پشتیبانی‌شدهٔ قانون نمونه:

```json
{
  "schemaVersion": 1,
  "enabled": true,
  "event": "record.created",
  "collection": "leads",
  "conditions": { "status": "new", "tag": "qualified" },
  "actions": [
    { "type": "create_activity", "title": "پیگیری سرنخ تأییدشده", "owner": "business", "dueMinutes": 60 },
    { "type": "add_tag", "tag": "followup-created" }
  ],
  "maxDepth": 1
}
```

رویدادهای پشتیبانی‌شده `record.created`، `record.updated` و `activity.due` هستند. تغییر صرفاً در تاریخ به‌روزرسانی یا تاریخچهٔ یادداشت‌ها، رویداد ویرایش جدید ایجاد نمی‌کند. مجموعه‌های مجاز شامل `accounts`، `contacts`، `leads`، `opportunities`، `tickets`، `samples`، `handoffs`، `partners` و `activities` هستند. `activity.due` فقط روی `activities` قابل تعریف است. پیش‌فاکتور امضاشده، پروندهٔ استخدام و انتشار محتوای بررسی‌شده، از مسیرهای اختصاصی و مجوزهای خودشان مدیریت می‌شوند.

شرط‌ها تطابق دقیق وضعیت، نقش مسئول، یک برچسب و نوع واقعی درخواست متصل را پشتیبانی می‌کنند. نوع درخواست از جدول درخواست‌ها خوانده می‌شود؛ افزودن یک برچسب هم‌نام، نوع درخواست را تغییر نمی‌دهد. اقدامات مجاز، ایجاد فعالیت مرتبط، واگذاری مسئولیت به نقش دارای دسترسی و افزودن برچسب هستند. تغییر برچسب محفوظ `quality` مجاز نیست. هر قانون حداکثر ۱۰ اقدام دارد. اجرای JavaScript دلخواه، HTTP webhook دلخواه، شاخه‌های پیچیده، cron دلخواه و ارسال بیرونی مستقیم در این موتور تعریف نشده است.

پیش‌نمایش، شرط‌ها را روی رکوردهای فعلیِ مجاز بررسی می‌کند؛ هیچ اقدامی انجام نمی‌دهد و ادعا نمی‌کند رویدادی در گذشته رخ داده است. سقف جست‌وجوی پیش‌نمایش ۵۰۰۰ رکورد و سقف نمایش ۲۰۰ تطابق است و نتیجهٔ بریده‌شده علامت دارد. اجرای دستی باید شناسهٔ رکوردهای انتخاب‌شده و یک `idempotencyKey` یکتا داشته باشد؛ حداکثر ۱۰۰ رکورد در هر درخواست پذیرفته می‌شود. تکرار همان کلید و همان ورودی، همان شناسهٔ رویدادها را برمی‌گرداند؛ استفادهٔ دوباره از کلید با ورودی متفاوت، خطای تعارض دارد.

رویداد، اجرای هر قانون و زنجیرهٔ منشأ فعالیت، در جدول‌های مستقل نگهداری می‌شوند. ترکیب قانون و رویداد یکتا است. هر اجرا یک تراکنش SQL کوتاه دارد و تغییر رکورد، تاریخچهٔ تغییر، audit و رویداد فرزند با هم commit می‌شوند. خطای یک اقدام، تغییرات اقدامات قبلی همان اجرا را برمی‌گرداند. نتیجهٔ اجرا یکی از `pending`، `succeeded`، `skipped` و `failed` است. پس از رفع یک خطای قطعی، برای تلاش دستی جدید باید کلید اجرای جدید انتخاب شود. سقف عمق پیش‌فرض ۱ و سقف سخت ۳ است؛ عمق از دیتابیس معتبر خوانده می‌شود و چرخهٔ «ایجاد فعالیت ← رسیدن موعد فعالیت» نیز این سقف را حفظ می‌کند.

موعد فعالیت از `record.due` خوانده می‌شود. زمان کامل، ISO 8601 با `Z` است؛ تاریخ بدون ساعت، شروع همان روز در UTC محسوب می‌شود. `dueMinutes` در اقدام ایجاد فعالیت، فاصلهٔ دقیقه‌ای از زمان اجرای قانون است؛ حذف آن یعنی فعالیت موعد خودکار ندارد. فعالیت‌های بایگانی، انجام‌شده، بسته، لغوشده و حل‌شده یادآوری جدید نمی‌گیرند.

برای هر ترکیب فعالیت، موعد و نقش مسئول، یک یادآوری پایدار ایجاد می‌شود. اعلان از صف سیاست اعلان می‌گذرد و تنها برای کاربران دارای MFA و دسترسی فعلی به رکورد، با رعایت موضوع، کانال، تناوب و ساعت سکوت تحویل می‌شود؛ دامنهٔ کیفیت و دسترسی فرد/تیم/قلمرو نیز دوباره بررسی می‌شوند. اگر گیرندهٔ واجد شرایط نباشد، رکورد در حالت انتظار می‌ماند و پس از پنج دقیقه دوباره بررسی می‌شود. تغییر مسئول یا موعد، ترکیب جدیدی می‌سازد. این یادآوری‌ها به‌صورت خودکار ایمیل، پیامک یا پیام شبکهٔ اجتماعی ارسال نمی‌کنند؛ هیچ credential بیرونی برای اجرای موتور CRM لازم نیست.

یادآور taskهای تکرارشوندهٔ CRM از occurrence و نسل جاری آن استفاده می‌کند. وضعیت‌های `pending`، `queued`، `delivered`، `cancelled`، `failed` و `uncertain` معناهای جدا دارند. defer برای ساعت سکوت یا قرارگرفتن در digest همچنان `queued` است؛ `remindedAt` تنها بعد از پذیرش واقعی تحویل ثبت می‌شود. بسته‌شدن task، تغییر مسئول/نسل، خروج از scope یا تغییر رضایت، پیش از درج اعلان دوباره بررسی می‌شود. اصلاح 036 این بازبینی را با قفل تحویل هماهنگ می‌کند تا یادآور کار بسته‌شده در رقابت همزمان، تحویل‌شده نامیده نشود. در نسخه‌های پیش از 036 که اعلان مستقیم in-app واقعاً ثبت شده بود، سابقهٔ تحویل موجود به صف تازه تبدیل یا دوباره ارسال نمی‌شود.

## ۹. سازگاری بکاپ تاریخی format2 و جلوگیری از بازگشت دادهٔ حذف‌شده

بکاپ تاریخی format2 شش عضو دارد: `database.dump`، `storage.tar`، `environment.env`، `release.env`، `privacy-anchor.json` و `manifest.json`. manifest نسخهٔ ۲، SHA-256 تمام payloadها، تعداد migrationها و تعداد relationهای عمومی را ثبت می‌کند. relation شامل جدول و view است؛ گزارش جدول باید view را جدا بشمارد. dump فقط schema عمومی پروژه را شامل می‌شود. کلید و تاریخچهٔ دفتر مستقل حذف در format2 قرار نمی‌گیرند. restore موجود سازگاری این قالب را حفظ می‌کند؛ بازیابی کامل میزبان تازه به format3 نیاز دارد و محدودیت شمارش قالب قدیمی به عنوان کنترل کامل hash داده معرفی نمی‌شود.

پیش‌فرض همهٔ حالت‌های `restore.sh` فقط format3 احرازشده است. برای format2 تاریخی باید پس از بررسی مستقل منشأ فایل، `--allow-legacy-format2` را کنار `--verify-only`، `--drill` یا `--confirm-replace` قرار دهید. رمزنگاری برای گیرندهٔ age و checksumهای داخل فایل، هویت فرستندهٔ قالب تاریخی را اثبات نمی‌کنند؛ کسی که کلید عمومی گیرنده را دارد نیز می‌تواند یک فایل رمزنگاری‌شده بسازد. این انتخاب صریح، کنترل checksum/anchor/مجوز و schema را حذف نمی‌کند و به بازیابی کامل میزبان تازه تعمیم ندارد.

`--verify-only` علاوه بر ساختار و checksum، هویت و سر زنجیرهٔ anchor را در دفتر مستقل **فعلی** بررسی می‌کند و restore انجام نمی‌دهد. `--drill` دیتابیس یکتای موقت می‌سازد، همهٔ داده‌ها و constraint/triggerها را restore می‌کند، شمار schema را تطبیق می‌دهد، دفتر فعلی حذف را روی دیتابیس موقت replay می‌کند و readiness می‌سنجد. رسانه نیز در پوشهٔ تازهٔ خصوصی استخراج می‌شود. گزارش عملیاتی موفق فقط پس از این گیت‌ها با نقش مالک ثبت می‌شود؛ برنامه اجازهٔ ساختن یا ویرایش مدرک recovery را ندارد.

در بازیابی جایگزین‌کننده، پس از restore دیتابیس و Volume همان پروژه، grants و replay اجباری اجرا می‌شوند؛ سپس برنامه و worker اجازهٔ شروع دارند. خطای هر مرحله، نویسندگان را متوقف نگه می‌دارد. format1 بدون anchor در این مسیر پذیرفته نیست و باید جداگانه و با بررسی اپراتور مهاجرت داده شود. فقط ساختار public که به دلیل نصب extensionها از قبل وجود دارد از فهرست CREATE کنار گذاشته می‌شود؛ table، row، function، index، trigger و constraint حذف انتخابی نمی‌شوند.

مسیر مستقل `PRIVACY_LEDGER_HOST_DIR` را با هویت و تمام تاریخچهٔ جاری در یک فرایند رمزگذاری‌شدهٔ جدا و خارج از میزبان نگهداری کنید. آن را هرگز از snapshot قدیمی همراه با دیتابیس بازنگردانید. کامل‌بودن و تازگی نسخهٔ مستقل شرط این ضمانت عملیاتی است؛ نگهداری هم‌زمان دیتابیس قدیمی و دفتر قدیمی روی یک دیسک، جایگزین این فرایند نیست. از دست‌رفتن یا ناسازگاری زنجیره باید با خطای روشن متوقف شود؛ ساخت هویت تازه برای عبور از خطا مجاز نیست.

## ۱۰. وضعیت پایش و پردازش رسانه

پایش تنها مقادیر واقعاً مشاهده‌شده، بازهٔ زمانی و تعداد نمونه‌ها را نشان می‌دهد. heartbeat با موفقیت provider یکسان نیست. نبود داده برای TLS، provider، بازیابی یا شاخص عملکرد با وضعیت unknown/بدون شاهد نمایش داده می‌شود. اندازه‌گیری anonymous فقط با رضایت analytics و مسیرهای عمومی مجاز انجام می‌شود؛ URL حاوی token، query، شناسهٔ حساب و مسیرهای خصوصی وارد اندازه‌گیری نمی‌شوند. رخدادهای incident و تغییر وضعیت آن‌ها با MFA مدیریتی، نسخهٔ مورد انتظار و تاریخچهٔ تغییر کنترل می‌شوند.

FFmpeg/ffprobe فقط فایل محلی مجاز را پردازش می‌کنند. منبع اصلی حفظ می‌شود، فایل قرنطینه یا دارای حق منقضی‌شده ورودی معتبر نیست و تغییر وضعیت job به ready نیازمند خروجی واقعی و ثبت سهمیه است. اجرای ناموفق یا نامطمئن نباید ready گزارش شود. subtitle تنها WebVTT محدود و پاک‌سازی‌شده است؛ پیوند منبع، محدودهٔ دسترسی و حقوق جاری در دانلود دوباره بررسی می‌شوند.

کتابخانهٔ رسانهٔ production فهرست واقعی سرور و وضعیت scan را نشان می‌دهد؛ آپلود پیش‌فرض خصوصی است. سقف اولیهٔ هر فایل ۲۰ MiB است؛ مدیر می‌تواند سقف عمومی و سقف هر نوع را تا حد نهایی ۸۰ MiB طبق [سیاست ذخیره‌سازی](UPLOAD-STORAGE.fa.md) تنظیم کند. محدودیت مؤثر سرور، سقف نوع فایل و سهمیهٔ باقی‌مانده ملاک‌اند. PNG/JPEG/WebP، PDF، DOCX، MP4، MP3 و WAV پذیرفته می‌شوند. تصویر به WebP نرمال می‌شود؛ عنوان فایل، MIME و حجم نهایی از پاسخ سرور گرفته می‌شوند. نسخهٔ اصلی تصویر خصوصی و retained است و URL قابل‌ویرایش پنل نیست. برش از نسخهٔ مجاز منبع ساخته می‌شود و اصل را بازنویسی نمی‌کند. انقضا یا ابطال حقوق منبع، دسترسی بعدی مشتق را نیز محدود می‌کند؛ usage عمومی یا خصوصی فقط در محدودهٔ فعلی کارمند نمایش داده می‌شود.

برای پردازش محلی، MP4 پاک و مجاز را انتخاب کنید؛ پروفایل‌های محدود `web_480p` و `web_720p` و WebVTT در پنل ارائه می‌شوند. منبع حداکثر ۱۰ دقیقه و 3840×2160 با ۶۰ فریم است؛ خروجی ویدیو حداکثر ۶۴ MiB، subtitle حداکثر ۲۵۶ KiB و ۱۰۰۰ cue است. سقف timeout بین ۳۰ و ۳۰۰ ثانیه و پیش‌فرض ۱۲۰ ثانیه است. پنل capability و محدودیت واقعی سرور را می‌خواند؛ نام profile، فرمان FFmpeg یا URL دلخواه پذیرفته نمی‌شود. وضعیت `scanning` پایان کار نیست. فایل خروجی تنها در `ready`، scan پاک و حقوق جاری قابل دانلود/ثبت در کتابخانه است؛ checksum بایت واقعی هنگام دانلود بررسی می‌شود. retry پس از شکست قطعی و با دلیل صریح محدود است؛ صف پردازش در این آزمون‌ها به provider بیرونی متصل نشده است.

## ۱۱. تفکیک شواهد تاریخی از سورس بازسازی‌شده

پیش از حذف مسیر توسعه، آخرین تمرین native روی PostgreSQL 16.15، ۳۳ migration، **۱۷۰ جدول و ۱ view**، و پنج فایل کنترل‌شده انجام شده بود: دو فایل عمومی/خصوصی و سه تصویر شامل اصل خصوصی، تصویر نرمال و برش مشتق. تطابق بایت‌ها، lineage، منع انتشار اصل خصوصی و replay دفتر با sequence صفر بررسی شده بود. آن نتیجهٔ تاریخی، آزمون سورس بازسازی‌شدهٔ فعلی محسوب نمی‌شود.

در بازسازی، SQLهای ۰۰۱–۰۲۴ دقیقاً از checkpoint برگشتند؛ ۰۲۵–۰۳۴ با checksum جدید و برچسب بازسازی ایجاد شدند. روی دیتابیس تازه، ۱۰۷۰ شیء SQL نرمال‌شده با schema ذخیره‌شدهٔ ۰۳۴ مطابقت داده شدند؛ backfillهای تاریخی گم‌شده به عنوان سورس اصل ادعا نمی‌شوند. مسیر ارتقای داده‌دار 026 و 034 بعداً با fixture واقعی جدا بررسی و اصلاح شد. 035 گواهی شرکت و 036 وضعیت/سیاست یادآور را اضافه می‌کنند؛ 037 قالب‌های تراکنشی و 038 تاریخچهٔ گردش ویرایشگر را اضافه می‌کنند. ledger قدیمی تغییر نکرده است؛ پس از freeze این فایل‌ها، دیتابیس نهاییِ مستقل از پذیرش مرورگر با ۳۷ migration ساخته شد. نتیجهٔ اجرای web/worker، مرورگر و recovery فعلی باید از گزارش تازهٔ همین سورس خوانده شود.

گیت تاریخی آن checkpoint شامل ۱۶ آزمون موفق archive/env/grants، ShellCheck و اعتبارسنجی واقعی پیکربندی Compose/Caddy بود. در زمان ثبت آن شاهد، daemon داکر، VM تازهٔ Ubuntu، TLS دامنه و پذیرش واقعی provider اجرا نشده بودند. این پاراگراف گزارش آزمون نسخهٔ جاری 2.1 نیست. workflowهای CI گیت‌های جدا دارند؛ وضعیت موفق CI فقط پس از اجرای واقعی همان workflow قابل گزارش است.

## ۱۲. شاهد تاریخی native و format2 تا schema 038

تمرین تاریخی native با PostgreSQL 16.15 و فایل‌های همان checkpoint تا 038، روی DB پاکِ جدا از پذیرش مرورگر و با 026 اصلاح‌شده، با exit صفر پایان یافت. dump، age، رمزگشایی، اعتبارسنجی format2 و SQL restore واقعی در clone اجرا شدند. ۳۷ نام/checksum migration با فایل‌های همان نسخه برابر بودند؛ ۱۸۳ جدول و یک view بازگشتند. ۱۱۸۶ بلوک DDL واقعی pg_dump و fingerprint داده/نسخهٔ تمام relationها پیش از replay با snapshot برابر بود. این fingerprintها فرادادهٔ قابل مقایسه‌اند و محتوای ردیف خصوصی را در گزارش عمومی منتشر نمی‌کنند. این نتیجه، شاهد بکاپ کامل format3، migrationهای بعدی یا نصب Ubuntu نسخهٔ 2.1 محسوب نمی‌شود.

grants در clone دوباره اعمال و مجوز تمام ۱۸۴ relation و ۱۰ sequence با نقش واقعی برنامه بررسی شد. هشت فرمان منفی ساخت schema، خواندن migration، تغییر/حذف/truncate audit و ساخت/تغییر/حذف مدرک recovery واقعاً با خطای مجوز 42501 رد شدند. یک گزارش موفق از مسیر محدود owner-only در پایش ثبت شد؛ حساب runtime اجازهٔ جعل این مدرک را ندارد.

storage منبعِ این پذیرش فایل کاربری نداشت. فقط در clone، دو فایل متنی عمومی/خصوصی و سه تصویر کنترل‌شده شامل اصل خصوصی، WebP نرمال و crop ساخته شدند. checksum، تعداد بایت، metadata، recipe و زنجیرهٔ source/derivative برابر شدند؛ اصل خصوصی public نبود و provenance در برابر UPDATE مقاوم ماند. هیچ fixture به DB یا storage منبع اضافه نشد. cloneها و فایل‌های خام موقت پس از موفقیت حذف شدند؛ آرشیو رمزنگاری‌شده و گزارش خصوصی برای شاهد باقی ماندند.

anchor بکاپ به دفتر مستقل **فعلی** متصل و replay اجباری و readiness موفق شدند. sequence این دفتر در پذیرش صفر بود؛ این تمرین وجود حذف واقعی سازمان در آن دفتر را ادعا نمی‌کند. آزمون‌های مجزای privacy، حذف/restore قدیمی/بازاعمال tombstone را با دادهٔ ایزوله می‌سنجند. برای نصب عملیاتی، همین گیت باید با بکاپ و دفتر مستقل جاری سازمان تکرار شود. این تمرین native، اجرای مسیر کانتینری یا Ubuntu VM نیست.

شاهد تاریخی قابل‌حمل و فاقد credential در [native-recovery.json](verification-evidence/native-recovery.json) و [manifest اشیا و نسخه‌ها](verification-evidence/native-recovery-object-manifest.json) آمده است. گزارش 036 قبلی نیز به عنوان checkpoint تاریخی نگه داشته شده است؛ اعداد این بخش از تمرین پیشینِ ۲۰۲۶-۱۰-۲۰ خوانده شده‌اند؛ روش شمارش بلوک DDL این تمرین با manifest ساختاری تاریخی ۲٬۰۷۳‌تایی یکی فرض نمی‌شود. برای ادارهٔ محتوای تماس، فوتر، نوار اعلان و جست‌وجوی اسناد، [راهنمای سطح عمومی](PUBLIC-SURFACE.fa.md) را بخوانید.

## ۱۳. نشانی تاریخی و مرز encoding در Caddy

۴۰ نشانی مرجع سند در دادهٔ پروژه حفظ می‌شوند. هنگام ارسال درخواست HTTP، علامت درصدی که خودِ عنوان است باید به `%25` تبدیل شود؛ تنها escapeهای معتبر با دو رقم hexadecimal دست‌نخورده می‌مانند. این الزام از [RFC 3986، بخش ۲٫۴](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.4) می‌آید. دوباره‌کدگذاری یا دوباره decode کردن یک عنوان، جایگزین تطبیق دقیق شناسه و عنوان منبع نیست.

مسیر درخواست در Go با `url.ParseRequestURI` خوانده می‌شود و escape نامعتبر پیش از اجرای handler خطا می‌دهد؛ برای این خطا پاسخ HTTP 400 ساخته می‌شود. منابع اصلی: [خواندن request در net/http](https://go.dev/src/net/http/request.go)، [اعتبارسنجی escape در net/url](https://go.dev/src/net/url/url.go) و [مدیریت خطای request در server](https://go.dev/src/net/http/server.go). [RFC 9112، بخش ۳٫۲](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2) برای request-line نامعتبر پاسخ 400 یا redirect به نشانی درست را پیش‌بینی می‌کند؛ تفسیر پنهانی ورودی نامعتبر می‌تواند با مرزهای کنترل درخواست ناسازگار شود.

قرارداد زیر برای عنوان تاریخی دارای `37%` در آزمون مستقل ثبت شده است؛ هر خانه دقیقاً یک status را الزام می‌کند:

| درخواست | از Caddy | مستقیم از Next |
| --- | --- | --- |
| درصد خام `37%-` | 400، بدون Location | 301 به مقصد دقیق منبع |
| encoding معتبر `37%25-` | 301 به مقصد دقیق منبع | 301 به مقصد دقیق منبع |
| escape نامعتبر `%GG` | 400، بدون Location | 404، بدون Location |
| double encoding به صورت `%2525` | 404، بدون Location | 404، بدون Location |

گیت ۴۰ آدرس معتبر در هر دو مسیر `301`، مقصد دقیق `/fa/.../` و `Cache-Control: no-store` را بررسی می‌کند. تست مرزی درصد خام مستقل است و پاسخ 400 قبل از handler را با نبود CSP برنامه تشخیص می‌دهد. پاسخ redirect یا 404 برنامه نیز `no-store` دارد و این درخواست‌ها نباید cookie بسازند. این آزمون برای عبور از خطای ورودی، پیکربندی Caddy یا منطق امنیتی برنامه را تغییر نمی‌دهد.

برای مرورگری که به reverse proxy محلی متصل است، `PLAYWRIGHT_HTTP_ENTRYPOINT=caddy` همراه `PLAYWRIGHT_NO_SERVER=true` و `PLAYWRIGHT_BASE_URL=http://127.0.0.1:3080` تنظیم می‌شود. پیش‌فرض `next` مخصوص سرور مستقیم و خودکار Playwright است. مقدار ناشناختهٔ entrypoint خطا دارد؛ نبود تطبیق، با skip یا پذیرش چند status پنهان نمی‌شود. نتیجهٔ اجرای تازه از گزارش همان گیت خوانده می‌شود؛ ترافیک HTTP روی loopback شاهد TLS مقصد یا HTTP/2 عملیاتی نیست.

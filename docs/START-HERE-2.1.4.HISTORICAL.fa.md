# از اینجا شروع کنید — نسخه ۲٫۱٫۴ ایده‌آل ماکو

این راهنما ترتیب راه‌اندازی و استفاده را مشخص می‌کند. وضعیت آزمون‌های انجام‌شده و محدودیت‌های واقعی تحویل در [گزارش پذیرش](VERIFICATION.fa.md) است. رمزها، کلیدهای واقعی و داده‌های مشتری همراه بستهٔ سورس نیستند.

## ۱. آماده‌سازی سرور و تنظیمات

برای نصب اصلی از Ubuntu 22.04 یا 24.04 با systemd استفاده کنید. نصاب Docker و Compose را آماده می‌کند. با آنتی‌ویروس محلی، حداقل ۶ GiB حافظه و ۱۵ GiB فضای آزاد اولیه در نظر گرفته شده است؛ برای ساخت و بهره‌برداری ۸ GiB حافظه مناسب‌تر است. اندازهٔ داده و بکاپ نیاز دیسک را افزایش می‌دهد. نصب و بازیابی میزبان تازه به مخازن اینترنتی نیاز دارند.

فایل ZIP نهایی و فایل `.sha256` کنار آن را در یک پوشه قرار دهید. از همان پوشه، ابتدا checksum را بررسی و سپس بسته را استخراج کنید:

```bash
sha256sum -c idealmakoo-production-2.1.4.zip.sha256
unzip idealmakoo-production-2.1.4.zip
cd idealmakoo-production-2.1.4
```

خروجی بررسی باید `OK` باشد؛ در صورت اختلاف، نصب را از آن فایل ادامه ندهید. اگر `unzip` روی سرور موجود نیست، آن را با `sudo apt-get install unzip` نصب کنید. فرمان‌های زیر از داخل پوشهٔ سورس اجرا می‌شوند:

```bash
sudo install -m 600 .env.example /root/idealmakoo.env
sudoedit /root/idealmakoo.env
```

پیش از نصب، این مقادیر را تعیین کنید:

| تنظیم | کاربرد |
| --- | --- |
| `SITE_URL` و `NEXT_PUBLIC_SITE_URL` | نشانی نهایی یکسان، برای نمونه `https://idealmako.ir` |
| `SITE_ADDRESS` | دامنه، بدون مسیر، برای نمونه `idealmako.ir` |
| `ACME_EMAIL` | ایمیل عملیاتی واقعی برای گواهی TLS |
| `BOOTSTRAP_ADMIN_EMAIL` و `BOOTSTRAP_ADMIN_NAME` | مشخصات مالک اولیه |
| `STAFF_PROVISIONING_MODE=hybrid` | ایجاد اولیه از env و مدیریت بعدی از پنل |
| `STAFF_ACCOUNTS_JSON` | حساب‌های اولیهٔ تیم، نقش و زبان‌های مجاز؛ قالب کامل در راهنمای کارکنان |
| کلیدهای SMTP، AI و سایر اتصال‌ها | فقط برای سرویس‌هایی که واقعاً استفاده می‌کنید |

در نصب اول، رمزهای داخلی خالی، کلید نشست، کلید MFA و رمز اولیهٔ مالک توسط نصاب تولید می‌شوند. متن نمونه را به‌عنوان رمز واقعی استفاده نکنید. کلید یک سرویس خارجی به‌صورت خودکار ساخته نمی‌شود. فایل env را با `source` اجرا نکنید؛ نصاب آن را به‌عنوان داده می‌خواند.

DNS دامنه باید به سرور برسد و پورت‌های ۸۰ و ۴۴۳ در دسترس باشند. مسیر پیشنهادی این تحویل `/var/www/idealmakoo-v2` است و باید مختص همین سایت باشد.

## ۲. نصب با یک فرمان

از پوشهٔ استخراج‌شده:

```bash
sudo bash scripts/install-ubuntu.sh \
  --env-file /root/idealmakoo.env \
  --app-dir /var/www/idealmakoo-v2
```

نصاب سرویس‌ها، دیتابیس، migration، محتوای اولیه، کاربران تعریف‌شده، بررسی سلامت و بکاپ زمان‌بندی‌شده را آماده می‌کند. کد خروج غیرصفر به معنی نصب موفق نیست؛ پیام مرحلهٔ ناموفق را بررسی کنید. تکرار seed عادی محتوای ویرایش‌شده یا رمز جدید کاربران را به مقدار اولیه برنمی‌گرداند.

پس از نصب:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/check-health.sh 240
sudo bash /var/www/idealmakoo-v2/current/scripts/doctor.sh
```

راهنمای [استقرار](DEPLOYMENT.fa.md) حالت HTTP آزمایشی، تنظیمات شبکه، مراحل دستی، ارتقا و خطاهای رایج را توضیح می‌دهد. تنظیمات Next که با `NEXT_PUBLIC_` شروع می‌شوند هنگام ساخت وارد خروجی می‌شوند؛ تغییر دامنهٔ عمومی به ساخت مجدد نسخه نیاز دارد.

## ارتقای نصب موجود

اگر سایت قبلاً نصب شده است، فایل `shared/.env` همان سایت را نگه دارید و `.env.example` را روی آن کپی نکنید. نسخهٔ تازه را در پوشه‌ای جدا استخراج و از release فعلی فرمان زیر را اجرا کنید:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/update.sh \
  --source /ABSOLUTE/PATH/idealmakoo-production-2.1.4
```

این عملیات بکاپ حفاظتی، ساخت release جدید، migration و بررسی آمادگی دارد. مسیر `--source` باید مسیر مطلق بستهٔ جدید باشد. پیش از ارتقای نسخهٔ ۲.۰.۰، checksumهای migration نصب‌شده را طبق راهنمای استقرار بررسی کنید؛ ledger را برای عبور از خطا تغییر ندهید.

آرشیو مرجع ارسالی `idealmakoo-production-2.0.0.zip` با SHA-256 برابر `b9a80316a6526435bf06a29084cbc93e33a5ad6c5ad7b57ac8db5aa1a744c716` بررسی شد: checksum بیرونی و هر ۷۷۲ ورودیِ فهرست داخلی درست بودند و هر ۳۷ migration آن با نسخهٔ ۲.۱.۴ بایت‌به‌بایت یکسان است؛ فقط migrationهای ۰۳۹ تا ۰۴۲ افزوده شده‌اند. هشدار تاریخی بازسازی در خود همان آرشیو نیز وجود دارد و به معنی تغییر این ۳۷ فایل در تحویل تازه نیست. این مقایسه، اجرای ارتقا روی دیتابیس نصب‌شدهٔ شما را اثبات نمی‌کند. اگر checksum واقعی `schema_migrations` نصب با فایل‌های متناظر متفاوت است، ارتقا را برای بررسی متوقف کنید؛ فایل‌ها یا ledger را برای عبور از خطا تغییر ندهید. [رسید مقایسهٔ آرشیو](verification-evidence/repair-2.1.4/legacy-2.0.0-reference.safe.json) و توضیح کامل در [راهنمای استقرار](DEPLOYMENT.fa.md) آمده است.

## ۳. ورود و مدیریت کاربران

در `/fa/auth/login/` با مالک اولیه وارد شوید. رمز تولیدشده در فایل خصوصی `shared/.env` نصب قرار دارد. MFA را در امنیت حساب فعال و کدهای بازیابی را جداگانه نگه دارید. پس از این مرحله، مدیریت کاربران از پنل ادمین در دسترس است.

در حالت پیش‌فرض `hybrid`، از بخش کاربران و دکمهٔ افزودن کاربر می‌توانید نام، ایمیل، رمز اولیه و نقش را تعیین کنید. مالک سامانه به همهٔ نقش‌های تعریف‌شده دسترسی دارد و می‌تواند زبان‌های مجاز و مجوزهای مرتبط را تنظیم کند؛ مدیر معمولی اجازهٔ ساخت حساب مشتری دارد. ساخت حساب با رمز اولیه به تنظیم SMTP وابسته نیست. کارمند تازه پیش از ورود به پنل باید MFA را فعال کند.

مدیر مجاز می‌تواند اطلاعات کاربر را اصلاح کند، ایمیل ورود و وضعیت حساب را تغییر دهد و رمز جدید تعیین کند. نقش، زبان‌ها و مجوزهای حساس فقط در محدودهٔ اختیار همان مدیر تغییر می‌کنند. ویرایش هم‌زمان با کنترل نسخه محافظت می‌شود. تغییر ایمیل یا رمز، نشست‌های قبلیِ حساب هدف را باطل می‌کند؛ تغییر ایمیل تأیید قبلی آن را نیز از اعتبار می‌اندازد. تغییر رمز، MFA فعال را خاموش نمی‌کند. مراحل کامل در [راهنمای مدیریت کاربران پنل](USER-MANAGEMENT.fa.md) است.

در حالت‌های `hybrid` و `panel`، مدیر ارشدِ دارای MFA می‌تواند برای کارمند فعال دیگری که authenticator خود را از دست داده، از مسیر محدود بازیابی دسترسی دومرحله‌ای استفاده کند. این اقدام رمز و TOTP تازهٔ خودِ مدیر و رمز جدید هدف را لازم دارد؛ نشست‌ها و عوامل قدیمی هدف را باطل و ورود بعدی را به ثبت دوبارهٔ MFA محدود می‌کند. بازیابی خودِ مالک و حالت `env` حدود جدا دارند. پیش از اقدام، مراحل و شرایط [بازیابی MFA در راهنمای کاربران](USER-MANAGEMENT.fa.md) را بخوانید.

مشتری از `/fa/auth/register/` ثبت‌نام می‌کند و نمی‌تواند برای خودش نقش مدیریتی انتخاب کند. فهرست کاربران در پنل جست‌وجو و صفحه‌بندی سمت سرور دارد؛ محدود به اولین هزار ثبت‌نام نیست.

`STAFF_PROVISIONING_MODE=env` یک انتخاب صریح برای مدیریت حساب‌های کارکنان از طریق فرمان مالک است: ساخت و دعوت کارمند، تغییر ایمیل، تعیین رمز مدیریتی، فعال‌سازی مجدد و تغییر نقش/مجوز از پنل محدود می‌شوند؛ ویرایش مجاز نام و پروفایل و غیرفعال‌کردن حساب همچنان ممکن است. آن را فقط وقتی انتخاب کنید که همین محدودیت‌ها را می‌خواهید. در حالت `hybrid` اجرای مجدد provisioning، تغییرات معمول پنل را بازنویسی نمی‌کند؛ گزینه‌های اعمال مجدد نقش یا رمز، عملیات صریح مالک هستند. قالب حساب‌ها، نقش‌ها و فرمان‌های دقیق در [راهنمای کاربران و env](STAFF-ENV.fa.md) آمده است.

## ۴. ویرایش محتوای موجود و ساخت محتوای تازه

نصب تازه ۱۲۰ پیش‌نویس صفحهٔ منبع در پنج زبان و ۱۷ محصول کاتالوگ را وارد می‌کند. سایت ابتدا محتوای عمومی منبع را نشان می‌دهد. برای جایگزینی آن، نسخهٔ زبان مربوط را از CMS ویرایش، برای بازبینی مستقل ارسال و منتشر کنید. ذخیرهٔ پیش‌نویس همان انتشار عمومی نیست.

اگر نصب تازه فقط حساب مالک دارد، پیش از نخستین انتشار از بخش کاربران یک حساب مستقل برای بازبین با نقش و زبان مجاز بسازید و MFA آن حساب را فعال کنید. نویسنده و بازبین باید دو حساب متفاوت باشند؛ حتی مدیر نمی‌تواند بازبینی محتوای خودش را تأیید کند. سپس با حساب نویسنده درخواست بازبینی بدهید و با حساب بازبین همان نسخه را بررسی کنید.

صفحه، محصول، بلوک، بلوک مشترک، منو، فرم، رسانه، اسناد و تنظیمات از بخش مرتبط مدیریت می‌شوند. طراحی قالب اصلی حفظ شده است. انعطاف محتوایی، مجوز اجرای JavaScript یا HTML اجرایی نامطمئن در صفحه عمومی ایجاد نمی‌کند.

برای هر زبان `fa`، `en`، `tr`، `ar` و `ru` نسخه و وضعیت انتشار مستقل وجود دارد. ساخت نسخهٔ زبان مقصد، متن فارسی را به‌عنوان ترجمهٔ آماده نمایش نمی‌دهد. مترجم در زبان‌های مجاز خود متن را تکمیل می‌کند؛ سپس بازبینی و انتشار همان زبان انجام می‌شود. [محتوای اولیه](SOURCE-CONTENT.fa.md)، [گردش کار ویرایشگر](EDITOR-WORKFLOWS.fa.md) و [فیلدهای قالب](CMS-TEMPLATE-FIELDS.fa.md) راهنمای جزئیات هستند.

## ۵. تولید و ترجمه با هوش مصنوعی

کلید ارائه‌دهنده، مدل و سقف مصرف را فقط در فایل محیط خصوصی تنظیم کنید. تا زمانی که کلید و مدل معتبر نباشند، ارسال واقعی به سرویس بیرونی تأییدشده نیست. برای تنظیم Google یا OpenRouter و قابلیت‌های متن، تصویر، صوت و ویدیو از [راهنمای AI](AI-MULTILINGUAL.fa.md) استفاده کنید؛ تمام مدل‌ها همهٔ این قابلیت‌ها را ندارند.

خروجی متن و ترجمه ابتدا پیشنهاد قابل ویرایش است. اعمال پیشنهاد روی نسخهٔ مشخص پیش‌نویس انجام می‌شود و تغییر هم‌زمان همکار را بدون بررسی بازنویسی نمی‌کند. نتیجه قبل از انتشار بازبینی می‌شود. فایل تولیدشده نیز تابع مجوز، سهمیه، اسکن و حقوق انتشار رسانه است.

## ۶. فایل‌ها و فضای ذخیره‌سازی

در تنظیمات پنل، مدیر سقف هر فایل و نوع فایل، سهمیهٔ کل سایت، هر حساب و مهمان را تعیین می‌کند. مقدار اولیه از env می‌آید؛ تنظیم ذخیره‌شدهٔ پنل مرجع بعدی است. سقف حفاظتی فعلی یک فایل ۸۰ MiB است؛ افزایش بالاتر به توسعهٔ انتقال جریانی/تکه‌ای جداگانه نیاز دارد.

فایل‌ها روی فضای پایدار سرور ذخیره می‌شوند. فایل خصوصی در پوشهٔ عمومی وب قرار نمی‌گیرد. سند، صوت و ویدیوی در انتظار اسکن قابل دانلود عمومی نیست؛ خاموشی اسکنر آن را آزاد نمی‌کند. کاهش سهمیه زیر مصرف فعلی، فایل موجود را حذف نمی‌کند و آپلود بعدی را محدود می‌کند. نوع‌ها، واحدها و خطاها در [راهنمای ذخیره‌سازی](UPLOAD-STORAGE.fa.md) آمده‌اند.

## ۷. بکاپ و دانلود با یک فرمان

روی سرور:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/backup.sh
```

برای ساخت و دانلود از کامپیوتر خود، در پوشهٔ سورس:

```bash
bash scripts/download-backup.sh \
  --host ubuntu@YOUR_SERVER \
  --remote-root /var/www/idealmakoo-v2 \
  --output ./website.tar.age \
  --recovery-key-output ./website-recovery-key.txt
```

میزبان و اثر انگشت SSH باید از قبل معتبر و حساب دارای مجوز عملیات باشد. آرشیو و فایل کلید باید مسیرهای خروجی جدید باشند. کلید را در محل امنی جدا از بکاپ نگه دارید؛ بدون آن بازیابی ممکن نیست.

بکاپ شامل دیتابیس، رسانه، سورس نسخه، تنظیمات خصوصی، integration، اطلاعات لازم دفتر حریم خصوصی و وضعیت Caddy/TLS است. خروجی رمزنگاری می‌شود. imageها و cacheهای قابل بازسازی در آرشیو نیستند. برای هماهنگی snapshot، سرویس‌های نویسنده موقتاً متوقف می‌شوند؛ این روش بدون وقفه نیست.

## ۸. بررسی و بازیابی

برای تمرین روی نصب موجود، بدون جایگزینی دادهٔ اصلی:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/restore.sh \
  --file /secure-export/website.tar.age --drill
```

برای جایگزینی نصب موجود، از release متناظر بکاپ استفاده کنید و نام پروژه را صریح تأیید کنید:

```bash
sudo bash /var/www/idealmakoo-v2/releases/RELEASE_ID/scripts/restore.sh \
  --file /secure-export/website.tar.age --confirm-replace idealmakoo
```

برای بازیابی کامل روی Ubuntu خالی، پس از قراردادن بستهٔ ابزار، آرشیو و کلید مستقل:

```bash
sudo bash scripts/recover-ubuntu.sh \
  --new-host \
  --file /secure-export/website.tar.age \
  --identity /secure-export/website-recovery-key.txt \
  --latest-ledger /secure-export/latest-ledger \
  --app-dir /var/www/idealmakoo-v2
```

پوشهٔ `latest-ledger` باید نسخهٔ جاری دفتر مستقل حذف اطلاعات از سرور مبدأ باشد؛ آن را جدا از آرشیو قدیمی منتقل کنید. این گزینه حذف‌های ثبت‌شده پس از زمان بکاپ را نیز اعمال می‌کند. اگر دفتر جدیدتری در دسترس نیست، گزینه را حذف کنید؛ بازیابی فقط با دفتر داخل آرشیو نمی‌تواند از حذف‌های بعد از آن snapshot اطلاع داشته باشد. تهیه و انتقال صحیح این پوشه در راهنمای بکاپ/بازیابی آمده است.

بازیابی، نشست‌های قدیمی را معتبر نمی‌کند. محدودیت‌ها و حذف دادهٔ ثبت‌شده در دفتر جاری روی نصب موجود حفظ می‌شوند. در بازیابی روی میزبان تازه، ارسال‌های بیرونی به‌صورت پیش‌فرض متوقف می‌مانند تا اپراتور پیکربندی را بررسی کند؛ بازیابی نصب موجود تنظیمات جاری میزبان را حفظ می‌کند. این دستورها جای خواندن [راهنمای بکاپ/بازیابی](BACKUP-RESTORE.fa.md) و [امنیت بازیابی](RESTORE-SECURITY.fa.md) را نمی‌گیرند؛ رفتار میزبان تازه و نصب موجود تفاوت دارد.

## ۹. سئو و بررسی پس از انتشار

عنوان و توضیح هر زبان را از پنل تنظیم و محتوای همان زبان را کامل کنید. canonical، hreflang و sitemap باید دامنهٔ عمومی درست را معرفی کنند. صفحهٔ خصوصی و ورود `noindex` می‌ماند. در Search Console مالکیت دامنه را تأیید و `/sitemap.xml` را ثبت کنید؛ سپس خطاهای ایندکس، وضعیت صفحات مهم و عملکرد واقعی کاربران را پیگیری کنید.

آزمون Lighthouse و گزارش metadata در [راهنمای Lighthouse](LIGHTHOUSE.fa.md) و اقدامات محتوا/نمایه‌سازی در [راهنمای SEO](SEO.fa.md) توضیح داده شده‌اند. امتیاز آزمایشگاهی یک محیط، تضمین سرعت تمام دستگاه‌ها یا قرارگرفتن در صفحهٔ اول گوگل نیست. نتیجهٔ واقعی این تحویل را از گزارش پذیرش بخوانید.

## ۱۰. ترتیب کار روزمره و نگهداری

پیش از ارتقا بکاپ بگیرید، سلامت و فضای آزاد را بررسی کنید، نسخهٔ جدید را طبق راهنمای استقرار اعمال کنید و پس از آن ورود، فرم مهم، انتشار محتوا و worker را کنترل کنید. بکاپی که فقط ساخته شده ولی تمرین بازیابی ندارد، شاهد کافی برای بازگشت سرویس نیست. به‌صورت دوره‌ای یک drill ثبت کنید و یک نسخهٔ رمزنگاری‌شده را خارج از همان سرور نگه دارید.

هر زمان یک اتصال خارجی را فعال کردید، نتیجهٔ واقعی همان سرویس را بررسی کنید. وضعیت صف، تحویل ایمیل یا SMS را ثابت نمی‌کند. کلید، env، cookie، دادهٔ مشتری و بکاپ خصوصی را همراه گزارش خطا منتشر نکنید؛ `doctor.sh` برای جمع‌آوری اطلاعات عملیاتی محدود طراحی شده است.

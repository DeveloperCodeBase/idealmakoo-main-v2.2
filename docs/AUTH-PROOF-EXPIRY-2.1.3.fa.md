# اصلاح انقضای نشست و اثبات ورود — نسخهٔ ۲٫۱٫۳

## مشکل و رفتار اصلاح‌شده

بررسی نسخهٔ ۲٫۱٫۲ یک خطای واقعی در کنترل انقضا پیدا کرد: اگر درخواست احراز هویت برای آزادشدن ردیف کاربر در PostgreSQL منتظر می‌ماند، ممکن بود مهلت نشست یا توکن در همان فاصله تمام شود، اما درخواست همچنان پذیرفته شود. علت، استفاده از `now()` در بررسی نهایی بود؛ این تابع زمان آغاز تراکنش را برمی‌گرداند و در طول انتظار جلو نمی‌رود.

در نسخهٔ ۲٫۱٫۳، چهار پرس‌وجوی بررسی نهایی در `src/server/auth.ts` از `clock_timestamp()` استفاده می‌کنند. بررسی عمر مطلق و بیکاری نشست، چالش ورود دومرحله‌ای، لینک تغییر رمز و لینک تأیید ایمیل، زمان واقعی پس از انتظار برای قفل کاربر را در نظر می‌گیرند. تعریف تفاوت این دو تابع در [مستندات رسمی PostgreSQL 16](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT) آمده است.

این تغییر، مدت اعتبار تنظیم‌شده، سیاست نقش‌ها، الزام MFA، شکل پاسخ API، ترتیب قفل‌ها و رفتار ابطال نشست را عوض نمی‌کند. migration جدید، تغییر داده یا تغییر طراحی لازم ندارد.

## بازتولید و آزمون واقعی

فایل `tests/server-auth-expiry.pg.mjs` پنج سناریوی واقعی را روی PostgreSQL 16.15 بررسی می‌کند. هر سناریو یک ردیف کاربر را در اتصال دیگری قفل می‌کند، منتظر می‌ماند تا درخواست برنامه واقعاً پشت همان قفل قرار بگیرد، مهلت اثبات را بین آغاز تراکنش و آزادشدن قفل قرار می‌دهد و نتیجه را بررسی می‌کند. ساعت، توابع برنامه و پرس‌وجوها mock نشده‌اند.

| سناریو | نتیجهٔ الزامی پس از اصلاح |
| --- | --- |
| پایان عمر مطلق نشست هنگام انتظار | پاسخ `401 SESSION_REQUIRED`؛ بدون تولید چالش، پیام خروجی یا رویداد تأیید ایمیل |
| پایان مهلت بیکاری نشست هنگام انتظار | همان رد درخواست، بدون آثار جانبی |
| پایان مهلت چالش MFA هنگام انتظار | پاسخ `401 MFA_INVALID`؛ بدون نشست جدید یا مصرف کد احراز هویت |
| پایان مهلت لینک تغییر رمز هنگام انتظار | پاسخ `422 RESET_EXPIRED`؛ رمز و نشست‌های موجود تغییر نمی‌کنند |
| پایان مهلت لینک تأیید ایمیل هنگام انتظار | پاسخ `422 VERIFY_EXPIRED`؛ ایمیل تأیید و توکن مصرف نمی‌شود |

هر پنج سناریو روی کد پیش از اصلاح شکست خورد و روی کد اصلاح‌شده موفق شد. Node.js آزمون والد را نیز می‌شمارد؛ بنابراین خروجی اجرا **۶ آزمون موفق، صفر ناموفق و صفر skipped** است. این عدد به معنی شش سناریوی مستقل نیست.

شاهدهای قابل بررسی: [اجرای قبل از اصلاح](verification-evidence/repair-2.1.3/auth-expiry-red-01.safe.json) و [اجرای پس از اصلاح](verification-evidence/repair-2.1.3/auth-expiry-green-01.safe.json). هر شاهد، هش دقیق کد و آزمون و کد خروج واقعی فرایند را ثبت می‌کند. اجرای قبل عمداً ناموفق است و نباید به‌عنوان نتیجهٔ نهایی تحویل خوانده شود.

## اجرای مجدد

روی دیتابیس آزمایشی مستقل و خالی، با دسترسی ایجاد schema و همان وابستگی‌های قفل‌شدهٔ پروژه:

```bash
node --env-file=/secure/path/test.env --import tsx --test tests/server-auth-expiry.pg.mjs
```

فایل خصوصی آزمون باید `TEST_ADMIN_DATABASE_URL` یا `TEST_DATABASE_URL` را به همان دیتابیس آزمایشی اشاره دهد. آزمون از schemaهای موقت استفاده و آن‌ها را پاک می‌کند. تنظیم اتصال تولید را برای این فرمان استفاده نکنید. وضعیت مجموعهٔ کامل PostgreSQL، API و ساخت تولید را از گزارش پذیرش همین انتشار بخوانید؛ موفقیت این پنج سناریو به‌تنهایی پذیرش تمام محصول نیست.

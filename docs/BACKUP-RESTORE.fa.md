# پشتیبان کامل، دانلود و بازیابی یک‌فرمانی

فرمان‌های این راهنما برای نسخه جاری و بکاپ **format4** هستند. بکاپ شامل کد همان نسخه در حال اجرا، دیتابیس، تمام رسانه‌ها، تنظیمات و کلیدهای داخلی/ارائه‌دهندگان، فایل‌های integration، دفتر امضاشده حریم خصوصی، داده/پیکربندی TLS پراکسی و دادهٔ ایمیل دامنه است. کل مجموعه پیش از خروج از مسیر خصوصی میزبان با `age` رمزنگاری می‌شود. **کلید رمزگشایی بکاپ عمداً خارج از آرشیو است**؛ برای بازیابی به فایل آرشیو و این کلید جداگانه نیاز دارید. format3 احرازاصالت‌شدهٔ قبلی همچنان پشتیبانی می‌شود؛ آن قالب شامل mailbox نبود.

در مثال‌ها، ریشه نصب `/var/www/idealmakoo-v2` و نام Compose برابر `idealmakoo` است. این دو مقدار را با نصب خود هماهنگ کنید. فرمان‌های روی میزبان با دسترسی مدیر اجرا می‌شوند؛ دانلود از دستگاه شخصی نیازمند SSH مجاز و کلید میزبانِ از قبل بررسی‌شده است.

برای timer روزانهٔ پیش‌فرض، مقصد نصب یک پوشهٔ اختصاصی زیر `/var/www` یا `/opt` باشد. نصاب مقصد واقعی داخل `/home`، `/root`، `/run/user`، `/tmp` یا `/var/tmp` را، حتی از مسیر symlink یا `..`، رد می‌کند؛ سرویس بکاپ با `ProtectHome=true` و `PrivateTmp=true` به چنین مقصدی دسترسی ندارد. فایل env ورودی می‌تواند جداگانه در مسیر خصوصی مانند `/root` باشد. گزینهٔ صریح `--without-backup-timer` برای انتخاب بکاپ دستی، راه‌اندازی timer را در همان اجرا کنار می‌گذارد؛ timer قبلاً ایجادشده را خاموش نمی‌کند. این قاعده در نصب و بازیابی روی میزبان تازه یکسان است.

## ۱. نصب از فایل محیط محافظت‌شده

بسته کد را روی Ubuntu 22.04 یا 24.04 استخراج کنید. آماده‌سازی تنظیمات یک بار انجام می‌شود:

```bash
cp .env.example .env
chmod 600 .env
```

فایل را با ویرایشگر خصوصی تکمیل کنید: `SITE_ADDRESS`، `SITE_URL`، `ACME_EMAIL`، `BOOTSTRAP_ADMIN_EMAIL` و در صورت نیاز `INSTALL_ROOT`، `COMPOSE_PROJECT_NAME`، اطلاعات کارکنان و کلیدهای سرویس‌ها. الگوی کامل کارکنان و نقش‌های مجاز در [STAFF-ENV.fa.md](STAFF-ENV.fa.md) آمده است. مقدارهای خالی رمزهای داخلی، کلید نشست، کلید MFA و URLهای نقش‌های دیتابیس را نصاب **فقط در نصب اول** با مقادیر مستقل و تصادفی تولید می‌کند؛ کپی فایل نمونه با این نصاب به خطای «رمز خالی» منتهی نمی‌شود. رمز موجود در نصب مجدد تغییر نمی‌کند.

سپس نصب با یک دستور:

```bash
sudo bash scripts/install-ubuntu.sh --env-file "$PWD/.env"
```

یا بدون فایل ورودی، با تولید تنظیمات اولیه و رمز مدیر:

```bash
sudo bash scripts/install-ubuntu.sh --domain YOUR_DOMAIN --email YOUR_EMAIL --app-dir /var/www/idealmakoo-v2
```

برای حالت اول، نشانی‌ها را پیش از اجرا واقعی کنید؛ فایل نمونه هنوز دامنه نمونه دارد. پورت‌ها، مسیرهای bind و نام پروژه از فایل محیط خوانده می‌شوند و گزینه صریح CLI بر انتخاب متناظر همان نصب مقدم است. هنگام اجرای عملیاتی، `deploy/compose.py` فایل محیط فعال و metadata نسخه را مرجع قرار می‌دهد؛ متغیرهای قدیمیِ exportشده در شل نمی‌توانند رمز، دامنه یا پروژه را عوض کنند. هرگز `.env` را با `source` اجرا نکنید.

پیش‌نیازها: میزبان systemd، حداقل ۶ GiB RAM با آنتی‌ویروس (۸ GiB توصیه می‌شود)، حداقل ۱۵ GiB دیسک آزاد اولیه و شبکه لازم برای مخازن و رجیستری‌ها. دامنه عمومی باید DNS صحیح و دسترسی TCP80/443 داشته باشد. نصاب Docker، Compose، ابزارهای سیستم، تصاویر برنامه، PostgreSQL، Caddy، worker، ClamAV، مهاجرت‌ها، seed قابل ویرایش، حساب‌های محیط، سلامت و نخستین بکاپ را آماده می‌کند. برای HTTP محلی، `--http` صریح لازم است؛ راهنمای اصلی TLS در [DEPLOYMENT.fa.md](DEPLOYMENT.fa.md) است.

## ۲. ساخت کامل بکاپ با یک دستور

روی سرور:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/backup.sh
```

مسیر آرشیو نهایی روی stdout و پیام پیشرفت روی stderr می‌آید. خروجی پیش‌فرض در `shared/backups` است. برای خروجی اختصاصی، پوشه مقصد باید از قبل موجود و مسیر فایل جدید باشد:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/backup.sh --output /secure-export/website.tar.age
```

آرشیو موجود رونویسی نمی‌شود. فایل `.sha256` کنار آن ایجاد می‌شود. مقایسه checksum برای تشخیص خرابی انتقال مناسب است؛ اصالت محتوا در بازیابی علاوه بر رمزنگاری age، با MAC مربوط به کلید خصوصی مستقل بررسی می‌شود.

### محتویات و سازگاری snapshot

| بخش | چیزی که واقعاً ذخیره می‌شود |
| --- | --- |
| دیتابیس | dump قالب custom از schema عمومی، همه ردیف‌ها، function، view، index، constraint، trigger، sequence، محتوا، کاربران، نقش‌های برنامه، تنظیمات پنل و صف‌ها |
| رسانه | تمام Volume `/app/storage`، شامل فایل‌های عمومی، خصوصی، اصل تصویر، مشتق‌ها، خروجی پردازش و قرنطینه |
| کد | سورس همان release واقعاً متصل به کانتینر، lockfile، فایل‌های build/Compose/نصب و migrations با checksum متناظر DB |
| پیکربندی محرمانه | فایل محیط فعال، کلیدهای نشست/MFA و credentialهای DB/provider؛ همگی داخل رمزنگاری |
| integration | فایل‌های واقعی integration، از جمله worker رسمی push در صورت پیکربندی |
| حریم خصوصی | هویت و زنجیره امضاشده حذف داده و anchor snapshot؛ کاربرد این کپی فقط بازیابی صریح روی میزبان تازه است |
| پراکسی | Volumeهای Caddy data و config، شامل گواهی‌ها و کلیدهای TLS در صورت موجود بودن |
| ایمیل دامنه | mailbox، صف/وضعیت، تنظیمات حساب و DKIM، لاگ‌های ایمیل و manifest همان پروژه؛ اگر سرویس اکنون خاموش است ولی دادهٔ مدیریت‌شده دارد نیز حفظ می‌شود |
| شواهد | manifest اصالت، SHA-256 تک‌تک payloadها، تعداد و hash محتوای هر relation، ساختار schema، sequenceها و نام/checksum migrations |

کلید خصوصی `shared/backup-identity.txt`، imageهای حجیم Docker، `node_modules`، cacheهای Next، امضاهای قابل دریافت ClamAV، لاگ‌های عمومی کانتینرهای برنامه، بکاپ‌های قبلی و داده‌های وب‌سایت‌های دیگر در آرشیو نیستند. لاگ‌های داخل پوشهٔ ایمیل بخشی از snapshot ایمیل‌اند و داخل رمزنگاری قرار می‌گیرند. موارد قابل بازسازی از lockfile/سورس و رجیستری دوباره ساخته می‌شوند؛ بازیابی میزبان تازه به اینترنت این مخازن نیاز دارد. برای محیط کاملاً آفلاین، باید mirror بسته‌ها و تصاویر جداگانه اداره شود.

### حفاظت ویژهٔ ایمیل در format4

`mail.tar` و `mail-manifest.json` هر دو در فهرست checksum و احراز اصالت آرشیو قرار دارند. پروژه و دامنهٔ mailbox به نصب مقیدند. snapshot فقط بعد از توقف نویسندهٔ ایمیل ثبت‌شده گرفته می‌شود؛ FIFO/socketهای موقتی کپی نمی‌شوند. مسیرهای خارج از ریشه، symlink فراری و فایل والدِ ناامن پیش از استخراج رد می‌شوند. سرویس ایمیل از قبل خاموش، در پایان بکاپ خودکار روشن نمی‌شود.

در restore همان میزبان، تنظیمات و کلیدهای **جاری** صندوق‌ها حفظ می‌شوند تا حساب یا رمز لغوشده از گذشته بازنگردد. بازیابی روی میزبان تازه، تنظیمات موجود در آرشیو احرازاصالت‌شده را برمی‌گرداند و مقصد غیرخالی را نمی‌پذیرد. پس از هر restore ایمیل، `MAIL_OUTBOUND_ENABLED=false` است و transport خروجی defer می‌شود. ابتدا صف واقعی را بررسی و سپس، اگر ارسال‌های آن صحیح‌اند، از `scripts/mail-server.sh activate-outbound --confirm-reviewed-queue` استفاده کنید. حالت `--activate-outbound` بازیابی برنامه، جای این بررسی مستقل صف Postfix نیست. [راهنمای ایمیل و صف](INSTALL-SERVICES-SEO-2.2.fa.md).

آرشیو قدیمی بدون بخش ایمیل، mailbox جاری را حذف نمی‌کند. backup/restore ایمیل، مهاجرت خودکار دامنه یا انتقال از ارائه‌دهندهٔ خارجی نیست؛ MX، PTR، دسترسی TCP25 و اعتبار تحویل دامنه بعد از تغییر میزبان جدا بررسی می‌شوند.

تعویض مرحله‌ای دادهٔ ایمیل، پوشهٔ قبلی را به `mail-server.before-restore-<شناسه>` منتقل و خصوصی نگه می‌دارد. این نسخهٔ محلی رمزگذاری‌شده با age نیست؛ از نظر دسترسی و نگهداشت، مانند دادهٔ جاری صندوق حساس است. ظرفیت کپی قبلی و دادهٔ جدید را پیش‌بینی و پس از پذیرش بازیابی، پاک‌سازی همان مسیر دقیق را طبق سیاست نگهداشت انجام دهید. حذف خودکار این نقطهٔ بازگشت انجام نمی‌شود.

هویت image از **شناسهٔ واقعی کانتینر در حال استفاده** گرفته می‌شود؛ تغییر tag یا pull نسخهٔ جدید، ابزارهای snapshot را به runtime دیگری منتقل نمی‌کند. برای دیتابیس، digest فقط از metadata همان image واقعی و از repository مربوط به مرجع اجرای DB انتخاب می‌شود؛ alias محلیِ نامرتبط نباید به‌عنوان مقصد دریافت در آرشیو ثبت شود. اگر مرجع اجرا digest صریح داشته باشد، همان digest لازم است؛ نبودن تطبیق معتبر یا چند digest مبهم، بکاپ را پیش از توقف نویسنده‌ها رد می‌کند.

این بررسی محلی، **انتشار یا در دسترس بودن image در registry را اثبات نمی‌کند**. Docker با backend مبتنی بر containerd می‌تواند برای image ساخته‌شده یا alias صرفاً محلی هم `RepoDigests` بسازد؛ بکاپ برای بررسی شبکهٔ registry تماس اجباری اضافه نمی‌کند. برای PostgreSQL سفارشی، image را واقعاً در registry مجاز منتشر کنید، با digest روی میزبان pull کنید و نگه‌داری همان digest و credential و دسترسی شبکهٔ میزبان جایگزین را جداگانه آزمایش کنید. تمرین بازیابی روی میزبان مستقل، امکان دریافت واقعی را بررسی می‌کند. format3 بایت‌های image سفارشی یا credential ورود Docker به registry را همراه آرشیو حمل نمی‌کند. [رفتار ثبت RepoDigest در Docker/containerd](https://github.com/moby/moby/blob/master/daemon/containerd/image_inspect.go)

برنامه، worker و پراکسیِ روشن هنگام snapshot متوقف می‌شوند؛ هماهنگی DB، رسانه و وضعیت TLS در همین پنجره انجام می‌شود. پیش از توقف، هویت همان container IDها ثبت می‌شود؛ شروع دوباره فقط همان شناسه‌ها را به ترتیب app، worker، proxy و با gate سلامت مرتبط برمی‌گرداند. سرویس از قبل خاموش، خودکار روشن نمی‌شود و snapshot ابزار recreate نیست. مدت توقف به حجم داده و زمان آمادگی بستگی دارد؛ این روش zero-downtime نیست. قفل عملیات، اجرای همزمان نصب/بکاپ/restore را منع می‌کند. فضای خام خصوصی و آرشیو رمزنگاری‌شده موقتاً همزمان وجود دارند؛ برای حجم زیاد، بیش از اندازه کل داده‌ها فضای آزاد لازم است. سقف بازکردن آرشیو ۱۲۸ GiB و تعداد اعضای رسانه ۲۰۰ هزار است؛ رشد بیشتر باید با ابزار و محدودیت‌های مرورشده برنامه‌ریزی شود.

پیش از نوشتن plaintext در restore، حد اندازه/نوع فایل و حداقل فضای آزاد **دو برابر فایل رمزنگاری‌شده به‌علاوه ۶۴ MiB** بررسی می‌شود. این فقط فضای رمزگشایی و استخراج اولیه است؛ حجم واقعی DB پس از بازکردن dump، رسانهٔ بازیابی‌شده، تصویرهای build و safety backup نیز باید جدا ظرفیت داشته باشند. در شکست بکاپ، حذف فضای موقت پیش از تلاش برای بازگرداندن نویسندگان انجام می‌شود؛ اگر حذف ناموفق باشد، خطا ثبت می‌شود و همان تلاش مجازِ بازگردانی ادامه می‌یابد. خطای اصلی غیرصفر بکاپ با خطای حذف یا بازگشت پوشانده نمی‌شود. کمبود ظرفیت، با پاک‌کردن خودکار داده‌های جاری جبران نمی‌شود.

### snapshot باقیمانده پس از شکست بازگشت سرویس‌ها

بکاپ فقط یک تلاش خودکار برای بازگرداندن مجموعهٔ قبلی دارد. اگر آن تلاش ناموفق باشد، EXIT دوباره startup را اجرا نمی‌کند. فایل کوچک `.snapshot.<شناسه>.runtime.json` با مجوز `600` در کنار پوشهٔ موقت نگه داشته می‌شود و مسیر دقیق آن در خطا می‌آید؛ این فایل، snapshot دیتابیس یا آرشیو قابل restore نیست. نام پروژه، مسیر واقعی env و هویت containerهای انتخاب‌شده را به هم متصل می‌کند. آن را منتشر، ویرایش یا با فایل دیگری جایگزین نکنید.

ابتدا علت خطا، ظرفیت دیسک، وضعیت Docker و لاگ محدود سرویس را بررسی کنید. پیام حذف ناموفق یعنی ممکن است پوشهٔ خصوصی plaintext نیز باقی مانده باشد؛ فقط مسیر دقیق گزارش‌شدهٔ همان تلاش را بعد از بررسی مالکیت و پایان عملیات پاک‌سازی کنید، نه همهٔ فایل‌های `.snapshot.*`. کمبود فضا یا دسترسی را پیش از تلاش بعدی برطرف کنید. اگر `shared/.pending-restore` وجود دارد، این روش مجاز نیست؛ ادامهٔ همان restore با `--resume` مقدم است.

پس از رفع علت و با اطمینان از اینکه containerهای ثبت‌شده حذف یا جایگزین نشده‌اند، یک تلاش صریح از کد helper بررسی‌شده انجام دهید. مسیر نمونهٔ زیر را فقط با **همان مسیر دقیق گزارش‌شده** عوض کنید:

```bash
sudo -i
cd /var/www/idealmakoo-v2/current
(
  source deploy/lib.sh
  require_environment
  acquire_ops_lock
  pending_restore assert-clear
  runtime_snapshot='/var/www/idealmakoo-v2/shared/backups/.snapshot.EXACT_ID.runtime.json'
  lifecycle start --snapshot "$runtime_snapshot" --timeout 1200
  rm -f -- "$runtime_snapshot"
)
```

حذف این فایل فقط پس از موفقیت `start` اجرا می‌شود؛ خطای جدید، آن را برای بررسی نگه می‌دارد. `start` هویت کانتینرها و وضعیت اجرا و سلامت سرویس‌های داخل snapshot را طبق نوع سرویس بررسی می‌کند؛ readiness عمومی فقط زمانی لازم است که **هر دو app و proxy** در مجموعهٔ ثبت‌شده باشند. این قاعده مخصوص بازگرداندن همان زیرمجموعه است؛ `up` جدید و `check` برای مجموعهٔ شامل proxy همچنان readiness عمومی را لازم می‌دانند. موفقیت یک زیرمجموعه به معنی روشن یا سالم‌بودن سرویس‌های خارج از آن نیست. برای نصب کاملی که هر سه سرویس باید فعال باشند، بعداً `scripts/check-health.sh 240` را نیز اجرا کنید. اگر IDها تغییر کرده‌اند، helper عمداً ادامه را رد می‌کند؛ فایل را برای عبور از کنترل اصلاح نکنید و به `up` عمومی به‌عنوان جایگزین خودکار متوسل نشوید. وضعیت release، env و checkpoint باید با مسیر عملیات مناسب بررسی شود. بازگشت سرویس‌ها، به‌تنهایی موفقیت بکاپی را که قبلاً خطا داده اثبات نمی‌کند؛ آرشیو باید جداگانه بررسی شود یا یک بکاپ تازهٔ موفق تهیه شود.

## ۳. ساخت و دانلود مستقیم با یک دستور از دستگاه شخصی

در دستگاه Linux/macOS/WSL با Bash، SSH و sha256sum، از کد همین نسخه اجرا کنید:

```bash
bash scripts/download-backup.sh \
  --host ubuntu@YOUR_SERVER \
  --remote-root /var/www/idealmakoo-v2 \
  --output ./website.tar.age \
  --recovery-key-output ./website-recovery-key.txt
```

این دستور از طریق SSH بکاپ کامل می‌سازد و **فقط بایت‌های رمزنگاری‌شده** را به فایل محلی می‌فرستد. کلید اختیاری در یک فایل مجزای خصوصی با مجوز ۶۰۰ ذخیره می‌شود؛ محتوای کلید در خروجی چاپ نمی‌شود. هر دو مسیر باید جدید و از نظر مقصد واقعی متفاوت باشند؛ نام نسبی/مطلق یا پوشهٔ لینک‌شده که کلید را به همان فایل آرشیو یا checksum برساند، پیش از SSH رد می‌شود. آرشیو و کلید را پس از دانلود در دو محل امن مستقل نگهداری کنید؛ پاک‌شدن یک دیسک نباید هر دو را از بین ببرد. در دانلودهای بعدی که کلید جداگانه را نگهداری کرده‌اید، گزینه `--recovery-key-output` لازم نیست.

برای پورت یا هویت SSH اختصاصی، `--port 2222` و `--ssh-identity /absolute/private-key` اضافه کنید. با `--known-hosts /absolute/verified-known-hosts` می‌توان فایل اثر انگشتِ از قبل بررسی‌شده را جدا انتخاب کرد. اتصال از `BatchMode=yes` و `StrictHostKeyChecking=yes` استفاده می‌کند؛ اثر انگشت واقعی میزبان را از مسیر معتبر بررسی و در known_hosts ثبت کنید. حساب SSH باید اجرای `sudo -n` برای این عملیات مجاز را داشته باشد؛ اسکریپت برای دورزدن مجوز یا تعویض کلید میزبان تنظیم SSH را تضعیف نمی‌کند. دانلود بدون تعیین میزبان آغاز نمی‌شود و بکاپ به یک سرویس ثالث فرستاده نمی‌شود.

معادل stream روی خود میزبان نیز موجود است: `backup.sh --stdout`. نتیجه آن باینری رمزنگاری‌شده است؛ آن را به فایل/کانال باینری معتبر هدایت کنید. پیام پیشرفت در stdout مخلوط نمی‌شود.

## ۴. اعتبارسنجی و تمرین بدون جایگزینی سایت

روی نصب موجود:

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/restore.sh --file /secure-export/website.tar.age --verify-only
sudo bash /var/www/idealmakoo-v2/current/scripts/restore.sh --file /secure-export/website.tar.age --drill
```

بررسی اول، رمزگشایی، اصالت manifest، checksum، مسیر/نوع امن همه اعضا، سازگاری migrationهای سورس/دیتابیس و anchor در دفتر جاری را کنترل می‌کند. تمرین، dump را واقعاً در یک DB موقت یکتا restore می‌کند، **hash ردیف‌های تمام relationها، ساختار، sequenceها و migrations** را با snapshot تطبیق می‌دهد، grants را اعمال و با نقش محدود برنامه می‌آزماید. دسترسی غیرمجاز به migration، ساخت schema، تغییر audit و جعل مدرک recovery باید خطای مجوز بدهد. رسانه در مسیر مستقل استخراج و بایت‌های فایل‌ها بررسی می‌شود. سپس دفتر حذف جاری replay، سطح دسترسی جاری تطبیق، مجوزهای ورود قدیمی باطل و gate سلامت کنترل می‌شود. تمام تغییرات امنیتی تمرین فقط روی DB موقت انجام می‌شوند. DB/فایل‌های تمرین در پایان پاک می‌شوند؛ گزارش موفق تنها پس از تمام gateها ثبت می‌شود.

قالب پیش‌فرض تمام حالت‌های بررسی/تمرین/جایگزینی، format3 یا format4 دارای احراز اصالت است. برای بکاپ تاریخی data-only از نوع format2، فقط پس از تأیید مستقل منشأ فایل، گزینهٔ `--allow-legacy-format2` را صریح اضافه کنید؛ رمزنگاری age برای گیرنده و checksum به‌تنهایی هویت فرستندهٔ آن قالب قدیمی را اثبات نمی‌کنند. این استثنا در بازیابی میزبان تازه پذیرفته نیست. شرح سازگاری در [راهنمای عملیات، بخش قالب تاریخی](OPERATIONS.fa.md) آمده است.

## ۵. بازگردانی یک‌فرمانی روی نصب موجود

از پوشه release متناظرِ داخل بکاپ:

```bash
sudo bash /var/www/idealmakoo-v2/releases/RELEASE_ID/scripts/restore.sh \
  --file /secure-export/website.tar.age --confirm-replace idealmakoo
```

`--confirm-replace` نام دقیق پروژه است و اجازه جایگزینی همان DB/Volume را می‌دهد. قبل از توقف و بازنویسی، safety backup تازه ساخته می‌شود. image و release باید متناظر باشند؛ ناسازگاری schema با کد رد می‌شود. این عملیات DB و رسانه را به زمان snapshot بازمی‌گرداند؛ تغییرات بعدی کنار می‌روند. تنظیمات فعلی میزبان و دفتر حذف **فعلی** حفظ می‌شوند. اگر کلید نشست/MFA متفاوت باشد، اجرای صریح `--restore-keys` پس از بررسی فقط همان دو کلید متناظر را بازمی‌گرداند. credentialهای نقش‌های DB و تنظیمات فعلی میزبان جایگزین نمی‌شوند.

در این مسیر، سورس و imageهای release متناظر باید از قبل موجود باشند؛ فرمان آن‌ها را از آرشیو روی نصب فعال استخراج نمی‌کند. فایل‌های اتصال سرویس‌ها در پوشه integrations و Volumeهای TLS/Caddy جاری نیز حفظ می‌شوند. برای بازسازی کامل کد، env، فایل‌های اتصال و وضعیت TLS از کپی احرازاصالت‌شده، مسیر **میزبان تازه** در بخش ۶ را روی هدف خالی اجرا کنید. هر دو حالت، قواعد دفتر حذف مستقل و باطل‌سازی ورودهای قدیمی را اعمال می‌کنند.

پس از بازیابی، همان کنترل کامل داده/grants/رسانه، replay دفتر جاری و سلامت انجام می‌شود. شکست پس از آغاز جایگزینی، app و worker همین پروژه را متوقف می‌کند؛ این توقف شامل شکست health پس از روشن‌شدن آزمایشی سرویس‌ها نیز می‌شود. دیتابیس، Volumeها و safety backup برای تشخیص و اصلاح باقی می‌مانند. اگر Docker امکان توقف سرویس‌ها را ندهد، خطا صریح گزارش می‌شود و باید پیش از اتصال ترافیک، این دو سرویس را متوقف کنید. پوشه نسخه و imageهای مورد نیاز بکاپ‌های نگهداری‌شده را حذف نکنید. برای از دست رفتن کامل میزبان از مسیر بعد استفاده کنید.

### ادامهٔ عملیات نیمه‌تمام با حفظ دسترسی جاری

پس از توقف نویسندگان و پیش از نخستین حذف دیتابیس، همان بایت‌های snapshot دسترسی جاری در پوشهٔ خصوصی `shared/.pending-restore` به‌صورت پایدار ثبت می‌شوند. metadata آن، hash آرشیو انتخابی، نسخه، پروژه، نشانی سایت، انتخاب `--restore-keys`، هویت snapshot و مسیر/hash **همان safety backup اولیه** را نگه می‌دارد. نخستین خطا و آخرین خطای قابل ثبت نیز حفظ می‌شوند. پاک‌شدن فایل‌های موقت، این checkpoint را حذف نمی‌کند.

تا پایان این عملیات، نصب، ارتقا، بکاپ معمولی و اجرای دوبارهٔ restore بدون `--resume` رد می‌شوند. این رفتار از گرفتن snapshot دسترسی جدید از دیتابیس تاریخی یا ناقص جلوگیری می‌کند. علت خطا را برطرف کنید و از **همان پوشهٔ release**، **همان آرشیو** و **همان انتخاب کلیدها** ادامه دهید:

```bash
sudo bash /var/www/idealmakoo-v2/releases/RELEASE_ID/scripts/restore.sh \
  --file /secure-export/website.tar.age --confirm-replace idealmakoo --resume
```

اگر فرمان اولیه `--restore-keys` داشت، ادامهٔ آن نیز باید این گزینه را داشته باشد. انتخاب آرشیو، نسخه، سایت یا پروژهٔ متفاوت رد می‌شود؛ safety backup اولیه باید موجود و بدون تغییر باقی بماند. `--resume` پیش از بررسی فایل، app/worker همان پروژه را متوقف می‌کند تا قطع ناگهانی پس از روشن‌شدن آزمایشی سرویس‌ها پنجرهٔ باز باقی نگذارد.

| مرحلهٔ پایدار | رفتار ادامهٔ عملیات |
| --- | --- |
| `prepared` | DB و رسانه دوباره از همان آرشیو بازیابی می‌شوند؛ snapshot دسترسی جاری و safety backup دوباره ساخته نمی‌شوند. نبود DB پس از قطع بین حذف و ایجاد دوباره قابل ادامه است. تا اعمال حفاظت‌ها، provisioning کارکنان نیز بسته می‌ماند. |
| `security-applied` | DB، رسانه و کلیدهای env دوباره بازنویسی نمی‌شوند. همان هویت reconciliation باید در audit موجود باشد؛ نتیجهٔ idempotent بررسی می‌شود، دفتر جاری و سلامت دوباره کنترل می‌شوند و بازیابی صریح حساب مدیر حفظ می‌شود. |

checkpoint فقط پس از آمادگی امنیتی، سلامت سرویس‌ها، ثبت گزارش موفق و تکمیل اشاره‌گر نسخه پاک می‌شود. خطای health، ثبت گزارش، سیگنال پایان یا خروج ۲ آن را نگه می‌دارد. **پوشهٔ pending، فایل دسترسی یا safety backup اولیه را برای دورزدن خطا حذف نکنید و نویسندگان را دستی روشن نکنید.** ابتدا ادامهٔ همان عملیات باید موفق شود. نبود هویت audit مرحلهٔ committed، خرابی checkpoint یا اختلاف hash نیازمند بررسی مدیر میزبان است و با بازخوانی نقش‌های تاریخی جبران نمی‌شود.

### حساب‌ها و ورود پس از بازیابی

در بازیابی روی میزبان موجود، پس از توقف app/worker و پیش از تعویض DB، یک snapshot خصوصی از **وضعیت فعلی** حساب‌ها، نقش‌ها، زبان‌های مجاز، دسترسی کیفیت/CRM و عضویت‌های تیم/قلمرو گرفته می‌شود. این snapshot از آرشیو قدیمی خوانده نمی‌شود و رمز یا کلید MFA در آن ذخیره نمی‌شود. پس از تطبیق کامل داده خام و replay حذف‌ها، همین دسترسی‌های جاری روی هویت‌های متناظر اعمال می‌شوند. حساب غیرفعال، دسترسی حذف‌شده، عضویت منقضی‌شده یا حسابی که دیگر در وضعیت فعلی وجود ندارد، با restore دوباره فعال نمی‌شود. اگر رمز یا MFA حساب بعد از snapshot تغییر کرده باشد، ابزار به‌جای فعال‌کردن credential قدیمی، آن حساب بازیابی‌شده را غیرفعال می‌کند؛ بازفعال‌سازی نیازمند اقدام صریح مدیر از مسیر `provision-staff.sh` و env بررسی‌شده است.

در تمام بازیابی‌های واقعی، نشست‌ها، challengeهای ورود/بازیابی رمز/تأیید ایمیل، دعوت‌های استفاده‌نشده، ثبت‌نام نیمه‌تمام MFA و کدهای بازیابی MFA قدیمی باطل می‌شوند؛ پیام‌های صف مربوط به همین challengeها نیز لغو می‌شوند. رمزهای ذخیره‌شده و TOTP ثبت‌شده حفظ می‌شوند. کاربران باید دوباره وارد شوند و کدهای بازیابی MFA را از پنل امنیت بازتولید کنند. کد TOTP در بازه جاری زمان بازیابی یا بازه‌ای که قبلاً پذیرفته شده نیز دوباره قابل استفاده نیست؛ از کد تازه‌ای استفاده کنید که قبلاً پذیرفته نشده باشد.

اگر پس از اعمال این حفاظت‌ها هیچ superAdmin فعالی باقی نماند، ابزار با **خروج ۲** متوقف می‌شود و app/worker را روشن نمی‌کند. مرحلهٔ `security-applied` پیش از این خروج پایدار شده است. هویت کارکنان را در env محافظت‌شده بررسی کنید و با فرمان مالک `provision-staff.sh --rotate-passwords --reactivate=STABLE_ENV_KEY` فقط حساب مشخص را بازیابی کنید؛ مقدار password باید صریحاً در همان رکورد env وجود داشته باشد. پس از رفع علت، همان restore را با `--resume` ادامه دهید. این ادامه دادهٔ تاریخی را دوباره وارد نمی‌کند و رمز/MFA تازهٔ بازیابی‌شده را بازنویسی نمی‌کند. شکست این gate با فعال‌کردن خودکار حساب تاریخی پوشانده نمی‌شود.

اگر authenticator بعد از snapshot عوض شده و دستگاه قدیمی در دسترس نیست، گزینه صریح `--reset-mfa=STABLE_ENV_KEY` همراه با `--rotate-passwords` و یک password تازه در همان رکورد env لازم است؛ حساب غیرفعال به `--reactivate` متناظر نیز نیاز دارد. این عملیات مالک، MFA قبلی و همه نشست‌ها/challengeهای قبلی را باطل می‌کند و ورود بعدی را به ثبت MFA جدید محدود می‌کند. جزئیات و محدودیت‌های هویت در [راهنمای کارکنان env](STAFF-ENV.fa.md) و [راهنمای امنیت بازیابی](RESTORE-SECURITY.fa.md) آمده‌اند.

## ۶. بازیابی کامل روی Ubuntu خالی با یک دستور

دو فایل خصوصی آرشیو و کلید مستقل را در میزبان تازه قرار دهید. از بسته کد بررسی‌شده، wrapper بازیابی را اجرا کنید:

```bash
sudo bash scripts/recover-ubuntu.sh \
  --new-host \
  --file /secure/website.tar.age \
  --identity /secure/website-recovery-key.txt \
  --app-dir /var/www/idealmakoo-v2 \
  --project-name idealmakoo
```

دامنه، تنظیمات برنامه، حساب‌ها، credentialها و کلیدها از **همان آرشیو تأییدشده** برمی‌گردند. wrapper ابتدا age/Python را از مخزن Ubuntu آماده، آرشیو را خصوصی رمزگشایی و اصالتش را کنترل می‌کند؛ سپس نصاب داخل **سورس تأییدشده همان بکاپ** را اجرا می‌کند. Docker/Compose و imageهای لازم روی میزبان آماده می‌شوند، DB بدون seed مجدد از snapshot بازمی‌گردد، رسانه و integrationها و TLS منتقل و کنترل بایتی می‌شوند، grants بازسازی و دفتر replay می‌شود. حساب‌های موجود، رمزها، MFA و محتوای ویرایش‌شده با seed کارخانه بازنویسی نمی‌شوند.

اگر رمز اولیه bootstrap را پس از راه‌اندازی از env حذف کرده‌اید، در بازیابی نیز خالی می‌ماند؛ رمز موجود DB حفظ می‌شود و نصاب رمز اولیه جایگزین تولید نمی‌کند. نبود کلید اصلی نشست/MFA یا credentialهای لازم DB در payload تأییدشده خطاست و با کلید تازه جایگزین نمی‌شود. باطل‌سازی نشست‌ها و challengeهای قدیمی پیش از شروع برنامه انجام می‌شود. میزبان تازه فقط وضعیت حساب‌های موجود در آرشیو را می‌شناسد؛ غیرفعال‌سازی‌ها یا تغییر رمز/نقش بعد از آن بکاپ بدون یک منبع جاری مستقل قابل استنتاج نیستند. قبل از اتصال عمومی، کارکنان را با env جاری و فرمان مالک بررسی و در صورت نیاز صریحاً همگام کنید. برای حذف داده‌های بعد از snapshot، آخرین دفتر مستقل را طبق بخش بعد همراه داشته باشید.

ریشه نصب باید خالی/ناموجود باشد. هیچ کانتینر یا Volume قبلی با نام پروژه هدف مجاز نیست. این حالت ابزار حذف یا بازنویسی نصب موجود نیست؛ برای جلوگیری از تداخل، مسیر و نام پروژه تازه انتخاب کنید. کلید خارجی با مجوز ۶۰۰ در shared نصب بازیابی‌شده قرار می‌گیرد و بکاپ بعدی همچنان با همان هویت قابل بازیابی است.

برای انتقال آگاهانه دامنه/پورت، گزینه‌های `--domain`، `--email`، `--http-port` و `--https-port` در همین فرمان قابل استفاده‌اند. برای تمرین HTTP ایزوله:

```bash
sudo bash scripts/recover-ubuntu.sh --new-host \
  --file /secure/website.tar.age --identity /secure/website-recovery-key.txt \
  --app-dir /var/www/idealmakoo-restore --project-name idealmakoo_restore \
  --domain 127.0.0.1 --http --http-port 8081 --https-port 8444 --bind-ip 127.0.0.1
```

در حالت HTTP نیز دو پورت Compose باید آزاد باشند؛ پورت HTTPS در این حالت استفاده عمومی ندارد ولی publish می‌شود. گزینه‌های حذف آنتی‌ویروس، حذف timer یا صرف‌نظر صریح از بررسی منابع فقط برای شرایط بررسی‌شده در دسترس‌اند؛ پیش‌فرض‌ها فعال می‌مانند.

### ارسال‌های معوق و دفتر حذف

بازیابی میزبان تازه به‌طور پیش‌فرض `NOTIFICATIONS_MODE=disabled` و `CRM_CAMPAIGNS_ENABLED=false` قرار می‌دهد. صف‌ها و credentialها حفظ می‌شوند ولی ارسال بیرونی معوق شروع نمی‌شود. پس از بررسی صف و رضایت‌ها، مقادیر مناسب را در محیط فعال و app/worker را recreate کنید. برای بازیابی عملیاتی که ارسال‌ها از قبل بررسی شده‌اند، `--activate-outbound` حفظ تنظیمات اصلی آرشیو را صریح می‌کند.

بکاپ قدیمی فقط تاریخچه حذف تا زمان خودش را دارد. **اگر پس از آن بکاپ حذف داده انجام شده، آخرین دفتر مستقل معتبر را نیز بازیابی کنید**:

```bash
sudo bash scripts/recover-ubuntu.sh --new-host \
  --file /secure/website.tar.age --identity /secure/website-recovery-key.txt \
  --latest-ledger /secure/latest-privacy-ledger \
  --app-dir /var/www/idealmakoo-v2 --project-name idealmakoo
```

مسیر دفتر مستقل باید حاوی `identity.json` و `erasures.jsonl` معتبر باشد. اگر دفتر جاری هدف از قبل وجود داشته باشد، همان دفتر حفظ و بررسی می‌شود؛ archive یا گزینه latest اجازه عقب‌بردن آن را نمی‌دهد. نبود هیچ دفتر روی **میزبان صریحاً تازه** اجازه استفاده از کپی امضاشده آرشیو را می‌دهد. بازیابی معمولی همیشه دفتر جاری مستقل را حفظ می‌کند. خطای هویت، شکست زنجیره یا anchor ناسازگار با ساخت دفتر جدید پوشانده نمی‌شود.

### خروجی سازگار از دفتر جاری و انتقال به میزبان تازه

اگر آرشیو انتخاب‌شده قدیمی است، دفتر حذف جدید را از یک **بکاپ کامل و سازگارِ جدیدتر** استخراج کنید. کپی مستقیم `erasures.jsonl` هنگام نوشتن برنامه کافی نیست. دستور زیر همان ابزار اصلی بکاپ را اجرا می‌کند؛ ابزار، نویسنده‌ها را متوقف و وضعیت DB، فایل‌ها و دفتر را در یک snapshot سازگار ثبت می‌کند و سپس سرویس‌ها را به حالت قبلی برمی‌گرداند. برای این عملیات، فضای آزاد و وقفهٔ لازم برای snapshot بکاپ را در نظر بگیرید. اگر همین بکاپ جدید را از قبل با ابزار اصلی تهیه کرده‌اید، می‌توانید مسیر همان آرشیو ثابت را در مراحل بررسی و استخراج استفاده کنید.

این بلوک را روی **میزبان مبدأ** و با دسترسی مجاز مدیریت اجرا کنید. مسیر release در آغاز ثابت می‌شود و staging رمزگشایی‌شده با خروج از همان shell پاک می‌شود:

```bash
sudo bash <<'BASH'
set -Eeuo pipefail
umask 077
release_dir="$(readlink -f /var/www/idealmakoo-v2/current)"
current_identity=/var/www/idealmakoo-v2/shared/backup-identity.txt
ledger_export_dir="$(mktemp -d /var/www/idealmakoo-v2/shared/ledger-export.XXXXXXXX)"
bash "$release_dir/scripts/backup.sh" \
  --output "$ledger_export_dir/current-ledger-source.tar.age"
ledger_verify_dir="$(mktemp -d "$ledger_export_dir/.verify.XXXXXXXX")"
trap 'rm -rf -- "$ledger_verify_dir"' EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
python3 "$release_dir/deploy/backup-archive.py" preflight-decryption \
  "$ledger_export_dir/current-ledger-source.tar.age" "$ledger_verify_dir"
age --decrypt --identity "$current_identity" \
  --output "$ledger_verify_dir/archive.tar" \
  "$ledger_export_dir/current-ledger-source.tar.age"
mkdir -m 700 "$ledger_verify_dir/verified" "$ledger_export_dir/latest-ledger"
python3 "$release_dir/deploy/backup-archive.py" unpack \
  "$ledger_verify_dir/archive.tar" "$ledger_verify_dir/verified" \
  "$current_identity" >/dev/null
python3 "$release_dir/deploy/backup-archive.py" restore-policy \
  "$ledger_verify_dir/verified" "$current_identity" 0
python3 "$release_dir/deploy/backup-archive.py" extract-storage \
  "$ledger_verify_dir/verified/privacy-ledger.tar" \
  "$ledger_export_dir/latest-ledger"
install -m 600 "$ledger_verify_dir/verified/privacy-ledger.tar" \
  "$ledger_export_dir/latest-ledger.tar"
(cd "$ledger_export_dir" && sha256sum latest-ledger.tar > latest-ledger.tar.sha256)
printf 'Protected ledger export: %s\n' "$ledger_export_dir"
BASH
```

اگر نصب از override به نام `IDEALMAKOO_BACKUP_IDENTITY` استفاده می‌کند، `current_identity` را به **کلید واقعی همین بکاپ جدید** تغییر دهید؛ کلید را در خروجی چاپ نکنید. موفقیت `unpack` برای فرمت ۳، HMAC با هویت مستقل age و checksum تمام payloadها را بررسی می‌کند؛ `restore-policy ... 0` نیز فرمت قدیمیِ بدون احراز HMAC را رد می‌کند. رمزنگاری به recipient age به‌تنهایی هویت فرستنده را اثبات نمی‌کند و فایل SHA256 فقط سلامت بایت‌ها را می‌سنجد. آرشیو باید از نصب/ذخیره‌سازی مورد اعتماد آمده باشد و کلید مستقل و مسیر انتقال نیز تحت کنترل شما باشند.

برای انتقال، `SOURCE` و نام دقیق مسیر چاپ‌شدهٔ `ledger-export.EXACT` را جایگزین کنید. حساب SSH باید از قبل مجاز به خواندن این فایل‌ها با `sudo -n` باشد؛ کلید میزبان SSH را از مسیر معتبر بررسی و در `known_hosts` ثبت کرده باشید. در shell خصوصیِ **میزبان بازیابی** اجرا کنید:

```bash
set -Eeuo pipefail
umask 077
ledger_receive_dir="$(mktemp -d "$PWD/latest-ledger-kit.XXXXXXXX")"
ssh -T -oBatchMode=yes -oStrictHostKeyChecking=yes ops@SOURCE \
  'sudo -n cat -- /var/www/idealmakoo-v2/shared/ledger-export.EXACT/latest-ledger.tar' \
  > "$ledger_receive_dir/latest-ledger.tar"
ssh -T -oBatchMode=yes -oStrictHostKeyChecking=yes ops@SOURCE \
  'sudo -n cat -- /var/www/idealmakoo-v2/shared/ledger-export.EXACT/latest-ledger.tar.sha256' \
  > "$ledger_receive_dir/latest-ledger.tar.sha256"
(cd "$ledger_receive_dir" && sha256sum -c latest-ledger.tar.sha256)
mkdir -m 700 "$ledger_receive_dir/latest-ledger"
python3 /path/to/trusted-release/deploy/backup-archive.py extract-storage \
  "$ledger_receive_dir/latest-ledger.tar" "$ledger_receive_dir/latest-ledger"
sudo bash /path/to/trusted-release/scripts/recover-ubuntu.sh --new-host \
  --file /secure-export/OLDER-selected-website.tar.age \
  --identity /secure-export/OLDER-archive-recovery-key.txt \
  --latest-ledger "$ledger_receive_dir/latest-ledger" \
  --app-dir /var/www/idealmakoo-v2 --project-name idealmakoo
```

مسیر `/path/to/trusted-release` باید سورس بررسی‌شدهٔ ابزار بازیابی باشد. `extract-storage` به‌تنهایی فقط استخراج امن فایل است؛ احراز آرشیو در مبدأ و بررسی زنجیره/anchor در ابزار بازیابی هر دو لازم‌اند. آرشیو قدیمیِ انتخاب‌شده، DB، رسانه، تنظیمات و سورس بازیابی را تعیین می‌کند؛ خروجی جدید فقط دفتر امضاشدهٔ جدیدتر را تأمین می‌کند. پس از چرخش کلید، هویت لازم برای بازکردن آرشیو قدیمی ممکن است با کلید بکاپ جدید فرق کند.

این خروجی **کلید امضای دفتر حذف** را هم در بر دارد: پوشه‌ها باید ۷۰۰ و فایل‌ها ۶۰۰ باشند، به فضای عمومی وب منتقل نشوند و پس از انتقال/نگهداشت طبق سیاست خصوصی سازمان مدیریت شوند. staging رمزگشایی‌شدهٔ کامل شامل دیگر اسرار هم هست و trap بالا آن را پس از خروج پاک می‌کند. دفتر استخراج‌شده فقط حذف‌ها تا نقطهٔ snapshot جدید را پوشش می‌دهد؛ اگر پس از آن حذف دیگری ثبت شد، زمان انتقال نهایی را هماهنگ کنید یا snapshot و خروجی تازه بگیرید. نگهداشت فایل قدیمی با نام «latest» آن را به دفتر جاری تبدیل نمی‌کند.

مجموعهٔ معتبر migration باید از **سورس واقعی همان آرشیو و ledger همان دیتابیس** خوانده شود؛ شمارهٔ آخر فایل، تعداد migrationها نیست و بعضی شماره‌های تاریخی ممکن است وجود نداشته باشند. بررسی و drill نام/checksum تمام فایل‌ها و ساختار بازیابی‌شده را تطبیق می‌دهند. migrationهای تازهٔ نسخهٔ ۲.۲ به مجموعه اضافه می‌شوند و checksum فایل‌های تاریخی تغییر نمی‌کند. آرشیو نسخهٔ دیگر با سورس و ledger خودش بررسی شود؛ افزودن دستی ردیف migration یا تغییر checksum برای عبور از ناسازگاری مجاز نیست.

## ۷. تشخیص خطا و نگهداشت

```bash
sudo bash /var/www/idealmakoo-v2/current/scripts/doctor.sh
sudo bash /var/www/idealmakoo-v2/current/scripts/check-health.sh 240
```

doctor به‌صورت خواندنی، صحت محیط، وضعیت سرویس‌ها، heartbeat، اسکنر و gate دفتر را بررسی می‌کند و env، argv خصوصی کانتینر یا ردیف‌های DB را چاپ نمی‌کند. نصاب در failure مرحله دقیق و مسیر diagnosis را گزارش می‌کند. اگر build یا شبکه مخزن خطا دهد، علت را رفع و همان نصب را با محیط موجود تکرار کنید؛ کلیدها و Volumeهای موجود حفظ می‌شوند. شکست بعد از مهاجرت، دلیل اجرای نسخه قدیمی روی schema نامشخص نیست؛ از safety backup و مسیر بازیابی نسخه متناظر استفاده کنید.

timer روزانه بکاپ باقی می‌ماند؛ انتقال به مقصد دوم و نگهداشت تعداد نسخه‌ها باید با مقصد و ظرفیت واقعی تنظیم شود. حذف خودکار بکاپ قدیمی انجام نمی‌شود. قبل از ارتقا، پس از تغییرات زیرساخت و در بازه منظم، restore drill و تمرین میزبان تازه را اجرا و نتیجه واقعی را ثبت کنید. معیار پذیرش، فایل ساخته‌شده به‌تنهایی نیست؛ داده/فایل و کنترل دسترسی بازیابی‌شده باید gateهای همین ابزار را بگذرانند.

آزمون‌های همراه سورس در `tests/deployment_complete_backup_test.py` و `tests/deployment_bootstrap_test.py`، رمزنگاری واقعی age، کلید اشتباه، تغییر manifest/payload، source/schema mismatch، مسیر خروج، symlink، کلید با مجوز ناامن، خطای داده/sequence، تطابق بایت فایل، اولویت محیط و حفظ رمز را می‌سنجند. `tests/deployment_failure_cleanup_test.py` مسیر واقعی Bash و handlerهای خروج را با Compose شبیه‌سازی‌شده اجرا می‌کند: شکست readiness پس از روشن‌شدن سرویس، شکست بکاپ اولیه، توقف ناقص Docker، سیگنال TERM و حفظ Volumeها بررسی می‌شوند. `tests/deployment_pending_restore_test.py` علاوه بر فایل خصوصی واقعی، اسکریپت restore و adapter نتیجهٔ owner را با جایگزین محدود Docker/DB اجرا می‌کند: شکست پیش از reconciliation، قطع پس از حذف DB، حفظ snapshot اولیه، رد تلاش عادی/آرشیو متفاوت، شکست health، خروج ۲ و ادامه پس از بازیابی حساب مدیر، بدون بازنویسی credential تازه آزموده می‌شوند. منطق SQL reconciliation در `tests/server-restore-security.pg.mjs` روی PostgreSQL واقعی آزموده می‌شود. در شواهد تاریخی v34، زیرمجموعهٔ پاک‌سازی restore پس از اصلاح با ۲۲ مورد موفق بررسی شده بود: خطای حذف فایل موقت یا دیتابیس تمرین، کد خطای اصلی یا پایان ناشی از سیگنال را نمی‌پوشاند و checkpoint موفقیت‌نیافته حذف نمی‌شود. [دامنه و شاهد دقیق این بررسی](VERIFICATION.fa.md) جدا از پذیرش بازیابی زیرساخت است. این آزمون‌ها جای اجرای واقعی Docker نیستند. نتیجه نصب VM و restore واقعی از گزارش همان اجرای تحویل خوانده می‌شود؛ این راهنما نتیجه اجرا را از پیش موفق فرض نمی‌کند.

# خروجی قابل تحویل Lighthouse برای صفحات خصوصی

این راهنما مربوط به `scripts/export-private-lighthouse-evidence.mjs` و قالب `private-lighthouse-evidence-v1` در نسخهٔ ۲.۱ است. نسخهٔ قرارداد اثبات ورود در هر تلاش با `authenticationProofVersion: 2` ثبت می‌شود و شاهد قبل و بعد از سنجش را لازم دارد. ابزار، گزارش‌های موجودِ یک اجرای احراز هویت‌شده را به شواهد قابل تحویل تبدیل می‌کند. خودش مرورگر باز نمی‌کند، وارد حساب نمی‌شود، دادهٔ برنامه را تغییر نمی‌دهد و امتیازی تولید یا اصلاح نمی‌کند.

اجرای مرورگر در ابزار جداگانهٔ `scripts/audit-private-lighthouse.mjs` انجام می‌شود. وضعیت واقعی آزمون‌ها و محدودیت‌های پذیرش در [گزارش بررسی نسخه](VERIFICATION.fa.md) ثبت می‌شود. راهنمای حاضر به‌تنهایی، مدرک اجرای موفق آزمون روی سایت نیست.

## اجرای فرمان خروجی

از ریشهٔ همان نسخهٔ پروژه، پس از نصب وابستگی‌های قفل‌شده و توقف اجرای در حال نوشتن گزارش، فرمان زیر را اجرا کنید. مسیرها نمونه‌اند؛ `--run` باید پوشهٔ گزارش خام خصوصیِ همان اجرا باشد. والد مقصد باید وجود داشته باشد و خود پوشهٔ مقصد نباید از قبل وجود داشته باشد.

```bash
mkdir -p /tmp/idealmakoo-audit-delivery
node scripts/export-private-lighthouse-evidence.mjs \
  --run /tmp/idealmakoo-lighthouse-evidence/protected-mobile \
  --output /tmp/idealmakoo-audit-delivery/protected-mobile-export
```

ابزار فقط همین دو آرگومان خط فرمان را می‌پذیرد. نیازی به env برنامه، اتصال دیتابیس، کلید MFA، رمز یا کوکی ندارد. شناسهٔ مسیرهای مجاز را از `src/lib/routes.ts` و شناسه‌های audit و خطا را از سورس Lighthouse نصب‌شده و اجراکنندهٔ خصوصی، شامل `scripts/lib/private-audit-session.mjs`، می‌خواند؛ ماژول برنامه یا مرورگر را اجرا نمی‌کند. نسخهٔ Lighthouse گزارش خام باید با وابستگی نصب‌شده یکسان باشد.

مقصد با سطح دسترسی `0700` و فایل‌ها با `0600` ساخته می‌شوند. خروجی ابتدا در پوشهٔ موقت اختصاصی آماده و پس از بررسی انسجام ورودی به مقصد تازه منتقل می‌شود. ابزار مقصد موجود را بازنویسی نمی‌کند. برای اجرای مجدد، نام مقصد تازه بدهید.

## چه چیزهایی در خروجی قرار دارد؟

| فایل | محتوا |
| --- | --- |
| `manifest.json` | نسخهٔ قالب، شناسهٔ build، نسخهٔ برنامه و مرورگر و Lighthouse، پیکربندی مجاز، اثرانگشت پیکربندی و محدودهٔ سناریوها |
| `inventory.json` | فهرست کارهای برنامه‌ریزی‌شده با برچسب مسیر ثبت‌شده، زبان، نقش، نوع سناریو و دستگاه؛ شناسهٔ درخواست مشتری در آن نیست |
| `summary.json` | تعداد کارهای انجام‌شده، موفق، خطادار، timeout و باقی‌مانده؛ آخرین نتیجهٔ هر کار و تمام تلاش‌های قبلی |
| `summary.csv` | جدول بازساخته‌شده از فیلدهای مجاز خروجی؛ CSV خام ورودی کپی نمی‌شود |
| `audit-part-0001.json` و بخش‌های بعدی | نتیجهٔ هر تلاش و تمام auditهای موجود، با جزئیات عددی و ساختاری محدودشده |
| `EXPORT.json` | زمان خروجی، حدود اندازه، فهرست بخش‌ها و اندازه و SHA-256 هر بخش، اثرانگشت manifest و inventory و summary ورودی |

هر بخش audit حداکثر **۳۲ MiB، برابر با ۳۳٬۵۵۴٬۴۳۲ بایت** است؛ اندازه شامل ساختار JSON و تمام نتایج آن بخش می‌شود. اگر یک تلاش حتی پس از اعمال سیاست محدودسازی، در این سقف جا نشود، خروجی با خطا متوقف می‌شود. نتیجه‌ای برای جا شدن در سقف حذف نمی‌شود. سقف خواندن هر LHR خام ۱۲۸ MiB و هر فایل JSON مدیریتی ورودی ۳۲ MiB است.

هر رکورد summary یک اشاره‌گر `evidence` دارد:

```json
{
  "filename": "audit-part-0001.json",
  "index": 0,
  "rawReportSha256": "<SHA-256 گزارش خام همان تلاش>"
}
```

`index` شمارهٔ صفرمبنا در آرایهٔ `attempts` همان بخش است. `rawReportSha256` اثرانگشت بایت‌های فایل خام است، نه اثرانگشت متن خلاصه‌شده. این اشاره‌گر، فایل خام را وارد بستهٔ تحویلی نمی‌کند. هنگام نیاز به بررسی جزئیات حذف‌شده، مسئول مجاز می‌تواند گزارش خام نگهداری‌شده در محل خصوصی را با همان اثرانگشت تطبیق دهد.

## سیاست حذف اطلاعات خصوصی

تبدیل با فهرست مجاز فیلدها انجام می‌شود؛ ابزار کل اشیای خام را کپی و سپس پاک‌سازی نمی‌کند. در تمام فایل‌های خروجی بخش `omissions` این سیاست را توضیح می‌دهد.

موارد زیر وارد خروجی نمی‌شوند:

- فایل خام LHR، screenshot، filmstrip، تصویر base64 و محتوای باینری.
- کوکی، هدر درخواست یا پاسخ، رمز، کلید، Authorization، شناسهٔ نشست، شناسهٔ کاربر یا شناسهٔ درخواست مشتری.
- متن DOM، snippet، برچسب فیلد یا کاربر، مقدار attribute، `id` و `class` عناصر.
- URL خام، query و fragment، مسیر منابع شبکه و نام فایل‌های خصوصی.
- عنوان، توضیح، display value و متن آزاد خطا و هشدارِ برگرفته از گزارش خام؛ این فیلدها ممکن است اطلاعات صفحهٔ خصوصی داشته باشند.
- مسیر پروفایل Chrome، مسیر فایل اجرایی و گزینه‌های ناشناختهٔ Chrome؛ تعداد گزینه‌های حذف‌شده و اثرانگشت مجموعهٔ اصلی نگهداری می‌شود.

آنچه حفظ می‌شود شامل امتیاز و حالت هر audit، مقدار و واحد عددی شناخته‌شده، امتیاز دسته‌ها، metricها، زمان اجرا، وضعیت تلاش، کد مجاز خطا، وجود خطا و تعداد هشدارهاست. حتی audit مربوط به screenshot، نتیجه و امتیاز/حالت خود را حفظ می‌کند؛ فقط دادهٔ تصویر آن حذف می‌شود. شناسهٔ audit ناشناخته به نام مستعار مشتق از SHA-256 تبدیل می‌شود تا متن ناشناخته وارد بسته نشود و نتیجهٔ آن audit باقی بماند.

تنظیم رندر مرورگر نیز حفظ می‌شود: `--use-gl=angle` و `--use-angle=swiftshader` در فهرست مجاز `chromeFlags` هستند و `graphicsMode` فقط یکی از مقادیر ثابت `browser-default`، `webgl-software-fallback` یا `swiftshader-driver` را می‌پذیرد. اثرانگشت کل پرچم‌های اولیه در `chromeFlagsSha256` باقی می‌ماند. حالت درایور SwiftShader همچنان پردازش نرم‌افزاری روی CPU است و گزارش، آن را به GPU فیزیکی تعبیر نمی‌کند؛ حالت تازه‌ای برای گزارش‌های قدیمی استنباط یا جعل نمی‌شود.

برای selector فقط نام عناصر استاندارد HTML/SVG، رابطهٔ عناصر و pseudo-classهای مکانی عددی مجازند. مثلاً selector زیر:

```text
body > main#private-account > div.customer-name > input[data-email="private"]:nth-child(2)
```

به این ساختار تبدیل می‌شود:

```text
body > main > div > input:nth-child(2)
```

selector دارای ساختار پشتیبانی‌نشده، escape، تابع نامجاز یا نام عنصر سفارشی، حذف و با `selectorOmitted` مشخص می‌شود. selector ساده‌شده ممکن است به چند عنصر اشاره کند؛ برای یافتن دقیق یک عنصر، گزارش خام خصوصی لازم است.

جزئیات هر audit به حداکثر ۲۰ عضو هر آرایه، عمق ۸ و ۲۰۰۰ گره محدود می‌شود. عددهای مربوط به اندازه، زمان، بایت، کنتراست، موقعیت و شمارش فنی در فهرست مجاز قرار دارند. دادهٔ تجاری یا فیلد عددی دلخواه، فقط به‌دلیل عدد بودن کپی نمی‌شود. حذف جزئیات با `omittedItems`، `omittedFields` یا دلیل صریح حذف مشخص می‌شود.

## تفسیر ورود، نقش و موفقیت

نتیجهٔ `completed` فقط وقتی قابل خروجی است که اجراکننده گزارش کرده باشد:

- پیش از سنجش، هویت و نقش نشست، دسترسی لازم MFA کارکنان و باقی‌بودن زمان معتبر نشست بررسی شده و هر سه کنترل `preSessionRoleVerified`، `preStaffMfaVerified` و `preSessionFreshnessVerified` درست باشند.
- `authVerified` درست و نقش مشاهده‌شده برابر نقش همان کار ثبت‌شده است.
- وضعیت HTTP برابر ۲۰۰ است و اثبات جداگانهٔ نقش و وضعیت HTTP درست است.
- پوسته و محتوای صفحه آماده است؛ زبان سند و مسیر نهایی درست است.
- شرط MFA کارکنان، بارگیری لازم محیط کار و کنترل‌های سناریوی درخواست متعلق به مشتری برقرار است.
- صفحهٔ خصوصی `noindex` دارد؛ خطای API یا خطای اجرایی مرورگر مشاهده نشده است.
- LHR معتبر همان نسخه وجود دارد و خودش `runtimeError` ندارد.

فیلدهای `checks.sessionRole` و `checks.httpStatus` به‌ترتیب **نقش واقعی مشاهده‌شده** و **عدد وضعیت HTTP** هستند. فیلدهای `sessionRoleVerified` و `httpStatusVerified` نتیجهٔ بولی بررسی را نگه می‌دارند. شمار خطاهای API و صفحه نیز جداگانه در خروجی می‌آید؛ مسیرهای دارای اطلاعات خصوصی و متن خطا حذف می‌شوند.

برای سناریوی مشتری، شرط MFA کارکنان و بارگیری workspace کارکنان قابل اعمال نیست. مقدار درستِ این کنترل‌های شرطی، ادعای فعال بودن MFA مشتری یا بازدید مشتری از پنل کارکنان ایجاد نمی‌کند. سناریوهای عادی نیز کنترل درخواست متعلق به مشتری را به‌صورت شرطی می‌گذرانند؛ فقط رکورد دارای `kind: owned-request-detail` شاهد آن سناریوی مشخص است.

### شاهد قبل از سنجش و تمدید واقعی ورود

رکورد `preflight` فقط فیلدهای زیر را نگه می‌دارد. شناسهٔ حساب و نشست، مقدار کوکی، هدر، متن پاسخ و اطلاعات محیط کار وارد خروجی نمی‌شوند.

| فیلد | معنای شاهد |
| --- | --- |
| `sessionRole` | نقش شناخته‌شدهٔ مشاهده‌شده؛ اگر هنوز معلوم نشده باشد `null` |
| `httpStatus` | وضعیت واقعی خواندن نشست؛ موفقیت HTTP به‌تنهایی به معنی وارد بودن نیست |
| `workspaceStatus` | وضعیت واقعی خواندن محیط کار کارکنان؛ برای مشتری `null` |
| `securityStatus` | وضعیت واقعی خواندن اطلاعات امنیت حساب برای زمان انقضای نشست جاری |
| `expiresAt` | زمان UTC انقضای همان نشست؛ اگر به دست نیامده باشد `null` |
| `observedAt` | زمان UTC ثبت بررسی قبل از سنجش |

برای نتیجهٔ موفق، نقش باید با inventory یکسان باشد، وضعیت نشست و امنیت حساب ۲۰۰ باشد و کارکنان شاهد workspace با وضعیت ۲۰۰ داشته باشند. انقضای نشست باید پس از زمان مشاهده و، اگر ثبت شده، پس از پایان همان تلاش باشد. زمان شاهد پیش از سنجش نیز نباید بعد از `fetchTime` ثبت‌شدهٔ Lighthouse باشد.

در اجرای طولانی، نزدیک شدن به انقضای مطلقِ یک نشست هنوز معتبر می‌تواند باعث ورود واقعی مجدد، خارج از سنجش صفحه، شود. شاهد `renewal` فقط علت ثابت `absolute-expiry-approaching`، زمان‌های UTC شروع و پایان، انقضای قبلی و جدید و نتیجهٔ بولی `success` را نگه می‌دارد. نتیجهٔ `completed` با شاهد تمدید ناقص، ناموفق، دارای علت ناشناخته یا زمان انقضای متفاوت از شاهد نهایی `preflight` پذیرفته نمی‌شود. این داده‌ها ادعای تغییر عمر نشست روی سرور ایجاد نمی‌کنند؛ ورود مجدد باید با جریان واقعی رمز و MFA انجام شده باشد.

از دست رفتن غیرمنتظرهٔ نشست یا مجوز، خطای آزمون است. مقدار `user: null` از API نشست یا پاسخ ۴۰۱/۴۰۳ نباید با ورود دوبارهٔ پنهان به نتیجهٔ موفق تبدیل شود. کنترل‌های قبل و بعد از سنجش هر دو در گزارش باقی می‌مانند. در نتیجهٔ ناموفق، شاهد ناقص، فیلدهای `null` و `renewal.success: false` حفظ می‌شوند؛ اگر اتصال حتی اجازهٔ دریافت شاهد را نداده باشد، نبود `preflight` مجاز است.

رفتار زمان انقضا از [تنظیمات سرور](../src/server/config.ts) و [احراز هویت](../src/server/auth.ts) می‌آید: مقدار پیش‌فرض عدم فعالیت ۶۰ دقیقه و انقضای مطلق ۲۴ ساعت است و env می‌تواند آن‌ها را تغییر دهد. درخواست معتبر، زمان آخرین فعالیت را به‌روز می‌کند؛ تاریخ انقضای مطلق تمدید نمی‌شود. MFA بازهٔ زمانی مستقل دیگری در نشست ندارد؛ وضعیت تأیید نشست و فعال بودن کنونی MFA حساب با هم بررسی می‌شوند. گزارش خام امنیت حساب، شامل شناسه‌های نشست، باید خصوصی باقی بماند.

اجرای قدیمی که فقط شاهد پس از سنجش دارد با افزودن دستی مقدار درست به کنترل‌های جدید معتبر نمی‌شود. برای داشتن شاهد کامل، سناریوی مربوط باید واقعاً با اجراکنندهٔ جدید سنجیده شود.

صفحات حساب و مدیریت باید خصوصی و `noindex` بمانند. نتیجهٔ دستهٔ SEO همان نتیجهٔ واقعی Lighthouse است؛ ابزار برای بالا بردن نمره، noindex یا قواعد ورود را تغییر نمی‌دهد.

## محدودهٔ پوشش را چگونه بخوانیم؟

`scenarioCoverage` در manifest، summary و EXPORT، نقش‌ها، زبان‌ها، دستگاه‌ها، تعداد مسیرهای خصوصی ثبت‌شده، مسیرهای زبانی حاضر در inventory و شمار هر نوع سناریو را ثبت می‌کند. تعداد پیش‌فرض یا امتیاز پیش‌فرض برای یک اجرای انجام‌نشده ساخته نمی‌شود؛ فهرست همان اجرای ورودی مرجع است.

`coverageComplete: true` یعنی برای تمام کارهای inventory حداقل یک نتیجه ثبت شده است. ممکن است بعضی نتیجه‌ها error یا timeout باشند. برای موفقیت تمام ناوبری‌های برنامه‌ریزی‌شده، علاوه بر این مقدار باید `allInventoriedNavigationsSucceeded: true`، `errors: 0` و `timeouts: 0` بررسی شود.

فهرست خصوصی، مسیرهای ثبت‌شده را با نقش اصلی و سناریوهای اضافیِ صریحاً انتخاب‌شده بررسی می‌کند. این کار معادل اجرای تمام ترکیب‌های نقش × مسیر × زبان × نوع داده، تمام CRUDها یا تمام گردش‌های کاری نیست. خروجی همیشه این حدود را روشن ثبت می‌کند:

```json
{
  "allRoleRouteCombinationsTested": false,
  "workflowActionsMeasured": false
}
```

اثبات ذخیره‌سازی، مجوز تغییر داده، تعارض و تراکنش، نصب، پشتیبان‌گیری و بازیابی باید در آزمون‌های مربوط به خودشان ارزیابی شوند. گزارش Lighthouse شاهد ناوبری و کیفیت صفحه در سناریوهای ثبت‌شده است.

## خطا، timeout و اجرای نیمه‌تمام

خروجی از یک اجرای متوقف‌شده یا نیمه‌تمام مجاز است، به‌شرط آنکه فایل‌های مدیریتی آن منسجم باشند. همهٔ تلاش‌های قبلی حفظ می‌شوند؛ آخرین تلاش هر کار شمارش نتیجهٔ فعلی را تعیین می‌کند. کارهای انجام‌نشده در `pending` می‌مانند.

اگر child گزارش خام را نوشته باشد اما پیش از ثبت اشاره‌گر در result قطع شود، ابزار فقط نام دقیق و قابل محاسبهٔ همان job/attempt را بررسی می‌کند. گزارش موجود و اثرانگشتش حفظ می‌شوند. گزارش خام ناقص و غیرقابل parse برای تلاش ناموفق با `rawReportInvalid` و اثرانگشت بایت‌های موجود معرفی می‌شود. نبود گزارش با `rawReportMissing` مشخص است. این موارد به نتیجهٔ موفق تبدیل نمی‌شوند.

کدهای شناخته‌شدهٔ Lighthouse و اجراکننده حفظ می‌شوند؛ متن آزاد خطا با `textOmitted: true` حذف می‌شود. کد ناشناخته به `UNCLASSIFIED` تبدیل می‌شود. پسوند عددی وضعیت HTTP فقط برای پیشوند خطای ثابتِ موجود در سورس اجراکننده مجاز است. برای ریشه‌یابی نیازمند متن آزاد، مسئول مجاز باید به شواهد خام خصوصی مراجعه کند.

| کد خروجی ابزار | اقدام |
| --- | --- |
| `OUTPUT_ALREADY_EXISTS` | مقصد تازه انتخاب کنید؛ خروجی قبلی بازنویسی نشده است |
| `LIGHTHOUSE_VERSION_MISMATCH` یا `RAW_LIGHTHOUSE_VERSION_MISMATCH` | وابستگی قفل‌شدهٔ مربوط به همان اجرای گزارش را استفاده کنید |
| `COMPLETED_PRIVATE_AUDIT_WITHOUT_AUTH_PROOF` | نتیجهٔ موفق فاقد یکی از کنترل‌های لازم است؛ علت اجرا را بررسی کنید، دادهٔ شاهد را دستی موفق نکنید |
| `COMPLETED_PRIVATE_AUDIT_WITHOUT_PREFLIGHT_PROOF` | شاهد قبل از سنجش، نقش، پاسخ امنیت/workspace یا زمان اعتبار نشست با موفقیت ادعاشده سازگار نیست |
| `COMPLETED_PRIVATE_AUDIT_WITH_INVALID_RENEWAL_PROOF` | ورود مجددِ ثبت‌شده ناقص یا ناموفق است، یا شاهد نشست جدید با نتیجهٔ قبل از سنجش تطبیق ندارد |
| `COMPLETED_REPORT_HAS_RUNTIME_ERROR` | summary با خطای واقعی LHR تناقض دارد |
| `SUMMARY_COUNTER_MISMATCH` یا `SUMMARY_COVERAGE_MISMATCH` | گزارش را پس از توقف کامل اجراکننده و تثبیت summary خروجی بگیرید |
| `RUN_CHANGED_DURING_EXPORT` | یکی از فایل‌های مدیریتی هنگام خروجی تغییر کرده است؛ پس از تثبیت اجرا، مقصد تازه بدهید |
| `UNSAFE_REPORT_REFERENCE` یا `ELOOP` | مرجع گزارش نامعتبر یا symlink است؛ ورودی را بررسی کنید |
| `SINGLE_ATTEMPT_EXCEEDS_PART_BOUND` | یک تلاش از سقف صریح بیشتر است؛ ابزار آن را پنهان یا حذف نکرده است |

## آزمون مستقل ابزار

از ریشهٔ پروژه:

```bash
node --test --test-isolation=none tests/private-lighthouse-export.test.mjs
```

این آزمون فقط fixtureهای موقت ساختگی می‌سازد؛ به برنامه، Chrome یا دیتابیس متصل نمی‌شود. موارد آن شامل جلوگیری از نشت متن و توکن، حفظ نتایج ناموفق و تلاش‌های قبلی، صحت اشاره‌گر و SHA-256، سقف اندازه، رد مسیر نامجاز و symlink، رد اثبات ورود ناکافی پیش و پس از سنجش، حفظ شاهد ورود مجدد واقعی و رد تمدید ناموفق، و حفظ مقصد قبلی است. نتیجهٔ آزمون ابزار جای نتیجهٔ اجرای واقعی Lighthouse را نمی‌گیرد.

برای تحویل، فقط پوشهٔ خروجی این ابزار را با بستهٔ شواهد منتشر کنید. پوشهٔ raw، فایل‌های `.lhr.json`، profile، ورودی child، فایل کنترل fixture، log خام و env احراز هویت را به بستهٔ تحویل عمومی اضافه نکنید.

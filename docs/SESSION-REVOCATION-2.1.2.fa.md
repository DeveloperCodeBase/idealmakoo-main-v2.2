# اصلاح اعتبار نشست در نسخهٔ ۲.۱.۲

## اشکال بازتولیدشده

در نسخهٔ ۲.۱.۱، اعتبار نشست در شروع درخواست بررسی می‌شد. بعضی عملیات پس از خواندن بدنهٔ درخواست، فقط فعال‌بودن حساب و مجوزهای فعلی کاربر را دوباره بررسی می‌کردند. بنابراین اگر هنگام دریافت یک فایل، کاربر از حساب خارج می‌شد یا بازنشانی رمز همهٔ نشست‌های او را لغو می‌کرد، عملیاتِ شروع‌شده هنوز می‌توانست فایل را ذخیره کند.

این مورد روی PostgreSQL واقعی بازتولید شد: آزمون، دریافت بدنهٔ multipart را پس از احراز هویت متوقف کرد، خروج یا بازنشانی رمز واقعی را انجام داد و سپس دریافت فایل را ادامه داد. نسخهٔ قبلی در هر دو حالت پاسخ `201` داد. ویرایش پروفایل و اطلاعات پرتال با هویتِ قبلاً خوانده‌شده نیز قابل انجام بود.

## تغییر انجام‌شده

هویتی که سرور از درخواست HTTP می‌سازد اکنون به همان نشستِ ایجادکنندهٔ آن متصل است. این اتصال یک `Symbol` داخلی است: با کپی استاندارد شیء در کد سرور حفظ می‌شود، در JSON خروجی وارد نمی‌شود و حاوی کوکی ورود یا توکن قابل استفاده برای ورود نیست.

هنگام بررسی دوبارهٔ مجوزها، سرور فعال‌بودن حساب، تعلق نشست به همان کاربر، لغونشدن نشست، زمان انقضا، مهلت بی‌فعالیتی و وضعیت فعلی تأیید دومرحله‌ای را بررسی می‌کند. در تراکنش‌های مربوط، قفل‌های ردیف کاربر و سپس نشست تا پایان تراکنش نگه داشته می‌شوند. این ترتیب با عملیات رمز و MFA یکسان است؛ بنابراین لغو نشست و ثبت عملیات به‌صورت ترتیبی انجام می‌شوند.

کنترل نهایی ذخیرهٔ فایل از همین بررسی استفاده می‌کند. اگر نشست در زمان خواندن فایل لغو شده باشد، پاسخ `401 / SESSION_REQUIRED` برمی‌گردد، رکورد فایل ثبت نمی‌شود، سهمیهٔ رزروشده آزاد می‌شود و فایلِ ثبت‌نشده از دیسک حذف می‌شود. ویرایش پروفایل، پرتال و فهرست‌های ذخیره‌شده نیز در محل قفل و تراکنش خود همین اعتبارسنجی را انجام می‌دهند.

کارهای پس‌زمینه، بررسی صلاحیت بازبینِ یک تأیید قبلی و تهیهٔ خروجی حریم خصوصیِ یک کاربر، هویت‌های مستقلی هستند. برای این عملیات، نشست مدیر یا ناشر به هویت شخص دیگر منتقل نمی‌شود. آزمون واقعیِ انتشار پس از خروج بازبین و خروجی گرفتن مدیر برای مشتریِ خارج‌شده، حفظ رفتار درست این مسیرها را تأیید می‌کند.

## شواهد آزمون

فایل آزمون: `tests/server-session-revalidation.pg.mjs`.

| مورد | نتیجهٔ پس از اصلاح |
| --- | --- |
| استفادهٔ مجدد از هویت و کپی آن پس از لغو، انقضا یا بی‌فعالیتی نشست | رد درخواست |
| حذف تأیید MFA از نشست زنده | حذف مجوز MFA از هویت دوباره‌خوانده‌شده |
| تعویض شناسهٔ کاربر در هویت متصل به نشست | رد درخواست |
| ادامهٔ آپلود پس از خروج واقعی | رد درخواست؛ بدون رکورد فایل، رزرو فعال یا فایل باقی‌مانده |
| ادامهٔ آپلود پس از بازنشانی واقعی رمز | رد درخواست؛ بدون رکورد فایل، رزرو فعال یا فایل باقی‌مانده |
| ویرایش پروفایل، پرتال و فهرست ذخیره‌شده با نشست لغوشده | رد درخواست |
| رقابت تراکنش مجاز با لغو هم‌زمان نشست | اثبات انتظار روی قفل و ترتیب قطعی دو عملیات |
| کار پس‌زمینه با هویت مستقل | موفق؛ پس از غیرفعال‌شدن حساب رد می‌شود |
| خروجی حریم خصوصی توسط مدیر برای مشتریِ خارج‌شده | موفق؛ پیام داخلی کارکنان در خروجی نیست |
| انتشار با تأیید بازبین مستقل پس از خروج بازبین | موفق با بررسی مجوز فعلی بازبین |

اجرای همان فایل پیش از اصلاح، ۱۰ زیرآزمون امنیتی ناموفق و ۳ زیرآزمون کنترل موفق داشت. پس از اصلاح هر ۱۳ زیرآزمون موفق شد. شمارش خود Node.js با احتساب آزمون والد، **۱۴ تست موفق، صفر شکست و صفر تست کنارگذاشته‌شده** است. آزمون هدفمند روی PostgreSQL 16.15 با SCRAM و پایگاه دادهٔ موقت اجرا شد؛ شمارش نهایی مجموعهٔ کامل آزمون‌ها در گزارش اعتبارسنجی همین انتشار ثبت می‌شود.

برای تکرار آزمون در پایگاه دادهٔ مجزای آزمایشی:

```bash
node --import tsx --test --test-isolation=none tests/server-session-revalidation.pg.mjs
```

پیش از اجرا، متغیر `TEST_ADMIN_DATABASE_URL` را از محیط امن به پایگاه دادهٔ آزمایشی بدهید. آزمون schema موقت می‌سازد، migrationهای واقعی را اجرا می‌کند و در پایان schema و فایل‌های موقت خود را حذف می‌کند. از اطلاعات یا حساب‌های واقعی کاربران استفاده نمی‌کند.

## اثر بر نصب و استفاده

این اصلاح migration جدید، تغییر قرارداد API یا تغییر ظاهر وب‌سایت ندارد. تصویر برنامه و worker باید از کد همین انتشار بازسازی و با روند استقرار مستند پروژه اجرا شوند. صفحهٔ ورود و پنل از همان پاسخ استاندارد پایان نشست استفاده می‌کنند. کلیدهای نشست و MFA را طبق راهنمای نصب در محیط امن نگه دارید؛ برای فعال‌شدن این اصلاح لازم نیست آن‌ها را عوض کنید.

# راهنمای استقرار نسخهٔ سروری ایده‌آل ماکو

این بسته، اجرای واقعی Next.js، پایگاه دادهٔ PostgreSQL 16، کارگر پس‌زمینه، رسانهٔ خصوصی و عمومی و پراکسی HTTPS را در یک پروژهٔ Docker Compose جداگانه تعریف می‌کند. مسیرهای سایت، پنل و API از یک مبدأ ارائه می‌شوند. تنظیمات و کد محیط محلیِ نسخهٔ پیشین، مبنای احراز هویت محیط سرور نیستند.

راهنمای [نصب صفر تا صد، ایمیل دامنه، کلید سرویس‌ها و Search Console](INSTALL-SERVICES-SEO-2.2.fa.md)، [پشتیبان کامل، دانلود و بازیابی یک‌فرمانی](BACKUP-RESTORE.fa.md) و [حساب‌های کارکنان از محیط](STAFF-ENV.fa.md) مکمل این سند هستند. بکاپ جاری format4 شامل کد/DB/رسانه/تنظیمات/integration/TLS، دادهٔ ایمیل مدیریت‌شده و کپی مخصوص بازیابیِ میزبان تازه از دفتر حریم خصوصی است؛ کلید مستقل age خارج از آرشیو نگهداری می‌شود. بکاپ‌های احرازاصالت‌شدهٔ format3 نیز قابل بررسی و بازیابی‌اند.

نسخهٔ ۲.۲ ایمیل دامنه را با انتخاب صریح `--with-mail-server` یا `MAIL_SERVER_ENABLED=true` نصب می‌کند؛ مسیر پیش‌فرض SMTP قبلی را حفظ می‌کند. رکوردهای عمومی DNS پس از تولید کلید DKIM ارائه می‌شوند و تا آماده‌شدن DNS/TLS، نصب موفق اعلام نمی‌شود. سرویس Postfix/Dovecot/Rspamd در image مشخص Docker Mailserver، پورت‌های استاندارد ایمیل و پوشهٔ اختصاصی داده دارد. برای سایت همراه ایمیل محلی حدود ۸ GiB RAM و Docker26+/Compose2.40+ لازم است. جزئیات DNS، PTR، relay، حساب صندوق و تمدید گواهی در راهنمای تازه آمده است.

دریافت‌های قابل‌تکرار، retry محدود و تشخیص DNS/شبکه/محدودیت نرخ دارند؛ خطای امضا، TLS، مجوز و تنظیمات متوقف می‌شود. `scripts/preflight.sh` بررسی خواندنی شبکه است. wrapper دریافت برای migration، restore یا ارسال پیام استفاده نمی‌شود. تنظیم proxy برنامه، registry مورد تأیید npm و حالت `local-images` در `.env.example` توضیح داده شده؛ هیچ‌کدام TLS یا کنترل integrity را حذف نمی‌کند.

## ۱. نصب با یک فرمان روی اوبونتوی خالی

پس از انتقال و استخراج بسته، از [.env.example](../.env.example) یک فایل خصوصی مانند `/root/idealmakoo.env` با مجوز `600` آماده کنید. نشانی سایت و دامنه، ایمیل مسئول فنی، مدیر اولیه، `STAFF_ACCOUNTS_JSON` و کلیدهای سرویس‌های مورد استفاده را در همان فایل تعیین کنید. راهنمای [حساب‌های کارکنان از محیط](STAFF-ENV.fa.md) نام نقش‌ها، زبان‌های مجاز و شیوهٔ تعریف حساب‌های مستقل نویسنده و بازبین را توضیح می‌دهد.

داخل پوشه‌ای که `package.json` و `docker-compose.yml` قرار دارند، نصب را با یک فرمان اجرا کنید:

```bash
sudo bash scripts/install-ubuntu.sh --env-file /root/idealmakoo.env --app-dir /var/www/idealmakoo-v2
```

فایل env ورودی به‌عنوان داده خوانده می‌شود و کد shell نیست. رمزها و کلیدهای داخلیِ خالی فقط طبق قواعد نصب اول تولید می‌شوند؛ کلید واقعی سرویس خارجی را اپراتور وارد می‌کند. فایل حاوی رمز را در سورس، لاگ، گفتگو یا مخزن عمومی قرار ندهید. روش بدون env ورودی نیز در README مستند است، اما مسیر اصلی این راهنما تنظیم حساب‌ها و سرویس‌ها از همان فایل خصوصی است.

`--app-dir` اختیاری است و مقدار پیش‌فرض آن `/var/www/idealmakoo` است. مسیر `/var/www/idealmakoo-v2` برای هماهنگی با مقصد اعلام‌شدهٔ شما، در مثال آمده است؛ مسیر نصب قابل تغییر است. سرور قبلاً معرفی‌شده `193.163.201.141` با کاربر `ubuntu` نیز یک مقصد قابل انتخاب است و این راهنما به معنی انجام استقرار روی آن سرور نیست.

با timer روزانهٔ پیش‌فرض، مسیر واقعی نصب نباید داخل `/home`، `/root`، `/run/user`، `/tmp` یا `/var/tmp` باشد: محدودیت‌های `ProtectHome=true` و `PrivateTmp=true` سرویس بکاپ، این مسیرها را از دسترس آن خارج می‌کنند. نصاب مسیر را با رفع symlink و بخش‌های `..` بررسی و چنین انتخابی را پیش از آماده‌سازی نصب رد می‌کند. یک پوشهٔ اختصاصی زیر `/var/www` یا `/opt` انتخاب کنید. این محدودیت مربوط به مقصد نصب است؛ فایل env ورودی مانند `/root/idealmakoo.env` می‌تواند همچنان خصوصی در همان مسیر باقی بماند و به محیط مدیریت‌شدهٔ نصب منتقل شود.

اگر آگاهانه بکاپ دستی می‌خواهید، گزینهٔ موجود `--without-backup-timer` راه‌اندازی timer را در همان اجرا کنار می‌گذارد و محدودیت مقصد مربوط به آن را اعمال نمی‌کند؛ قواعد دیگر مسیر نصب همچنان برقرارند. این گزینه timer از قبل موجود را غیرفعال نمی‌کند. تغییر این انتخاب، جای انتقال بکاپ به مقصد مستقل و نگهداشت نسخه‌ها را نمی‌گیرد.

نصاب، بسته‌های لازم را از مخازن اوبونتو نصب می‌کند و اگر Docker وجود نداشته باشد، مخزن رسمی Docker را با کنترل اثر انگشت کلید امضا اضافه می‌کند. هیچ اسکریپت دریافت‌شده‌ای مستقیماً به شل لوله نمی‌شود. کد برنامه با `npm ci` و lockfile در تصویر ساخته می‌شود؛ نصب Node روی میزبان لازم نیست. منابع و شیوهٔ نصب مخزن، مطابق [مستند رسمی Docker برای Ubuntu](https://docs.docker.com/engine/install/ubuntu/) است.

### پیش‌نیازهای قابل بررسی پیش از اجرا

| مورد | مقدار یا شرط |
| --- | --- |
| سیستم‌عامل | Ubuntu 22.04 LTS یا 24.04 LTS، همراه systemd و دسترسی sudo |
| حافظه با اسکن محلی فایل | حداقل پیشنهادی نصاب ۶ گیگابایت؛ ۸ گیگابایت مناسب‌تر برای فضای ساخت و بهره‌برداری است |
| حافظه بدون ClamAV محلی | حداقل پیشنهادی ۴ گیگابایت؛ اسکنر بیرونی باید بعداً پیکربندی شود |
| دیسک آزاد اولیه | حداقل ۱۵ گیگابایت؛ ظرفیت بیشتر با توجه به حجم فایل‌ها و بکاپ‌ها لازم است |
| DNS | رکورد دامنه به سرور مقصد اشاره کند؛ اگر رکورد IPv6 دارید، آن مسیر نیز باید واقعاً قابل دسترسی باشد |
| شبکهٔ عمومی | TCP پورت‌های ۸۰ و ۴۴۳ برای وب و صدور/تمدید گواهی؛ دسترسی خروجی برای مخازن، رجیستری و سرویس‌های فعال |
| image دیتابیس | image واقعاً منتشرشده و قابل دریافت از registry با digest ثابت؛ برای image سفارشی، انتشار، pull و نگه‌داری همان digest و دسترسی میزبان بازیابی لازم است |
| تداخل پروژه | پورت انتخابی و نام Compose باید آزاد یا متعلق به همین نصب باشند |

ClamAV به تنهایی حافظهٔ قابل توجهی لازم دارد؛ مستند رسمی حداقل ۳ و ترجیحاً ۴ گیگابایت برای خود اسکنر ذکر می‌کند و توضیح می‌دهد که بارگذاری مجدد امضاها می‌تواند مصرف حافظه را موقتاً بالا ببرد. به همین علت ظرفیت پیشنهادی کل پشته بالاتر از یک وب‌سرور ساده است. [مستند حافظه و اجرای غیرریشهٔ ClamAV](https://docs.clamav.net/manual/Installing/Docker.html)

بکاپ ایمنی ارتقا، digest را از image واقعی کانتینر DB جاری و repository مرجع اجرای همان DB ثبت می‌کند؛ pull شدن نسخهٔ تازهٔ tag یا اضافه‌شدن alias محلی، هویت snapshot قبلی را عوض نمی‌کند. نبودن digest منطبق یا انتخاب مبهم پیش از توقف نویسنده‌ها رد می‌شود. وجود `RepoDigests` به‌تنهایی اثبات انتشار image نیست؛ برخی backendهای Docker این metadata را برای image محلی نیز تولید می‌کنند. آرشیو format3 شامل imageهای Docker نیست و بازیابی میزبان تازه باید نسخهٔ ثبت‌شده را واقعاً از registry دریافت کند. برای PostgreSQL سفارشی، انتشار، نگه‌داری digest، credential و دسترسی میزبان جایگزین را پیش از اتکا به بکاپ آماده و با تمرین مستقل بررسی کنید. جزئیات و مرز بررسی محلی در [راهنمای پشتیبان و بازیابی](BACKUP-RESTORE.fa.md) آمده است.

نصاب، وب‌سایت‌های دیگر، سرویس SSH، تنظیمات فایروال، مخزن Git دیگر یا داده‌های قدیمی خارج از این نصب را متوقف یا حذف نمی‌کند. اگر پورت متعلق به سایت قبلی باشد، نصب با توضیح تداخل متوقف می‌شود تا انتقال سرویس به صورت مشخص مدیریت شود.

پس از آغاز آماده‌سازی دیتابیس، شکست نصب یا بازیابی، app و worker همین پروژه را متوقف می‌کند؛ حتی اگر برای بررسی سلامت روشن شده باشند. این حفاظت تا پایان بکاپ اولیه و بررسی نهایی سلامت فعال است. خطای build پیش از این مرحله، سرویس قبلی را متوقف نمی‌کند. دیتابیس، Volumeها و اطلاعات تشخیص خطا باقی می‌مانند؛ شکست خود فرمان توقف نیز صریح گزارش می‌شود.

اگر پیش‌تر یک restore جایگزین‌کننده نیمه‌تمام مانده باشد، نصاب و ابزار ارتقا به‌جای شروع سرویس روی وضعیت تاریخی، وجود checkpoint خصوصی `shared/.pending-restore` را گزارش می‌کنند. ابتدا همان عملیات را با همان آرشیو و release و گزینهٔ `restore.sh --resume` تکمیل کنید. snapshot دسترسی جاری و safety backup اولیه را حذف نکنید. مسیر خروج ۲ و بازیابی صریح مدیر در [راهنمای پشتیبان و بازیابی](BACKUP-RESTORE.fa.md) توضیح داده شده است.

برای میزبان کند یا اجرای شبیه‌سازی‌شده، مهلت‌های بررسی سلامت به صورت ثانیهٔ صحیح در env محافظت‌شده قابل تنظیم‌اند. پیش‌فرض‌های عادی تغییر نکرده‌اند و تنظیم بزرگ‌تر، موفقیت نصب را ثابت نمی‌کند؛ سلامت واقعی API، worker، دیتابیس و اسکنر همچنان باید تأیید شود. حدود و روش بررسی در [راهنمای عملیات](OPERATIONS.fa.md) آمده است.

### نتیجهٔ نصب

نصاب یک تصویر با شناسهٔ اختصاصی نسخه می‌سازد، PostgreSQL را آماده می‌کند، migration را اجرا می‌کند، دفتر مستقل حذف داده را پیش از seed حساب اولیه آماده و بازپخش می‌کند و مجوز نقش دیتابیس برنامه را محدود می‌کند و سپس برنامه، کارگر و پراکسی را بالا می‌آورد. سلامت دیتابیس، API، ضربان کارگر، اسکنر فعال و نشانی عمومی باید تأیید شود تا نسخه به عنوان `current` انتخاب شود. برای نخستین دریافت امضاهای اسکنر تا ۲۰ دقیقه فرصت در نظر گرفته شده است؛ طول واقعی به دسترسی رجیستری و CDN امضا بستگی دارد.

پوشه‌ها به این شکل ساخته می‌شوند:

| مسیر نسبت به `--app-dir` | کاربرد |
| --- | --- |
| `releases/<شناسه نسخه>/` | کد و تنظیمات غیرمحرمانهٔ همان نسخه |
| `current` | پیوند نسخه‌ای که بررسی سلامت آن موفق شده است |
| `previous` | پیوند نسخهٔ قبلی پس از ارتقا |
| `shared/.env` | رمزها و تنظیمات؛ فقط در نصب اول تولید می‌شود و مجوز آن ۶۰۰ است |
| `shared/backup-identity.txt` | کلید خصوصی رمزگشایی بکاپ؛ با مجوز ۶۰۰ |
| `shared/backups/` | بکاپ‌های رمزنگاری‌شده و checksum آن‌ها |
| Volumeهای Docker متعلق به پروژه | دیتابیس، کل رسانه، کش Next، گواهی‌های Caddy و امضاهای ClamAV |

فایل `.release.env` در هر نسخه، نام تصویر برنامه، نام تصویر پراکسی و شناسهٔ نسخه را ثبت می‌کند. اسکریپت‌های عملیاتی آن را پس از `.env` می‌خوانند تا بازگشت کد به تصویر مشخص امکان‌پذیر باشد. نام ثابت پروژهٔ Compose باعث می‌شود داده‌ها هنگام تعویض نسخه در همان Volumeها بمانند.

## ۲. ورود اولیه و تنظیم سرویس‌ها

حساب اولیه از `BOOTSTRAP_ADMIN_EMAIL` ایجاد می‌شود؛ پیش‌فرض، `admin@دامنه` است. با `--admin-email` می‌توانید نشانی دیگری تعیین کنید. رمز قوی، تصادفی و مختص همان نصب تولید می‌شود. نصاب رمز را در خروجی یا لاگ نمایش نمی‌دهد؛ مدیر سرور آن را از `BOOTSTRAP_ADMIN_PASSWORD` در فایل محافظت‌شدهٔ `shared/.env` می‌خواند. پس از ورود، رمز را تغییر دهید و MFA را برای حساب مدیریتی تنظیم کنید.

Seed تکرارشونده، رمز یا نقش حساب موجود را بازنویسی نمی‌کند. هیچ رمز ثابت دمو برای محیط تولید تعریف نشده است. تنظیم `DEMO_MODE=true` در حالت production مجاز نیست و کنترل دسترسی در سرور انجام می‌شود.

پیش‌فرض نصب تازه `STAFF_PROVISIONING_MODE=hybrid` است: حساب‌های اولیه از محیط محافظت‌شده ساخته می‌شوند و مدیر دارای مجوز و MFA می‌تواند اطلاعات، رمز و دسترسی کاربران را از پنل مدیریت کند. اجرای عادی seed یا provisioning، ویرایش‌های بعدی پنل را بازنویسی نمی‌کند. `env` گزینهٔ صریح برای سازمانی است که اعطای نقش و دعوت کارکنان را فقط با فرمان مالک می‌خواهد؛ نصب مجدد مقدار انتخاب‌شدهٔ نصب قبلی را حفظ می‌کند. برای انتقال نصب موجود از `env` به `hybrid`، ابتدا نسخهٔ جدید را با مقدار جاری محیط ارتقا دهید تا بکاپ ایمنی بتواند با runtime قبلی اجرا شود. سپس mode را در `shared/.env` به `hybrid` تغییر دهید و طبق بخش تغییر تنظیمات در راهنمای عملیات، app و worker را دوباره ایجاد و سلامت را بررسی کنید؛ restart ساده متغیر کانتینر را عوض نمی‌کند. کلید سرویس‌های خارجی و credentialهای زیرساخت همچنان فقط در محیط محافظت‌شده نگه‌داری می‌شوند. جزئیات نقش‌ها، محدودیت آخرین مدیر، ابطال نشست پس از تغییر رمز و تفاوت حالت‌ها در [راهنمای حساب‌ها](STAFF-ENV.fa.md) آمده است.

فایل [.env.example](../.env.example) مرجع تمام متغیرهاست. متغیرهای خصوصی در `NEXT_PUBLIC_*` قرار نمی‌گیرند و Dockerfile هیچ secret واقعی را در زمان build دریافت نمی‌کند.

| تنظیمات | کاربرد |
| --- | --- |
| `DATABASE_URL` | اتصال نقش محدود `idealmakoo_app` در برنامه و کارگر |
| `MIGRATION_DATABASE_URL` | اتصال نقش مالک schema؛ فقط در مهاجرت، seed و عملیات مجاز |
| `DATABASE_APP_ROLE=idealmakoo_app` | انتخاب صریح نقش محدود؛ فرمان grants با مقدار خالی یا نقش دیگر خطا می‌دهد |
| `STAFF_PROVISIONING_MODE` | پیش‌فرض `hybrid`: ایجاد اولیه از محیط و مدیریت مجاز کاربران در پنل؛ `env` برای سیاست صریح مدیریت محیطی و `panel` برای سازگاری گردش دعوت |
| `PRIVACY_LEDGER_HOST_DIR` | مسیر مستقل دفتر حذف، پیش‌فرض `/var/lib/idealmakoo-privacy/<project>`؛ مجوز ۷۰۰ و مالک 10001:10001 |
| `INTEGRATIONS_HOST_DIR` | فایل اختیاری رسمی push با اتصال فقط‌خواندنی؛ از سورس کنار گذاشته و در payload رمزنگاری‌شدهٔ مستقل بکاپ کامل ذخیره می‌شود |
| `SESSION_SECRET` | حفاظت نشست؛ در نصب بعدی حفظ می‌شود |
| `SESSION_IDLE_MINUTES`, `SESSION_HOURS` | انقضای بی‌فعالیتی و سقف طول نشست؛ پیش‌فرض ۶۰ دقیقه و ۲۴ ساعت |
| `DB_POOL_SIZE`, `DATABASE_SSL` | اندازهٔ pool هر پردازش؛ TLS اتصال DB بیرونی در صورت نیاز. شبکهٔ خصوصی Compose از تنظیم پیش‌فرض استفاده می‌کند |
| `MFA_ENCRYPTION_KEY` | کلید رمزنگاری MFA با ۶۴ نویسهٔ hexadecimal؛ برای بازیابی حساب‌ها حفظ شود |
| `SITE_URL`, `SITE_ADDRESS`, `ACME_EMAIL` | مبدأ برنامه، دامنه/نشانی Caddy و ایمیل ثبت گواهی |
| `NOTIFICATIONS_MODE` | پیش‌فرض `disabled`؛ برای ارسال واقعی `live` و تنظیم provider لازم است |
| `SMTP_*` | اتصال SMTP احرازشده برای ایمیل؛ مثال پورت ۵۸۷ با STARTTLS یا ۴۶۵ با TLS |
| `KAVENEGAR_*`, `NAJVA_API_KEY`, `NAJVA_API_URL`, `TELEGRAM_*` | اتصال کانال‌های پیام‌رسان در صورت فعال‌سازی؛ Najva به NAJVA_API_KEY خصوصی، website_id، SDK و worker رسمی و originهای صریح نیاز دارد؛ هدر apiKey طبق نمونهٔ رسمی بررسی‌شده در ۲۰۲۶-۱۰-۱۹ فقط از سرور ارسال می‌شود |
| `AI_PROVIDER`, کلید و مدل‌های provider | فعال‌سازی قابلیت مشخص AI پس از انتخاب صریح مدل واقعی |
| `AI_DAILY_BUDGET_USD`, `AI_MONTHLY_BUDGET_USD` | سقف‌های کنترل مصرف تنظیم‌شده در برنامه |
| `AI_*_RESERVE_USD` | ذخیرهٔ بودجه برای کارهای متن/تصویر، ویدیو و صوت؛ باید با تعرفه و سقف درخواست هم‌خوان باشد |
| `AI_PUBLIC_CHAT` | پیش‌فرض `false`؛ گفتگو برای مراجعه‌کنندهٔ ناشناس نیازمند فعال‌سازی صریح است |
| `CLAMAV_HOST`, `CLAMAV_PORT` | نشانی اسکنر INSTREAM؛ پورت پیش‌فرض ۳۳۱۰ در شبکهٔ خصوصی |

بدون کلید و مدل مناسب، قابلیت بیرونی به صورت «در دسترس نیست/پیکربندی نشده» باقی می‌ماند؛ نصب، پرداخت یا اعتبار سرویس خارجی را ایجاد نمی‌کند. برای SMTP از سرویس احرازشده استفاده می‌شود و SMTP عمومی یا Open Relay روی سرور ایجاد نمی‌شود. حساب‌ها و کلیدهای ارائه‌دهندگان فقط از سمت سرور مصرف می‌شوند.

راهنمای [تولید محتوا و ترجمه با هوش مصنوعی](AI-MULTILINGUAL.fa.md) نام متغیرهای provider، سقف بودجه، انتخاب زبان، بررسی انسانی و ثبت نتیجه را شرح می‌دهد. برای سقف فایل، سهمیهٔ مالک، مجوز مدیر و اسکن/فضای واقعی سرور، [راهنمای آپلود و ذخیره‌سازی](UPLOAD-STORAGE.fa.md) را بخوانید.

تغییر مقدارهای build-time از جمله `NEXT_PUBLIC_SITE_URL` نیازمند ساخت تصویر تازه است. تغییر متغیرهای runtime نیز نیازمند recreate سرویس مربوط است؛ `docker compose restart` به تنهایی محیط کانتینر موجود را تغییر نمی‌دهد.

## ۳. اجرای HTTP برای محیط بررسی

برای یک ماشین آزمایشی که DNS و TLS هنوز روی آن آماده نیست، این فرمان پورت ۸۰۸۰ را فقط روی loopback باز می‌کند:

```bash
sudo bash scripts/install-ubuntu.sh --domain 127.0.0.1 --http --http-port 8080 --https-port 8443 --bind-ip 127.0.0.1 --without-antivirus --app-dir /var/www/idealmakoo-test --project-name idealmakoo-test
```

نشانی آن `http://127.0.0.1:8080` است. برای دسترسی از لپ‌تاپ به loopback سرور می‌توان از تونل SSH استفاده کرد. این حالت صریحاً HTTP است و برای نشانی عمومی اصلی، نصب HTTPS بخش اول استفاده می‌شود.

گزینهٔ `--without-antivirus` در تولید فایل تنظیمات اولیه، پروفایل اسکنر محلی را کنار می‌گذارد. فایل‌های غیرتصویری تا دریافت نتیجهٔ پاک از اسکنر، در قرنطینه می‌مانند. می‌توان `CLAMAV_HOST` را به اسکنر خصوصی بیرونی متصل کرد یا با تأمین حافظه، `COMPOSE_PROFILES=antivirus` را فعال کرد. انتخاب این گزینه روی تنظیمات موجود، به معنی تغییر خودکار `.env` نیست.

## ۴. معماری شبکه و حفاظت محیط اجرا

| سرویس | نقش | دسترسی شبکه و فایل |
| --- | --- | --- |
| `proxy` | Caddy، HTTPS خودکار و reverse proxy | تنها ورودی عمومی TCP ۸۰/۴۴۳؛ بدون دسترسی به دیتابیس یا Volume رسانه |
| `app` | Next.js standalone، سایت، پنل و API | پورت ۳۰۰۰ فقط داخلی؛ دسترسی به رسانه و دیتابیس با نقش محدود |
| `worker` | صف کار، اعلان‌ها، انتشار زمان‌بندی‌شده و اسکن | بدون پورت عمومی؛ heartbeat در دیتابیس |
| `migrate` | migration، seed و grants | یک‌بار اجرا با نقش مالک schema؛ bootstrap فقط در این سرویس |
| `db` | PostgreSQL 16 و افزونه‌های نصب‌شده | بدون انتشار پورت؛ شبکهٔ داخلی جدا؛ دادهٔ پایدار |
| `clamav` | اسکن فایل غیرتصویری | پروفایل `antivirus`؛ پورت ۳۳۱۰ فقط داخلی؛ امضاهای پایدار |
| `storage-tool` | انتقال کنترل‌شدهٔ رسانه برای بکاپ/بازیابی | فقط پروفایل `operations`، بدون شبکه و بدون اطلاعات اتصال |

برنامه با UID ۱۰۰۰۱، پراکسی با UID ۱۰۰۰۲ و PostgreSQL و ClamAV با کاربر غیرریشهٔ تصویر اجرا می‌شوند. ریشهٔ کانتینرها فقط‌خواندنی است؛ مسیرهای موقت و Volumeهای لازم جدا هستند. قابلیت‌های لینوکس حذف، افزایش امتیاز غیرفعال و چرخش لاگ Docker به پنج فایل ۱۰ مگابایتی برای هر سرویس محدود شده است. رمز نقش superuser دیتابیس به برنامه یا کارگر داده نمی‌شود.

در ساخت تصویر پراکسی، `getcap /usr/bin/caddy` بررسی می‌شود؛ اگر file capability وجود داشته باشد، با `setcap -r` حذف و سپس خالی‌بودن نتیجه دوباره کنترل می‌شود. خطای هر دو بررسی یا حذف، build را متوقف می‌کند. این اصلاح برای سازگاری باینری تصویر پایه با محدودیت `cap_drop: ALL` است؛ اجرای UID ۱۰۰۰۲، `no-new-privileges`، ریشهٔ فقط‌خواندنی و sysctl موجودِ پورت‌های غیرممتاز حفظ می‌شوند. برای رفع `operation not permitted`، قابلیت تازه، حالت privileged یا اجرای root اضافه نکنید؛ تصویر اصلاح‌شده را از سورس بررسی‌شده بسازید و از مسیر استقرار کنترل‌شده جایگزین کنید.

Caddy صدور و تمدید گواهی را با دادهٔ پایدار خود مدیریت می‌کند؛ در این بسته جایگزین Nginx و Certbot جداگانه شده است. هدرهای IP و پروتکل از اتصال واقعی پراکسی بازنویسی می‌شوند. این پیکربندی به IPهای دلخواه CDN اعتماد نمی‌کند؛ در صورت افزودن CDN باید زنجیرهٔ اعتماد آن به صورت مشخص بررسی شود. جزئیات HTTPS در [مستند Caddy](https://caddyserver.com/docs/automatic-https) آمده است.

## ۵. Docker Compose بدون نصاب؛ تمرین توسعه و کاربری پیشرفته

این مسیر برای تمرین توسعه و راه‌اندازی دستیِ پیشرفتهٔ یک پروژهٔ تازه با Docker Engine و افزونهٔ Compose نسخهٔ ۲٫۲۴ یا جدیدترِ آماده است. Python 3 و curl نیز باید روی میزبان موجود باشند. این دستورها نصب مدیریت‌شدهٔ پشتیبانی‌شده برای چرخهٔ کامل بکاپ، ارتقا و بازیابی را ایجاد نمی‌کنند؛ برای آن چرخه از نصاب بخش اول استفاده کنید. برای نصب مدیریت‌شده‌ای که پوشهٔ `current` دارد، از فرمان‌های [راهنمای بهره‌برداری](OPERATIONS.fa.md) استفاده کنید؛ ارتقای آن نصب از مسیر `scripts/update.sh --source` انجام می‌شود.

ابتدا `.env` را بر اساس `.env.example`، با رمزهای مستقل، URLهای هماهنگ دیتابیس، اطلاعات مدیر و دامنهٔ واقعی تکمیل کنید. فایل نمونه به‌تنهایی تنظیمات قابل اجرای تولید نیست. دو مقدار `PRIVACY_LEDGER_HOST_DIR` و `INTEGRATIONS_HOST_DIR` باید مسیرهای مطلق و اختصاصی همین نصب، بدون symlink باشند. دفتر حذف داده باید از رسانه، بکاپ عادی، نسخه‌های کد و integrations مستقل بماند؛ برای آن مسیر عمومی سایت را انتخاب نکنید.

پیش از ساخت کانتینرها، helper موجود `deploy/runtime-directories.py` مسیرهای ثبت‌شده در همان فایل محیط را با این مالکیت‌ها آماده می‌کند:

| متغیر مسیر میزبان | مالک UID:GID | مجوز | کاربرد |
| --- | --- | --- | --- |
| `PRIVACY_LEDGER_HOST_DIR` | `10001:10001` | `0700` | دفتر مستقل و امضاشدهٔ حذف داده؛ قابل نوشتن برای پردازش مجاز برنامه |
| `INTEGRATIONS_HOST_DIR` | `0:10001` | `0750` | پوشهٔ integrations؛ در کانتینر فقط‌خواندنی و با push غیرفعال می‌تواند خالی باشد |

helper مسیر تازه را می‌سازد؛ اگر مسیر موجود مالکیت یا مجوز متفاوت داشته باشد، با خطا متوقف می‌شود و آن را خودکار تغییر نمی‌دهد. Compose برای این دو bind mount از `create_host_path: false` استفاده می‌کند؛ نوشتن نام مسیر در `.env` به‌تنهایی کافی نیست. در بلوک زیر، مسیر پوشهٔ استخراج‌شدهٔ واقعی را جایگزین کنید. ورود به شل root پیش از `cd` برای پوشه‌هایی با دسترسی مدیریتی ضروری است:

```bash
sudo -i
cd /ABSOLUTE/PATH/TO/EXTRACTED_PROJECT
chmod 600 .env
export IDEALMAKOO_ENV_FILE="$PWD/.env"
(
  source deploy/lib.sh
  require_environment
  acquire_ops_lock
  pending_restore assert-clear
  python3 deploy/runtime-directories.py "$ENV_FILE" "$PROJECT_ROOT"
  build_services=(app proxy)
  if [[ ",$(env_get COMPOSE_PROFILES)," == *,antivirus,* ]]; then build_services+=(clamav); fi
  build_release_images "${build_services[@]}"
  dc pull db
  dc up -d --no-deps --wait --wait-timeout 180 db
  dc up --no-deps --force-recreate --abort-on-container-exit --exit-code-from migrate migrate
  if [[ ",$(env_get COMPOSE_PROFILES)," == *,antivirus,* ]]; then dc up -d --no-deps clamav; fi
  lifecycle up --timeout 1200 app worker proxy
  lifecycle check --timeout 240
)
```

`source` در این فرمان، فقط کد بررسی‌شدهٔ `deploy/lib.sh` را بارگذاری می‌کند؛ فایل `.env` به‌عنوان کد shell اجرا نمی‌شود. `require_environment` خصوصی‌بودن فایل محیط را کنترل می‌کند و تابع `dc` را با `--env-file` صریح، `--project-directory` همین پروژه و `-f` فایل `docker-compose.yml` آن آماده می‌کند. اگر `.release.env` موجود باشد، آن را به‌عنوان فایل محیط دوم نیز می‌خواند تا نام image و شناسهٔ نسخه حفظ شود. برای جلوگیری از چاپ رمزهای بسط‌یافته، بررسی config با `--quiet` انجام می‌شود.

قفل عملیاتی و `pending_restore assert-clear` پیش از هر تغییر اجرا می‌شوند؛ پایان subshell قفل را آزاد می‌کند. migration باید با خروج صفر تمام شود. پس از آن helper، app را تا سلامت Docker، سپس worker را تا سلامت آن و در پایان proxy و نشانی واقعی `SITE_URL/api/v1/health/ready` پیش می‌برد. فرمان `check` وضعیت نهایی همهٔ سرویس‌های انتخابی و ClamAV فعال را دوباره بررسی می‌کند. `lifecycle up` تصویر نمی‌سازد یا دریافت نمی‌کند و وابستگی‌ها را پنهانی بالا نمی‌آورد؛ آماده‌سازی صریح DB، migration، تصویر و اسکنر در همین فرمان‌ها لازم است. این مسیر برای پروژهٔ تازه است؛ روی نصب موجود، migration یا شروع سرویس را جایگزین `update.sh` یا ادامهٔ restore نکنید.

این مسیر نصب ابزارهای میزبان، ساخت کلید age، زمان‌بندی بکاپ، ساخت پوشه‌های release و تولید فرادادهٔ `.release.env` منطبق با release و تصویر واقعیِ نصب‌شده را انجام نمی‌دهد. اسکریپت بکاپ کامل، تطبیق همین فراداده با تصویر در حال اجرا را لازم دارد؛ ساخت کلید age به‌تنهایی این نصب دستی را برای چرخهٔ مدیریت‌شده آماده نمی‌کند. `.release.env` را برای عبور از این کنترل به‌صورت دستی نسازید. نصب یک‌فرمانیِ بخش اول، این مراحل را همراه آماده‌سازی همین مسیرها یکپارچه انجام می‌دهد و برای سرور خالی مسیر توصیه‌شده است. دفتر موجود را با دفتر خالی جایگزین نکنید؛ مقداردهی اولیه یا پذیرش یک دیتابیس قدیمی تابع کنترل‌های بخش حریم خصوصی است.

پس از مقداردهی اولیه، تغییر رمز در `.env` به تنهایی رمز ذخیره‌شدهٔ PostgreSQL را تغییر نمی‌دهد؛ init فقط روی Volume خالی اجرا می‌شود. گردش رمز موجود به تغییر هماهنگ نقش PostgreSQL و URLهای مربوط نیاز دارد.

### مرز cache ساخت برنامه و فایل‌های عملیات

مرحلهٔ builder ورودی‌های واقعی کامپایل و TypeScript را می‌گیرد: فایل‌های تنظیمات، `src`، `public`، `worker`، اسکریپت‌های TypeScript، آزمون‌های TypeScript و e2e و مولد service worker. `public` نهایی، از جمله service worker تولیدشده، از builder منتقل می‌شود. فایل‌های جاری `scripts`، `deploy` و `db` پس از خروجی کامپایل در تصویر runtime کپی می‌شوند؛ تغییر اسکریپت عملیاتی از تصویر نهایی حذف نمی‌شود.

با ثابت‌ماندن تصویر پایه، lockfile، ورودی‌های builder و build arguments، تغییر صرفاً shell/Python عملیاتی یا راهنما لازم نیست کامپایل Next.js را باطل کند؛ تغییر کد TypeScript، دارایی عمومی، تنظیمات، `NEXT_PUBLIC_SITE_URL` یا وابستگی می‌تواند آن را باطل کند. نخستین ساخت با این Dockerfile ممکن است به کامپایل کامل نیاز داشته باشد و وجود cache تضمین نمی‌شود. تصویر نهاییِ دارای فایل‌های تغییرکرده باید واقعاً ساخته و بررسی شود؛ استفاده از image قدیمی، اثبات ساخت سورس تازه نیست. راهنماها و آزمون‌های Python جزء ورودی کامپایل نیستند؛ برای افزودن ورودی جدید build، فهرست `COPY` و آزمون `deployment_docker_build_inputs_test.py` نیز باید بازبینی شوند.

### شبکه سازمانی و گواهی CA در زمان build

نصب عمومی به CA اختصاصی نیاز ندارد. اگر شبکه سازمان با پراکسی TLS دارای CA بررسی‌شده کار می‌کند و npm خطای زنجیره گواهی می‌دهد، مسیر مطلق PEM همان CA را در `BUILD_CA_CERT_FILE` فایل محیط فعال قرار دهید و override اختیاری را صریح انتخاب کنید:

```bash
sudo env IDEALMAKOO_COMPOSE_OVERRIDE="$PWD/compose.build-ca.yml" \
  bash scripts/install-ubuntu.sh --env-file "$PWD/.env"
```

پیکربندی مجاز پراکسی/اعتماد Docker daemon و میزبان باید توسط مدیر زیرساخت انجام شده باشد؛ نصاب پراکسی دلخواه یا غیرفعال‌سازی بررسی TLS را ایجاد نمی‌کند. [BuildKit secret mount](https://docs.docker.com/build/building/secrets/) فقط هنگام سه فرمان npm فایل CA را در دسترس می‌گذارد. مقدار CA در ARG، history یا image نهایی کپی نمی‌شود و `NODE_EXTRA_CA_CERTS` نیز فقط همان فرایند build را تحت تأثیر قرار می‌دهد. برای شبکه سازمانی در runtime، mount و اعتماد محدود سرویس‌های نیازمند دسترسی بیرونی باید جدا و آگاهانه تنظیم شود. آرشیو، کد override را حفظ می‌کند؛ مسیر/اعتماد شبکه میزبان تازه باید با محیط مقصد هماهنگ باشد.

در شبکهٔ نیازمند پراکسی، پیکربندی daemon به‌تنهایی لزوماً برای فرمان Docker/Buildx کافی نیست: دریافت token یا metadata رجیستری می‌تواند از فرایند client انجام شود. در پذیرش واقعی ۲.۱.۴، `sudo` تنظیمات پراکسی محیط اپراتور را منتقل نکرده بود؛ client برای `auth.docker.io` به DNS مستقیمِ مسدودشده رفت و ساخت پیش از کامپایل و migration متوقف شد، در حالی که HTTPS از پراکسی معتبر موفق بود. با حفظ انتخابی تنظیمات موجود، درخواست metadata با بررسی TLS موفق شد. اگر همین شرایط در شبکهٔ شما برقرار است و متغیرهای زیر از قبل در محیط اپراتور به‌درستی تنظیم و export شده‌اند، آن‌ها را صریح منتقل کنید؛ نمونهٔ ارتقای نصب موجود:

```bash
sudo --preserve-env=HTTP_PROXY,HTTPS_PROXY,NO_PROXY,IDEALMAKOO_COMPOSE_OVERRIDE \
  bash /var/www/idealmakoo-v2/current/scripts/update.sh \
  --source /ABSOLUTE/PATH/idealmakoo-production-2.1.4
```

این الگو فقط نام متغیرهای لازم را به `sudo` می‌دهد؛ مقدار نشانی پراکسی یا اطلاعات احتمالی ورود آن در آرگومان فرمان قرار نمی‌گیرد. پذیرش `--preserve-env` تابع سیاست همان میزبان است؛ برای عبور از خطا، sudoers یا بررسی TLS را غیرفعال نکنید. برای نصب تازه نیز همین پیشوند را همراه فرمان `install-ubuntu.sh` و آرگومان‌های مستند آن به کار ببرید. سرور با اتصال مستقیم به رجیستری به پراکسی یا CA اختصاصی نیاز ندارد. فایل env برنامه را برای ساخت محیط shell با `source` اجرا نکنید.

در مسیر اختیاری CA، نصاب plan تولیدشده توسط `docker compose build --print` را بدون چاپ عمومی به Buildx می‌دهد و فقط مجوز `fs.read` همان فایل بررسی‌شده را اعطا می‌کند؛ بنابراین پلاگین Compose باید این فرمان را پشتیبانی کند. این مسیر با کنترل دسترسی فایل در نسخه‌های جدید Buildx سازگار است؛ فایل‌های بیرون از پروژه مجوز کلی نمی‌گیرند و بررسی filesystem خاموش نمی‌شود. مسیر PEM باید فایل معمولی بدون symlink، حداکثر یک مگابایت و فقط شامل گواهی عمومی باشد. مستند رسمی: [مجوزهای محدود فایل در Buildx Bake](https://docs.docker.com/reference/cli/docker/buildx/bake/#allow-extra-privileged-entitlement---allow).

اعتماد زمان ساخت به‌طور خودکار به آنتی‌ویروسِ در حال اجرا منتقل نمی‌شود. اگر همان پراکسی سازمانی ارتباط FreshClam را نیز با خطای گواهی متوقف کند، مدیر زیرساخت باید مجموعهٔ CA بررسی‌شدهٔ مقصد را فقط‌خواندنی در سرویس `clamav` mount و `CURL_CA_BUNDLE` را در همان سرویس به مسیر آن فایل تنظیم کند. این متغیر در [راهنمای رسمی FreshClam](https://docs.clamav.net/faq/faq-freshclam.html#problem-with-the-ssl-ca-cert) مستند شده است.

نمونهٔ زیر فقط تنظیم سرویس اسکنر را نشان می‌دهد. آن را در یک override مستقلِ اپراتور، با ورودی‌های موجود `services` و `secrets` مربوط به اعتماد build ادغام کنید؛ جایگزین‌کردن کامل `compose.build-ca.yml` با این قطعه، تنظیم اعتماد build را حذف می‌کند. مسیر `source` باید به فایل PEM موجود و بررسی‌شدهٔ همان میزبان اشاره کند. مجموعه باید CAهای عمومی لازم و CA مجاز شبکه را داشته باشد؛ کلید خصوصی در آن قرار ندهید.

```yaml
services:
  clamav:
    environment:
      CURL_CA_BUNDLE: /run/idealmakoo-ca/trusted.pem
    volumes:
      - type: bind
        source: /ABSOLUTE/PATH/reviewed-ca-bundle.pem
        target: /run/idealmakoo-ca/trusted.pem
        read_only: true
        bind:
          create_host_path: false
```

مسیر مطلق override ادغام‌شده را در `IDEALMAKOO_COMPOSE_OVERRIDE` تنظیم و export کنید و آن را با همان پیشوند `sudo --preserve-env` بالا به فرمان نصب یا به‌روزرسانی بدهید. همین override باید برای عملیات بعدیِ بازسازی اسکنر نیز در دسترس باشد. تنظیم شبکهٔ میزبان تازه را پیش از نصب یا بازیابی با محیط مقصد هماهنگ کنید.

در پذیرش واقعی این بسته، تلاش نخست نصب به‌دلیل نبود این اعتماد در کانتینر ClamAV با خروج ۱ متوقف شد. همان نصب و volumeها با تنظیم محیطی بالا ادامه یافت؛ مقایسهٔ پیکربندی حل‌شده نشان داد فقط متغیر اسکنر و mount فقط‌خواندنی افزوده شده‌اند. هر سه پایگاه رسمی `daily`، `main` و `bytecode` دریافت شدند و اسکنر سالم شد. بررسی TLS، امضای رسمی و اسکن فایل برقرار ماندند و پایگاه امضای نصب قبلی کپی نشد. شکست اولیه و ادامهٔ همان نصب، دو نصب مستقل موفق محسوب نمی‌شوند؛ [رسید محیط شبکه](verification-evidence/repair-2.1.4/operations/13-fresh-install-network-trust.safe.json) جزئیات را ثبت می‌کند.

### مهلت بررسی سلامت روی میزبان کم‌سرعت

اگر سرویس سالم است ولی اجرای یک probe روی میزبان اندازه‌گیری‌شده از مهلت پیش‌فرض طولانی‌تر می‌شود، این تنظیمات را در فایل محیط خصوصی تعیین کنید. در نصب موجود، مرجع تنظیمات `shared/.env` است. پس از تغییر، از مسیر معمول استقرار/به‌روزرسانی کانتینرها را بازسازی کنید؛ ویرایش فایل به‌تنهایی تنظیم کانتینر موجود را تغییر نمی‌دهد.

| متغیر | پیش‌فرض (ثانیه) | محدودهٔ مجاز |
| --- | --- | --- |
| `APP_HEALTH_TIMEOUT_SECONDS` | ۸ | ۸ تا ۱۲۰ |
| `APP_HEALTH_START_PERIOD_SECONDS` | ۴۵ | ۴۵ تا ۶۰۰ |
| `WORKER_HEALTH_TIMEOUT_SECONDS` | ۱۰ | ۱۰ تا ۱۲۰ |
| `WORKER_HEALTH_START_PERIOD_SECONDS` | ۶۰ | ۶۰ تا ۶۰۰ |

مهلت شروع هر سرویس باید دست‌کم برابر مهلت probe آن باشد. مقدار خالی همان پیش‌فرض را نگه می‌دارد؛ مقدار نامعتبر پیش از اجرای Compose رد می‌شود. برای نمونه، در محیط آزمایشیِ شبیه‌سازی کامل CPU، مهلت probe برابر ۹۰ ثانیه و مهلت شروع برابر ۶۰۰ ثانیه انتخاب شد. این انتخاب برای همهٔ سرورها توصیهٔ پیش‌فرض نیست و خطای اتصال DB، خرابی سرویس یا کمبود منابع را برطرف نمی‌کند.

probe برنامه از همان بودجهٔ ثبت‌شده استفاده می‌کند و دو ثانیه را برای شروع/پایان فرایند کنار می‌گذارد. `doctor.sh` نیز اکنون همان مهلت را رعایت می‌کند؛ بنابراین به‌خاطر بازگشت ناخواسته به مهلت پیش‌فرض، با نتیجهٔ Docker تناقض ایجاد نمی‌کند. بررسی worker مستقیماً با Node اجرا می‌شود و به شروع یک فرایند اضافهٔ npm وابسته نیست. سلامت worker همچنان به heartbeat واقعی و تازه در PostgreSQL وابسته است؛ افزایش مهلت، شرط سلامت یا بررسی اسکنر را حذف نمی‌کند.

## ۶. محدودهٔ پذیرش و قابلیت بازتولید

### وضعیت بررسی همین سورس

سورس جاری ۴۱ migration تا شمارهٔ 042 دارد. نتیجهٔ هر آزمون باید به hash منبع و شناسهٔ build همان اجرا متصل باشد؛ شواهد قدیمیِ سورس بازیابی‌شده، نتیجهٔ خودکار سورس اصلاح‌شده نیستند. [گزارش پذیرش](VERIFICATION.fa.md) مرجع build، مرورگر، API، PostgreSQL، Lighthouse و عملیات واقعی Docker در انتشار جاری است. [گزارش اصلاح DevOps](DEVOPS-REPAIR-2.1.fa.md) سابقهٔ اصلاح نصب و بازیابی در مرحلهٔ پیشین را ثبت می‌کند.

در آن مرحلهٔ پیشین، compiler واقعی Docker روی منبع بازیابی‌شده در آزمایشگاه مستقل Ubuntu اجرا شد، migration و seed به پایان رسید و پایگاه امضای رسمی ClamAV دریافت شد. اجرای مرحلهٔ سلامت، سقف شش‌ثانیه‌ای ثابت داخل probe را آشکار کرد که بودجهٔ تنظیم‌شدهٔ Docker را نادیده می‌گرفت؛ این ایراد اصلاح و با HTTP واقعی کند آزموده شد. شکست نصب قبلی و توقف حفاظت‌شدهٔ نویسنده‌ها در سابقه حفظ شده‌اند. پذیرش نصب یا restore فقط پس از خروج موفق اجرای واقعی ثبت می‌شود. این فرمان‌ها روی سرور عمومی کاربر اجرا نشده‌اند؛ دامنه، TLS عمومی و provider به تنظیم و آزمون مقصد واقعی نیاز دارند.

migration `042_user_directory.sql` دو index مرتب‌شده برای فهرست حساب‌ها و کارکنان می‌سازد. تعداد واقعی فایل‌ها ۴۱ است، چون 005 در مجموعه نیست. این indexها در تراکنش عادی ساخته می‌شوند؛ روی جدول بزرگ، برای قفل و مدت ساخت در پنجرهٔ نگهداشت برنامه‌ریزی کنید. migrationهای قبلی یا checksumهای ledger را برای عبور از خطا تغییر ندهید.

فایل `.github/workflows/ci.yml` سه مسیر مستقل دارد: آزمون برنامه روی PostgreSQL واقعی با نقش‌های مجزا، بررسی وابستگی‌های runtime و اسکریپت‌ها، و ساخت/اجرای Compose همراه با بکاپ رمزنگاری‌شده و restore drill واقعی. تعریف CI به معنی اجرای آن در GitHub یا موفقیت خودکار نیست؛ نتیجهٔ هر run باید از همان run خوانده شود. فعال‌سازی کلیدهای بیرونی و صدور TLS نیز روی مقصد واقعی بررسی می‌شود.

lockfile نسخهٔ وابستگی‌های برنامه را تثبیت می‌کند و هر نصب، تصویر اختصاصی نسخه را نگه می‌دارد. متغیرهای `NODE_IMAGE`, `POSTGRES_IMAGE`, `CADDY_IMAGE`, `CLAMAV_IMAGE` امکان استفاده از digest تأییدشدهٔ رجیستری را دارند. tagهای upstream می‌توانند با انتشار امنیتی تغییر کنند؛ به‌روزرسانی تصویر باید همراه با اجرای CI و ثبت digest جدید انجام شود.

این طراحی، استقرار تک‌سروری با بکاپ و مسیر بازیابی است. failover چندسروری، تکرار دیتابیس بین مراکز و ذخیره‌سازی شیء بیرونی نیازمند پیکربندی زیرساخت متناسب با نیاز بهره‌برداری‌اند و به صرف داشتن Docker Compose ایجاد نمی‌شوند.


## دفتر مستقل حریم خصوصی و راه‌اندازی native

متغیر `PRIVACY_LEDGER_DIR` در Compose برابر `/app/privacy-ledger` و مستقل از `/app/storage` است. اولین اجرای migration روی دیتابیس تازه، پیش از ایجاد حساب، دفتر امضاشده را ایجاد می‌کند؛ سپس replay و readiness اجرا می‌شوند. نبودن یا عقب‌بودن دفتر، برنامه و کارگر را متوقف نگه می‌دارد. دیتابیس موجود بدون هویت دفتر، به پذیرش صریح `initialize --adopt-existing` پس از بررسی بکاپ مستقل نیاز دارد؛ نصاب این پذیرش را خودکار انجام نمی‌دهد.

در اجرای native، یک مسیر مطلق مستقل و خصوصی با مالک کاربر پردازش در `PRIVACY_LEDGER_DIR` تعیین کنید. دو فایل با مجوز `600` آماده کنید: `.env.owner` برای عملیات migration با `DATABASE_URL` و `MIGRATION_DATABASE_URL` متعلق به `idealmakoo_owner`، و `.env.local` برای برنامه و worker با `DATABASE_URL` متعلق به `idealmakoo_app`. فایل runtime نباید اتصال مالک را در اختیار پردازش برنامه بگذارد. مقدار صریح `DATABASE_APP_ROLE=idealmakoo_app` را برای فرمان grants ثبت کنید؛ نبودن آن خطاست. کلیدهای نشست/MFA، URL سایت، مسیر رسانه و دفتر مستقل باید در هر دو فایل یکسان باشند.

روی دیتابیس تازهٔ همین نسخه، پس از آماده‌کردن نقش‌ها و extensionهای `pgcrypto` و `vector`، ترتیب راه‌اندازی چنین است:

```bash
chmod 600 .env.owner .env.local
node --env-file=.env.owner --import tsx scripts/db-migrate.ts
node --env-file=.env.owner --import tsx scripts/privacy-ledger.ts initialize
node --env-file=.env.owner --import tsx scripts/privacy-ledger.ts replay
node --env-file=.env.owner --import tsx scripts/privacy-ledger.ts ready
node --env-file=.env.owner --import tsx scripts/db-seed.ts
DATABASE_APP_ROLE=idealmakoo_app node --env-file=.env.owner deploy/grant-runtime.mjs
node --env-file=.env.local --import tsx scripts/privacy-ledger.ts ready
npm run build
node --env-file=.env.local --run start
```

ساخت را با `npm run build` اجرا کنید تا مرحلهٔ `prebuild` برای تولید service worker نیز انجام شود. Next فایل `.env.local` را هنگام ساخت می‌خواند؛ `node --run build` این مرحلهٔ npm را اجرا نمی‌کند.

worker را در پردازش جدا با `node --env-file=.env.local --import tsx scripts/worker.ts` شروع کنید. در نصب native دائمی، مدیر سرویس سیستم باید هر دو پردازش را supervise کند؛ نصاب Compose این کار را با restart policy انجام می‌دهد. CLI دفتر مستقیماً `DATABASE_URL` را می‌خواند و برخلاف migration، خودکار به `MIGRATION_DATABASE_URL` تغییر نمی‌دهد؛ تفکیک دو فایل از اجرای آماده‌سازی با نقش محدود جلوگیری می‌کند. از چاپ URL و `source .env.local` در شل خودداری کنید. متغیرهای قدیمیِ exportشده در شل نباید مقادیر فایل را override کنند. `PRIVACY_RESTORE_DATABASE` فقط برای نام‌های موقت کنترل‌شدهٔ `idealmakoo_drill_*` معتبر است.

## رسانه، RAG و اتصال اختیاری push

تصویر runtime شامل FFmpeg و ffprobe است. کار پردازش فقط با منبع مجاز، scan-clean، حقوق معتبر و درخواست صریح اجرا می‌شود. worker با `WORKER_CPUS` و `WORKER_MEMORY` محدود است؛ `MEDIA_PROCESSING_TIMEOUT_SECONDS` سقف زمانی پردازش را تعیین می‌کند. سهمیهٔ کل رسانه به‌طور پیش‌فرض ۱۰ گیبی‌بایت و سهمیهٔ هر حساب ۱ گیبی‌بایت است. بایت‌های PDF صادرشدهٔ پیش‌فاکتور در دیتابیس و بکاپ آن نگهداری می‌شوند و جزو سهمیهٔ فایل‌های آپلودی نیستند.

RAG با `RAG_ENABLED=false` خاموش است. فعال‌سازی نیازمند کلید OpenRouter، مدل embedding صریح، بعد سازگار ۷۶۸/۱۰۲۴/۱۵۳۶ و بودجه است؛ نام مدل حدسی انتخاب نمی‌شود. اندازه‌گیری مرورگر نیز پیش‌فرض خاموش است و بعد از فعال‌سازی به رضایت analytics نیاز دارد. بررسی بیرونی اختیاری پایش، پیش‌فرض خاموش است.

برای push، فایل رسمی جاری را از پنل سازمان دریافت و بررسی کنید، سپس `--najva-worker-file /ABSOLUTE/PATH/najva-messaging-sw.js` را به نصاب بدهید. این فایل باید UTF-8 و بین ۲۰ بایت و ۲۵۶ کیبی‌بایت باشد؛ مسیر سروری آن `/app/integrations/najva-messaging-sw.js` است. کلید خصوصی `NAJVA_API_KEY`، SDK، `website_id` و originهای دقیق HTTPS نجوای لازم را نیز پیکربندی کنید. الزام هدر `apiKey` و مقصد دقیق در [مستند رسمی نجوا](https://www.najva.com/api-docs/) در ۲۰۲۶-۱۰-۱۹ بررسی شده است. wildcard، host حدسی، مسیر داخل origin و پورت غیر۴۴۳ پذیرفته نیست. جزئیات DKIM، OTP، Telegram و نگاشت رضایت در [راهنمای ارتباطات](COMMUNICATIONS.fa.md) آمده است. ارسال واقعی همچنان پیش‌فرض غیرفعال است.

## سازگاری آرشیو ۲.۰.۰ و سابقهٔ بازسازی

آرشیو مرجع ارسالی `idealmakoo-production-2.0.0.zip` با SHA-256 برابر `b9a80316a6526435bf06a29084cbc93e33a5ad6c5ad7b57ac8db5aa1a744c716` با checksum ارائه‌شده تطابق دارد. هر ۷۷۲ ورودی فهرست checksum داخلی و CRC آرشیو بررسی شد. هر ۳۷ migration آن با نسخهٔ ۲.۱.۴ بایت‌به‌بایت یکسان است و فقط فایل‌های ۰۳۹ تا ۰۴۲ اضافه شده‌اند؛ نبود شمارهٔ ۰۰۵ از همان مجموعهٔ قدیمی است. همچنین هر ۴۱ migration مبنای ۲.۱.۳ بدون تغییر مانده است. [رسید این مقایسه](verification-evidence/repair-2.1.4/legacy-2.0.0-reference.safe.json) همراه بسته است.

هشدار بازسازی زیر، از قبل در خود آرشیو ۲.۰.۰ وجود داشته است: پس از حذف مسیر موقت توسعه در یک مرحلهٔ تاریخی، سورس از checkpoint و cache بازسازی شد؛ فایل‌های ۰۰۱ تا ۰۲۴ با checksum تاریخی آن مرحله تطابق داشتند و ۰۲۵ تا ۰۳۴ بازسازی صریح schema با checksum تازه بودند. این سابقه به نصب‌های ناشناخته یا دفترهای متعلق به پیش از آن بازسازی مربوط است و نباید به‌معنی تغییر ۳۷ فایلِ آرشیو مرجع بررسی‌شده در انتشار ۲.۱.۴ خوانده شود.

مقایسهٔ ZIP، اجرای ارتقا روی دیتابیس نصب‌شدهٔ شما نیست. پیش از ارتقا، checksumهای واقعی `schema_migrations`، بکاپ و دفتر مستقل حریم خصوصی همان نصب باید بررسی شوند. runner در صورت اختلاف checksum توقف می‌کند؛ فایل migration یا ledger را برای عبور از این خطا تغییر ندهید. نصب با ledger متفاوت به بررسی مستقل schema، داده و مسیر انتقال نیاز دارد.

در checkpoint تاریخی بازسازی، ۱۶ آزمون ابزارهای آرشیو/محیط/grants و اعتبارسنجی ShellCheck، parser واقعی Compose و Caddy موفق شده بودند. آن نتیجه به‌تنهایی اجرای Docker، نصب Ubuntu، TLS عمومی یا ارسال provider را اثبات نمی‌کند و نتیجهٔ جاری ۲.۱.۴ نیست. [گزارش پذیرش این انتشار](VERIFICATION.fa.md) نتایج تازه را با محیط، شناسهٔ ساخت و حدود همان اجرا ثبت می‌کند.

## قفل بسته‌های سیستم و خطای مخزن

فرمان‌های نصب بسته در `install-ubuntu.sh` و `recover-ubuntu.sh` از گزینهٔ بومی `DPkg::Lock::Timeout=180` استفاده می‌کنند. اگر فرایند معتبر دیگری مانند به‌روزرسانی خودکار قفل frontend یا پایگاه دادهٔ dpkg را گرفته باشد، APT حداکثر ۱۸۰ ثانیه برای آزادشدن آن صبر می‌کند. تمام‌شدن این مهلت خطای واقعی است و همان مرحله متوقف می‌شود؛ نصاب قفل را حذف نمی‌کند، فرایند دیگر را نمی‌کشد و نصب را بی‌قید تکرار نمی‌کند. این گزینه تضمین انتظار برای تمام قفل‌های APT، از جمله قفل فهرست مخزن، نیست.

خطای اندازه یا checksum بسته/فهرست را جداگانه بررسی کنید. پس از ثبت خطا و بررسی نشانی مخزن و وضعیت proxy/cache، دریافت سازگار از مخزن رسمی و قابل‌اعتماد را دوباره انجام دهید. بررسی امضای Release، checksum بسته و TLS باید برقرار بماند؛ `--allow-unauthenticated`، خاموش‌کردن TLS یا حذف فایل قفل راه‌حل نیست. `apt-get update` نیز با `APT::Update::Error-Mode=any` اجرا می‌شود تا شکست دریافت فهرست به‌عنوان آماده‌بودن مخزن گزارش نشود.

## restore اصلی روی همان میزبان

فرمان اصلی restore بدون تغییر محتوای اسکریپت اجرا شد. safety backup داخلی و کنترل دسترسی جاری حفظ شدند. جایگزینی دیتابیس و رسانه، بررسی اصلی، اعمال امنیت و startup/check-health معمول در روند اصلی فعال بودند؛ کنترل image، release، TLS یا آنتی‌ویروس کنار گذاشته نشد.

اجرا در `09:15:59.075464 UTC` آغاز و در `09:51:10.969524 UTC` با خروج **۰** پایان یافت؛ مدت واقعی **۳۵ دقیقه و ۱۱٫۸۹۴ ثانیه** بود. انتظار فرزند اصلی، observer و collector دریافت شد. [رسید فشردهٔ restore](verification-evidence/repair-2.1.2/same-host-seed-restore-script-20261024.json)، [خروج واقعی فرزند](verification-evidence/repair-2.1.2/same-host-seed-restore-outcome-20261024.json) و [رسید گردآوری](verification-evidence/repair-2.1.2/same-host-seed-restore-collection-20261024.json).

این اجرا از ابزار عملیات جدید به کمک alias خصوصی deployment و پیوند عادی metadata همان release استفاده کرد. نصب تازه و کامل ZIP ابزار فراخوان روی میزبان تمیز ادعا نمی‌شود؛ سورس داخل آرشیو، image و `current` هویت قبلی خود را حفظ کردند.

## مرحلهٔ واقعی فایل پاک و EICAR

اجرای نخستِ fixture پس از readback بالا، در `09:58:41.443702 UTC` با خروج ۱ و خطای `Unexpected end of JSON input` پایان یافت. هیچ assertion کامل نشده و مراحل مشتری، کارکنان، صفحه و آپلود هنوز نرسیده بودند. ابزار پیش از بررسی status، JSON را parse می‌کرد؛ روش، مسیر و status پاسخ اصلی ثبت نشده است. وجود یا نبود نشست اولیه یا enrollment ناتمام مالک نیز از نتیجهٔ ناقص معلوم نیست. [رسید شکست نخست](verification-evidence/repair-2.1.2/api-seed-01-failure-20261024.json).

مقایسهٔ محدود و ناشناس با همان Node 24.22.1، بدون رمز یا cookie ورودی، اختلاف مسیر انتقال را ثبت کرد: Fetch به `http://proxy` با Host درخواستیِ متفاوت، HTTP ۲۰۰ با بدنهٔ صفر و بدون JSON/cookie گرفت؛ درخواست `node:http` با Host صریح همان endpoint، HTTP ۲۰۰ و JSON معتبر نشست ناشناس و یک cookie دریافت کرد. این مقایسه، پاسخ ثبت‌نشدهٔ درخواست اولیه را بازسازی نمی‌کند. [رسید مقایسهٔ ناشناس](verification-evidence/repair-2.1.2/api-bootstrap-transport-01.safe.json).

برای ادامه، فقط launcher پذیرش تغییر کرد: یک کانتینر کم‌اختیار و فقط‌خواندنی با همان image تغییرناپذیر، از شبکهٔ میزبان به origin واقعیِ loopback سایت درخواست داد. driver، timeout و نحوهٔ پردازش درخواست آن تغییر نکردند؛ شبکه یا سیاست Host سرویس‌های اصلی نیز دست‌نخورده ماندند. رمز، MFA یا SQL بازنشانی نشد.

اجرای `api-seed-02` در `10:09:47.245919 UTC` آغاز شد و در `10:12:45.256064 UTC` با خروج **۰** پایان یافت. هر **۱۲ assertion** موفق شد و انتظار فرزند، observer و collector دریافت شد:

چرخهٔ تازه‌ای برای بکاپِ داده‌های اکنون ایجادشده، تغییر با API اصلی، restore همان میزبان و verify اصلی در انتظار است تا فایل آپلودی، غیرفعال‌سازی کارکنان، لغو نشست و حذف حریم خصوصی با fixture غیرخالی بررسی شوند. هیچ نتیجه‌ای از این چرخه هنوز پذیرفته نشده است. آرشیو تاریخی `708049…` با دامنهٔ seed-only حفظ می‌شود و ابزار عملیات مورد استفاده همچنان همان ZIP `3552…` است؛ بسته‌بندی تازهٔ مستندات، هویت آن ابزار را عوض نمی‌کند.

## وضعیت‌های باقی‌مانده و تاریخچه

نصاب کاملِ تلاش ۶ همچنان با خروج ۱۲۴ در نخستین snapshot بکاپ ناموفق است؛ موفقیت بعدی بکاپ و restore مستقل، آن خروج تاریخی را بازنویسی نمی‌کند. build05 بومی، بازیابی روی میزبان مستقل، ماتریس کامل Lighthouse و آزمون واقعی AI/SMTP/SMS با حساب مالک و DNS/TLS عمومی هنوز تکمیل نشده‌اند. دامنهٔ نتایج تاریخی build02/03/04 نیز حفظ می‌شود.

observer فایل‌های پیشرفت ابتدا قالب JSON خطای lifecycle را اشتباه تشخیص می‌داد. آرایه‌های خالی خطا در پیشرفت‌های ۰۱ تا ۰۶ شاهد نبود خطا نیستند؛ markerهای مرحله و خروج واقعی همچنان محفوظ‌اند. decoder پیش از نتیجهٔ نهایی اصلاح شد و بازخوانی کامل لاگِ گردآوری‌شده، همراه با خروج واقعی، مبنای نتیجهٔ نهایی است. [رسید اصلاح decoder](verification-evidence/repair-2.1.2/restore-observer-decoder-correction-20261024.json). تاریخچهٔ heartbeat و لاگ خصوصی داخل بسته منتشر نشده‌اند.

هر رسید SAFE زمان و دامنهٔ مشاهدهٔ خودش را دارد؛ مثلاً رسید بکاپ در زمان پایان دانلود، restore را هنوز اجراشده نمی‌دانست و رسیدهای بعدی نتیجهٔ آن را اضافه می‌کنند. فایل‌های قدیمی تغییر نکرده‌اند؛ عبارت‌های «در انتظار» در گزارش‌های محفوظ مراحل قبلی به زمان ثبت همان گزارش تعلق دارند. مرجع جاری، [گزارش پذیرش](VERIFICATION.fa.md)، [خلاصهٔ وضعیت](CURRENT-VALIDATION.fa.md) و [خلاصهٔ ماشینی](verification-evidence/repair-2.1.2/acceptance.json) است؛ فرمان‌های مالک در [راهنمای بکاپ/بازیابی](BACKUP-RESTORE.fa.md) باقی‌اند.

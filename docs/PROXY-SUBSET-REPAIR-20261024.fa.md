# اصلاح ازسرگیری دقیق سرویس‌های ثبت‌شده — ۲۴ اکتبر ۲۰۲۶

## نقص بازتولیدشده

بکاپ، مجموعهٔ سرویس‌های در حال اجرا را ثبت می‌کند تا پس از پایان کار همان مجموعه را از سر بگیرد. پس از شکست نصب ششم، app و worker با cleanup نصاب متوقف بودند و proxy روشن مانده بود. بررسی کد پیش از اجرای بکاپ بعدی نشان داد که ازسرگیری snapshot شامل proxy، همیشه منتظر پاسخ عمومی app می‌ماند؛ درحالی‌که app عمداً در مجموعهٔ ثبت‌شده نبود.

آزمون قدیمی هر هشت زیرمجموعه، پاسخ HTTP را همواره موفق فرض می‌کرد. آزمون جدید با app خاموش و HTTP ناموفق، شکست نسخهٔ قبلی را برای دو مجموعهٔ `proxy` و `worker + proxy` بازتولید کرد. این نقص با انقضای مهلت snapshot نصب ششم متفاوت است؛ timeout آن اجرا دلیل این تغییر نیست.

## رفتار اصلاح‌شده و حدود آن

در `Lifecycle.start(existing=...)` فقط هنگام ازسرگیری مجموعهٔ ثبت‌شده، پاسخ عمومی زمانی لازم است که **هر دو سرویس app و proxy در همان مجموعه حضور داشته باشند**. بررسی سلامت و هویت کانتینرها همچنان اجرا می‌شود. سرویس غایب روشن یا ساخته نمی‌شود و شناسهٔ ثبت‌شده تغییر نمی‌کند.

| مسیر | پاسخ معتبر عمومی لازم است؟ |
| --- | --- |
| ازسرگیری snapshot فقط شامل proxy | خیر؛ app عمداً غایب است |
| ازسرگیری snapshot شامل worker و proxy | خیر؛ سلامت worker و هویت هر دو سرویس بررسی می‌شود |
| ازسرگیری snapshot شامل app و proxy | بله |
| ازسرگیری هر سه سرویس | بله |
| اجرای جدید `up` با proxy | بله؛ رفتار قبلی حفظ شده |
| اجرای صریح `check` با proxy | بله؛ رفتار قبلی حفظ شده |

پارامتر `require_public` در `wait_ready` پیش‌فرض `True` دارد. فقط ازسرگیری snapshot آن را بر اساس مجموعهٔ ثبت‌شده تعیین می‌کند. سقف زمانی snapshot همچنان ۳۰ ثانیه است؛ متغیر env جدیدی اضافه نشده و مهلت کلی، inspect، probe، کنترل هویت، آنتی‌ویروس، خروجی، لغو و cleanup تغییر نکرده‌اند.

آزمون متمرکز از ساعت و driver آزمایشی موجود استفاده کرد و فراخوانی واقعی Docker یا HTTP نداشت. مجموعهٔ کامل از Compose `2.40.3` و age `1.1.1` با اصالت و hash بررسی‌شده و fixtureهای محلی استفاده کرد؛ Docker daemon، VM یا بکاپ واقعی در این مجموعه اجرا نشد. دو روش جدید شمار قبلی ۲۰۴ را به ۲۰۶ رسانده‌اند؛ سه روش متمرکز به مجموع ۲۰۶ افزوده نمی‌شوند.

## وضعیت واقعی نصب و بکاپ

این اصلاح پس از تلاش ۶ آماده شد و هنوز روی میزبان اولیه مستقر نشده است. نصب ششم از ZIP `1b2dd59c60a97bd1c113f6fdf7faaa330d6ca3157ccf3187b94f37eb4cecb806` استفاده کرد. مرحلهٔ کامپایل Docker از cache بود؛ migration خروج صفر داشت. نصاب اصلی از startup و `check-health 240` عبور کرد، سپس `snapshot --timeout 30` در اولین بکاپ با `DEADLINE_EXCEEDED` شکست خورد و کل نصب با خروج ۱۲۴ پایان یافت. cleanup نصاب app و worker را متوقف کرد. [خروج واقعی نصب](verification-evidence/repair-2.1.2/installer-06-outcome-20261024.json) و [شرح دقیق مرحله و وضعیت نهایی](verification-evidence/repair-2.1.2/installer-06-final-state-20261024.json).

مهلت ۳۰ ثانیه، انتخاب صریح فراخواننده بود؛ افزایش timeout یا افزودن تنظیم تازه برای عبور از این اجرا انجام نشده است. بکاپ در همان snapshot و پیش از dump و رمزنگاری متوقف شد؛ پذیرش بکاپ کامل یا دانلود ثبت نشده است. یک اجرای مستقل بکاپ با ابزار عملیات جدیدِ مورد اعتماد در انتظار است. منبع نصب‌شده و مرجع سورس آرشیو همان نسخهٔ نصب ششم باقی می‌ماند؛ آن اجرای محدود جای پذیرش نصب کامل را نمی‌گیرد.

ساخت بومی ۰۵، اسکن واقعی فایل پاک/EICAR، restore، recover روی میزبان مستقل و Lighthouse تمام موجودی نیز هنوز تکمیل نشده‌اند. دامنهٔ هر گیت در [گزارش پذیرش](VERIFICATION.fa.md) و [خلاصهٔ ماشینی](verification-evidence/repair-2.1.2/acceptance.json) آمده است. مسیرهای workspace داخل رسیدها صرفاً منشأ اجرا را ثبت می‌کنند و لاگ خام، env یا کلید خصوصی همراه بسته نیست.

# طرح پیاده‌سازی سروری ایده‌آل ماکو

## مبنا و اولویت اسناد

مبنای اجرا، آخرین فرانت‌اند ارسال‌شده و `ORIGINAL-SPEC.md` است. سندها و جدول‌های ارسال‌شده در گفتگوهای قبلی نیز خوانده شده‌اند. درخواست جدید مالک، بک‌اند، دیتابیس، DevOps، Docker، تست و اجرای واقعی را به محدودهٔ قبلی اضافه می‌کند.

سند اصلی PostgreSQL 16 و مسیر Next.js/TypeScript را مشخص کرده است. این نسخه از SQL migration و node-postgres استفاده می‌کند. Payload یا Lexical بدون استفاده به dependency اضافه نشده‌اند؛ ویرایشگر متن امن از Markdown پشتیبانی می‌کند. تفاوت با درخواست‌های جزئی اسناد قدیمی در ماتریس پوشش ذکر می‌شود.

## تقسیم کار

سه مسیر موازی برای بک‌اند CMS/CRM، اتصال رابط و آزمون مرورگر، و DevOps/بازیابی/اتوماسیون اجرا شده است. ریشهٔ یکپارچه‌سازی، احراز هویت و مجوز API، درخواست‌ها، فایل و PDF، AI، سازمان‌ها و پذیرش نهایی را پوشش می‌دهد. نتایج هر مسیر روی یک کد و یک قرارداد سرور ادغام می‌شود.

## دامنهٔ نهایی سورس و وضعیت پذیرش

۴۱ migration شماره‌گذاری‌شده تا 042، با نبود شمارهٔ 005، گردش‌های تخصصی مخاطب/حساب، scope تیم/قلمرو، قیمت‌نامه/پیش‌فاکتور ثابت، pipeline/routing، کمپین و رضایت کانال، ورودی connector/CSV، task/reminder، منابع/data room، مناقصه، privacy/ledger، پایش/incident، DAM، RAG عمومی، نماینده، wishlist، گواهی شرکت، glossary، قالب تراکنشی، تاریخچهٔ فرم/گردش ویرایشگر، کارکنان env، سهمیهٔ storage، پیشنهاد یک‌بارهٔ ترجمه، ثبت اصالت و فهرست صفحه‌بندی‌شدهٔ کارکنان/مشتریان را پوشش می‌دهند. رابط‌های production از API و capability/نسخهٔ واقعی استفاده می‌کنند؛ نتیجهٔ mutation قبل از پاسخ سرور موفق نشان داده نمی‌شود. جدول بندبه‌بند و حدود هر گردش در [ماتریس جاری](PRODUCTION-COVERAGE.fa.md) است.

در بازسازی پس از حذف مسیر موقت، 001–024 دقیقاً از checkpoint برگشتند و 025–034 با checksum تازه بازسازی شدند. ledger تاریخی حفظ شد؛ پذیرش روی DB تازه انجام می‌شود. مسیر populated upgrade سازمان/CRM و recipient کمپین جدا آزموده شده است. جایگزینی اجباری checksum، حذف migration ناموفق یا نادیده‌گرفتن TypeScript روش پذیرش نیست.

گیت‌های نسخهٔ ۲.۱ طبق [برنامهٔ اصلاح و پذیرش](PRODUCTION-REPAIR-PLAN.fa.md) اجرا می‌شوند. پس از اصلاح فهرست کاربران، ۵۸۷ Unit، ۴۸۳ PostgreSQL، ۲۰ API و ۴۲ سناریوی مرورگر با برنامهٔ فعلی موفق شدند؛ runtime همان اجراها در [گزارش پذیرش](VERIFICATION.fa.md) مشخص است. اصلاح بعدی تایمر بکاپ و هویت URL، برنامه را تغییر نداد و هفت و ۲۹ آزمون متمرکز موفق دارد؛ قبولی گیت کامل و build runtime تازه هنوز ثبت نشده است. DB مستقل تحویل آماده و سرویس‌های بومی برای VM متوقف‌اند. نصب/بازیابی نهایی، Lighthouse و انتشار مقصد فقط با نتیجهٔ واقعی همان اجرا تکمیل می‌شوند. شاهد P08/CRM-032 همچنان دو سازمان، RFQ/تبدیل، پیش‌فاکتور پنج زبان، پاسخ مشتری، گزارش ارزی و نمونه/کیفیت را از HTTP واقعی و UI می‌سنجد.

بازیابی format3 باید سورس و پیکربندی، تمام DB، فایل‌ها و دفتر privacy را با احراز اصالت مستقل بازگرداند و هم‌زمان نشست‌ها، کدهای بازیابی و اختیارهای منسوخ را احیا نکند. نتیجهٔ تمرین native قدیمی با ۳۷ migration تاریخی است؛ شاهد جاری باید ۴۱ migration، hash داده/فایل و نصب میزبان تازه را پوشش دهد.

نصاب تک‌فرمانی و Compose همراه کد هستند؛ وضعیت اجرای واقعی Ubuntu/Docker در گزارش پذیرش درج می‌شود. DNS/TLS عمومی و provider زنده به دامنه و کلید مقصد نیاز دارند. ارسال‌ها پیش‌فرض غیرفعال‌اند. Caddy پراکسی این پشته است و SMTP تنظیم‌پذیر است؛ Postfix یا Payload به عنوان سرویس نصب‌شده ادعا نمی‌شوند.

## معیار تحویل

- ذخیرهٔ موفق فقط پس از پاسخ موفق سرور در رابط اعلام شود.
- حساب ناشناس یا نقش جعل‌شده در مرورگر به دادهٔ حساب دیگر دسترسی پیدا نکند.
- خاموش‌بودن provider یا اسکنر، موفقیت مصنوعی ایجاد نکند.
- انتشار و پیش‌فاکتور فقط با نسخه و بازبینی معتبر انجام شوند.
- جست‌وجو و صفحه‌بندی حساب‌ها با بیش از هزار مشتری جدیدتر، زمان‌های برابر و دقت میکروثانیه آزموده شوند؛ حساب قدیمی برای ویرایش یا خاتمهٔ دسترسی پنهان نشود و لغو نقش/MFA در صفحهٔ بعد مؤثر باشد.
- migration واقعی دو بار اجرا شود؛ اجرای دوم ledger، index و داده را تغییر ندهد. بازیابی داده واقعاً اجرا و نتایج ثبت شوند.
- اجرای کانتینر، SSH مقصد و اتصال بیرونی فقط در صورت اجرای واقعی موفق، تأییدشده اعلام شوند.
- موارد باقی‌ماندهٔ سند در `PRODUCTION-COVERAGE.fa.md` و نتایج در `VERIFICATION.fa.md` به‌صورت مشخص ثبت شوند.

## تفکیک تکمیل کد از راه‌اندازی مقصد

ایجاد Dockerfile، نصاب و CI، به معنی مشاهدهٔ اجرای آن‌ها روی مقصد نیست. بسته شامل مسیر اجرای این کنترل‌هاست؛ شواهد همین محیط و موارد نیازمند دسترسی مقصد جداگانه ثبت می‌شوند. هدف این تفکیک آن است که اپراتور بداند کدام رفتار را می‌تواند با مدرک بررسی کند و کدام مرحله هنوز باید روی زیرساخت نهایی اجرا شود.
